前面 P3–P5 你学的大多是行存（row-oriented）页式或日志结构：`一条记录的字节连在一起`。很多 OLTP 系统这样设计很合理。但分析型负载（OLAP）常常只扫少数几列、却要处理海量行——列式存储（column-oriented）为此而生。**P6-1 开始**

**今天这次的目标**
- 我们现在正式开始 `P6`，主题是：`列式存储数据库`。
- 这一段建立总框架：行存 vs 列存、OLAP 动机、和 bustub 行存主线的关系。
- 你学完这一段后，应该能回答 3 个问题：
- 为什么 OLAP 更适合列存而不是行存。
- 列存在磁盘上“按列连续”是什么意思。
- bustub 行存主线和列存思想在哪里仍能相通。

**先把 `P5` 和 `P6` 接起来**
- `P3/P4`：行存 page 内 tuple 连续存放，点查/更新友好。
- `P5`：另一种写路径哲学（append-only），但仍常是 row-wise record。
- `P6`：换的是`数据在 page 内的组织维度`——按列聚簇，而不是按行。

- 不是“列存取代行存”，而是`负载不同，物理格式不同`。

**本课英文名词速查（先看这一段再往下读）**
- P6 英文词也不少。下面按“中文意思 → 它在系统里干什么”解释；后文再出现时你可随时回查。

| 英文 | 中文意思 | 一句话 |
|------|----------|--------|
| row-oriented / row store | 行存 | 同一行的各列相邻存放，读整行友好 |
| column-oriented / column store | 列存 | 同一列的多行值相邻存放，扫少列友好 |
| OLAP | 联机分析处理 | 大范围扫描、聚合、分组，点查/频繁更新相对少 |
| OLTP | 联机事务处理 | 大量单行读写、短事务、更新频繁 |
| HTAP | 混合事务/分析处理 | 试图同时兼顾 OLTP 与 OLAP 的一类系统 |
| Column chunk | 列块 / 列段 | 一列的一段连续值（常按一批行切，如约 64K 行） |
| rowid / row index | 行号 / 行下标 | 用来对齐不同列上“同一条逻辑行” |
| projection pruning | 投影裁剪 | 计划里只保留需要的列，少算（行存未必少读盘） |
| predicate / filter pushdown | 谓词下推 | 把 WHERE 尽量靠近存储扫描，早过滤 |
| Vectorized execution | 向量化执行 | 一次处理一列向量（一批值），而不是一次一行 |
| Volcano model | Volcano 模型 | 逐 tuple 拉取：`Next()` 一次返回一行 |
| Late materialization | 延迟物化 | 先在列上 filter/聚合，最后再按需拼成完整行 |
| Early materialization | 早期物化 | 很早拼出宽行，再 filter/聚合 |
| Dictionary encoding | 字典编码 | 重复值多时存“字典 + id 列” |
| RLE (Run-Length Encoding) | 游程编码 | 连续相同值压成 `(value, count)` |
| Bit packing | 位打包 | 小范围整数用更少 bit 存，而不是整型全宽 |
| Delta encoding | 差分编码 | 存相邻差值，适合递增 id/时间戳 |
| Zone map / min-max | 区间图 / 最小最大统计 | 每个 block 记 min/max，用于跳过无关块 |
| NULL bitmap | 空值位图 | 标记哪些位置是 NULL |
| SIMD | 单指令多数据 | CPU 一条指令同时处理多个同类型值 |
| ColumnVector / ColumnBatch | 列向量 / 列批次 | 一批同类型列值 + 可选 null bitmap |
| Parquet | Parquet 文件格式 | 分析生态常见的列式 interchange 格式 |
| row group | 行组 | Parquet 等格式里一批行的列块集合 |
| lakehouse | 湖仓一体 | 常把数据湖文件（如 Parquet）当分析表管理 |
| bytes_read | 读入字节数 | 实验主指标：真正从存储读了多少字节 |
| cardinality | 基数 | 一列有多少不同取值；低基数更适合字典编码 |
| selectivity | 选择性 | filter 后剩下比例；影响延迟物化是否划算 |
| mask | 掩码 | 向量化 filter 后标记哪些位置被选中 |

- 最容易混的几组（**易混点总整理**，先钉死再往下读）：

**1. P6-1 和 P6-2 各讲什么**
| 分段 | 主线 |
|------|------|
| P6-1 | **物理布局 + 负载选型**：行存 vs 列存，OLTP vs OLAP |
| P6-2 | **叠在列存上的三板斧**：压缩、延迟物化、向量化执行 |

- P6-1 还不重点讲执行模型；P6-2 才对比 Volcano 逐行 vs 向量化批处理。
- 不要概括成：“P6-1/2 讲的就是按行执行还是按列执行”——那会把布局和执行模型混在一起。

**2. 列存、压缩、延迟物化、向量化分别是什么**

| 概念 | 归类 | 一句话 |
|------|------|--------|
| 列存（column store） | **物理布局** | 同一列的值相邻存放 |
| 压缩（compression） | **存储（编码）优化** | 用更少字节表示列值；列存特别好压，但压缩 ≠ 列存的一种 |
| 延迟物化（late materialization） | **执行 / 读路径优化** | 先 filter，再按 rowid 取需要的列拼行 |
| 向量化执行（vectorized execution） | **执行模型** | `NextBatch()` 一次处理一批值；相对 Volcano 的 `Next()` 逐行 |

```text
列存 = 怎么存
压缩 = 存得省（尤其适配列存；列存也可以不压缩）
延迟物化 = 何时拼行（先滤后取）
向量化 = 怎么算（一批批算；≠ 多线程）
```

**3. 最容易说错的话（对照改正）**
- 错：`压缩是列存的一种方式。`  
  对：`压缩是存储编码优化；可以叠在列存上，列存也可以不压缩。`
- 错：`延迟物化就是另一种列存格式。`  
  对：`延迟物化是读路径/执行策略：先过滤后拼行。`
- 错：`向量化 = 列存。`  
  对：`列存是布局，向量化是执行模型；常一起出现，但可以分开理解。`
- 错：`向量化 = 多线程并行。`  
  对：`向量化首先是 batch/SIMD 批处理；并行是另一层。`
- 错：`P6-1 和 P6-2 讲的都是按行/按列怎么执行。`  
  对：`P6-1 先讲怎么存、适合什么负载；P6-2 再讲压缩、何时拼行、以及一批批怎么算。`

**4. 一层记忆卡**
```text
布局层:  行存 / 列存
存储优化: 压缩、zone map
读路径优化: 延迟物化（相对早期物化）
执行模型: Volcano 逐行 / 向量化批处理
```

**先给你一张总图**

```text
行存 (bustub 主线)                 列存 (OLAP 常见)
-------------------                 ----------------
Page: [row1][row2][row3]...         Column chunk: [v1,v2,v3,...] 只含一列
点查一行：读一条 tuple               聚合一列：顺序读连续值，IO 少
更新一行：改一条 tuple               更新一行：可能要改多列文件
```

- 逻辑上仍是同一张表；物理布局不同。

---

**问题定义**
- 什么是行存（row-oriented / row store）？
- `同一记录的各列在存储上相邻放置，读一行时局部性好。`

- 什么是列存（column-oriented / column store）？
- `同一列的多行值在存储上相邻放置，读一列时局部性好。`

- 什么是 OLAP（Online Analytical Processing，联机分析处理）？
- `在线分析处理：大范围扫描、聚合、分组、少列投影，单行点查和频繁更新相对少。`

- 什么是 OLTP（Online Transaction Processing，联机事务处理）？
- `在线事务处理：大量单行读写、短事务、更新频繁。`

---

**为什么 OLAP 更适合列存**
- 典型查询：

```sql
SELECT region, SUM(sales)
FROM orders
WHERE year = 2024
GROUP BY region;
```

- 可能只需要 `region`、`sales`、`year` 三列。
- 表可能有 50 列。

**行存要读什么**
- 每条 record 含 50 列，即使用户只要 3 列。
- 扫描 10 亿行 -> 读入大量无用列 bytes -> I/O 和 cache 浪费。

**列存要读什么**
- 只读 `year` 列 chunk、`region` 列 chunk、`sales` 列 chunk。
- 读入字节量 ≈ 3/50 的行宽比例，数量级节省。

**第一性原理结论**
- `当查询只需要少数列时，按列连续存储能直接减少 I/O 和内存带宽。`

---

**为什么列存对点查和频繁更新不友好**
- 读整行：
- 行存：一次 tuple 读取。
- 列存：要到 N 个列文件/chunk 各读一块，再按 rowid 拼回。

- 更新一行：
- 行存：改一条 tuple（或 page 内 relocation）。
- 列存：可能更新多列存储结构，维护 rowid 映射，代价高。

- 所以列存常见于：
- 数据仓库、ClickHouse、Redshift、Parquet 分析文件
- 而不是高频 OLTP 主库（虽有混合系统）。

---

**列存在磁盘上的样子（直觉）**

```text
表 Orders(rowid, region, sales, year, ...)

列文件 region.col:  [East, West, East, ...]
列文件 sales.col:   [100, 250, 80, ...]
列文件 year.col:    [2023, 2024, 2024, ...]
```

- 每列可有：
- 压缩编码（dictionary 字典编码、RLE 游程编码、bit packing 位打包）
- zone map / min-max 索引（区间统计，跳过不相关 block）

- rowid 或 implicit row index（隐式行下标）用于对齐不同列的同一条逻辑行。

---

**和 bustub 的关系**
- bustub 主线：行存 TableHeap + Tuple。
- 但以下思想相通：
- **投影裁剪（projection pruning）**：优化器只读需要的列；列存是物理层天然裁剪。
- **谓词下推（predicate / filter pushdown）**：WHERE 在存储层过滤；列存可在列 chunk 上先 filter。
- **批处理**：Volcano 逐 tuple 慢；列存常配合向量化 batch（批次）执行。

- 你在 bustub 做 SeqScan 时若 schema 很宽，可以 mentally 对比“若列存会少读多少”。

---

**核心术语入门（与上方速查表对照）**
- `Column chunk`（列块）：一列的一段连续值（常 64K 行一批）。
- `Vectorized execution`（向量化执行）：一次处理一列向量而不是一行。
- `Late materialization`（延迟物化）：先 filter/aggregate 列向量，最后再拼完整行。
- `Dictionary encoding`（字典编码）：列中重复值多，存 dict + id 列。
- `RLE`（游程编码）：连续相同值压成 (value, count)。
- `Zone map`（区间图）：每个 block 的 min/max，用于跳过。

---

**不变量（列存视角）**
- `C1`：不同列的同 row index 应对齐同一逻辑行（在同一 snapshot 下）。
- `C2`：压缩块必须可解码为与 schema 一致的类型。
- `C3`：late materialization 拼行时 rowid 映射必须一致，不能串行。

---

**没有列存视角会怎样**
- 以为“宽表 scan 慢只能加索引”，想不到投影列数决定 I/O。
- 读 Parquet/ClickHouse 文档只会背“列存快”，说不清快在哪个硬件路径（带宽、cache、SIMD）。

---

**硬件路径：为什么列存 + 向量化常一对出现**
- 列 chunk 是同质类型连续数组 -> CPU SIMD 一条指令处理多个值。
- 分支预测友好：对整列做 `year == 2024` 过滤。
- cache line 利用率高：读 sales 列不会把无关 string 列拉进 cache。

```text
行存 scan:  load 混合类型 row -> 解析 -> 判断 -> 累加  (循环开销大)
列存 scan:  load sales[i..i+8] -> SIMD add/filter      (批处理)
```

---

**初学者易错点**
- 以为列存“所有查询都快”——整行点查可能更慢。
- 把 Parquet 文件格式当成“数据库 buffer pool”——它是分析 interchange，层次不同。
- 忽略 rowid 对齐：两列 filter 后 merge rowid 错了，聚合全错。
- 把“列存”和“向量化执行”当成同一件事：前者是布局，后者是执行模型；它们常一起出现，但可以分开理解。

---

**从硬件路径再看一遍为什么列存划算**
- 分析型查询的热点往往不是“算得复杂”，而是“扫得太多”。
- 行存扫一张宽表时，即使你只需要 1 列，也会把相邻列一起读进 page / cache line。
- 列存把同一列连续放，收益会落到三条物理路径上：
- 磁盘 / SSD：读到的字节更接近真正用到的字节，I/O 更少。
- CPU cache：同一列数值类型一致、相邻访问，更容易命中缓存，也更容易 SIMD。
- 压缩：同列取值分布往往更规律，字典编码、RLE、bit packing 更有效。

- 所以你要记住一句话：
- `列存的价值，首先来自“少读、好压、好批处理”，不是来自“把表竖着画更好看”。`

---

**什么时候不该迷信列存**
- 高频点查：`SELECT * FROM t WHERE id = ?`
- 列存可能要到多列文件/段里拼回一行，局部性反而差。
- 高频单行更新 / 短事务：
- 行存改一页就能完成；列存往往要动多个列段，还可能牵动压缩块重写。
- 宽结果、少过滤、结果几乎要整行输出的查询：
- 列存的“少读列”优势会被“最后拼行”的代价吃掉一部分。

- 这也是为什么：
- OLTP 系统更常行存。
- OLAP / 数仓更常列存。
- HTAP（Hybrid Transactional/Analytical Processing，混合事务分析）系统会在两者之间做混合或分层。

---

**它和前面几课怎么接**
- `P3` 的 page / tuple layout，默认语境是行存堆表。
- `P5` 的日志结构，强调写路径变成追加；列存则更强调读路径按列组织。
- `P1/P2` 里的投影裁剪、谓词下推，在列存里收益往往更大：因为少读一列，真的少读一大块连续数据。
- 所以即使你主线还在做 bustub 行存，这节课也不是“旁支选修”，而是帮你看清：
- `同一条 SQL 语义，换一种物理布局，代价模型会完全换一套。`
