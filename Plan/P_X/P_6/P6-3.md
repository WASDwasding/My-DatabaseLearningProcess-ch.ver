**bustub 主线：行存 TableHeap 回顾**
- Tuple 在 TablePage 内 row-wise（按行）存放。
- SeqScanExecutor 逐 tuple 调用 Next()。
- Optimizer 可做 projection pruning（投影裁剪）、filter pushdown（谓词下推）（逻辑层）。

```text
bustub 现状:
  Storage: row-oriented page
  Execution: Volcano tuple-at-a-time (mostly)
  Optimizer: logical rewrite, column pruning at plan level
```

- 列存是物理层重组；bustub 在逻辑层已部分体现“少算少读”。

---

**优化器层面的相通：投影裁剪（projection pruning）**
- SQL：

```sql
SELECT name FROM Student WHERE age > 20;
```

- Planner 可生成只输出 `name` 的投影计划。
- 行存执行时仍读整 tuple bytes，但 executor 上层只传递 `name` 列。

**与列存的差距**
- 逻辑裁剪 != 物理 I/O 裁剪。
- 行存仍从 disk 读整行；列存只读 name 列文件。

**学习价值**
- 理解 optimizer 的 projection 是“不算多余列”，列存是“不读多余列”。
- 两层优化叠加才是 OLAP 系统极致。

---

**谓词下推（predicate / filter pushdown）的相通与差距**
- Optimizer 把 filter 下推到 SeqScan 附近。
- 行存：每个 tuple 读入后 evaluate predicate。
- 列存：可在 compressed column block 上先 filter，甚至 zone map skip 整块。

- bustub 中 predicate 在 SeqScan 或 Filter 算子执行。
- 若你有 zone map（列存），filter 可在读块之前发生。

---

**执行器：Volcano 与向量化扩展路径**
- 当前 bustub：

```cpp
bool Next(Tuple *tuple, RID *rid);
```

- 向量化扩展（hypothetical，假想扩展）：

```cpp
bool NextBatch(ColumnBatch *batch);
```

- 最小扩展步骤（课程项目级）：
- 1. 定义 ColumnVector 结构（固定类型数组 + null bitmap 空值位图）
- 2. 实现 ColumnScan 从列文件读 batch
- 3. FilterExecutor 对 ColumnVector 做 mask（掩码）
- 4. Aggregate 对 ColumnVector 做 SIMD sum

- 不必先改 TableHeap，可并行做 `ColumnStoreFile` 实验模块。

**最小对比实验：同一表两种布局**
- 准备：100 万行，20 列，其中 1 列 int 做 SUM，1 列 int 做 WHERE。

**行存版本**
- 用 TableHeap 或简单文件：每行 20*8 字节定长。
- 扫描：读每行 160B，解析，filter，累加。

**列存版本**
- 两个文件：`year.col`、`sales.col`，各 100 万 * 8B。
- 扫描：先读 year 列 filter 得 rowids，再读 sales 对应位置。

**度量**
- `bytes_read`（读入字节）：主指标。
- `wall_time`（墙上时间）：次指标（教学环境可粗略）。
- 预期：列存 bytes_read ≈ 行存 * (2/20) 量级（只看两列时）。

**实验报告要回答**
- 行存瓶颈在 I/O 还是 CPU？
- 列存 filter 选择性变化如何影响第二步随机读 sales？

**最小整数列压缩实验**
- 对 sales 列（值域 0–1000）：
- 原始 4B * N
- bit pack 到 10 bit * N
- 对比文件大小与 decode（解码）时间

- 体会：压缩率 vs CPU decompress tradeoff（权衡）。

---

**Parquet / CSV 作为对照（概念）**
- Parquet：列式、嵌套、压缩，分析生态标准文件格式（interchange，交换格式）。
- bustub 不必实现 Parquet，但读文档时可对照：
- row group（行组）= 一批 row 的 column chunks
- page 级 dictionary/RLE

- 帮助理解工业列存不是“一个 .col 文件”那么简单，有分层索引与统计。

---

**列存更新难：若实验要做 UPDATE**
- 行存 bustub：UpdateTuple relocation（迁移）。
- 列存：每列文件可能要 rewrite chunk，或 delta + merge。
- 教学实验建议：**只读 OLAP 查询，不做 UPDATE**，避免复杂度爆炸。

---

**调试列存实验常见问题**
- rowid 不对齐：year filter 的 index 与 sales 列顺序假设不一致。
- 忘记 null bitmap：filter 结果含 NULL 行。
- 压缩块边界：点查 row 500000 需先定位 block。
- 选择性极低时 random access sales 劣于全列 scan——要测 crossover（交叉点：哪种策略开始更优）。

---

**与 LSM / P5 的交叉视角**
- LSM SST 内也可 columnar block（如 Parquet in Delta Lake）。
- 写路径 append + 列存 block = 现代 lakehouse（湖仓）常见形态。
- 你学的 P5 segment 与 P6 column chunk 可以组合理解。

---

**bustub 源码阅读建议（对照列存概念）**
- `SeqScanExecutor`：tuple-at-a-time（逐行）路径。
- `Planner` / `Optimizer`：projection、filter pushdown。
- `Tuple` / `Schema`：列类型与 offset——行内布局。
- 思考：若 Schema 按 column file 存，Catalog 要什么 metadata（元数据）？

---

**扩展项目分级**
- **Level A（推荐）**：行/列文件对比实验 + bytes_read 报告。
- **Level B**：单列 dictionary 压缩 + decode scan。
- **Level C**：ColumnVector + batch filter executor。
- **Level D**：改 storage engine 接 bustub optimizer（大工程）。

- 按时间选一级，不要一口吃 D。

---

**初学者易错点**
- 以为 bustub 有列存——默认没有，是对照学习。
- 实验只比 time 不比 bytes，结论模糊。
- 列存实验用宽行点查当主 benchmark（基准测试）——选错负载。
- 忽略 NULL 与变长列，实验全是定长 int 却推广到 string 列。
