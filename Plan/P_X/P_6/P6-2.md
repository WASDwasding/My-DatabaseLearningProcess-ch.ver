**压缩：为什么列存更容易压**
- 行存 tuple 内类型混杂：int 旁边 string，难统一编码。
- 列存一列同质、相邻，模式简单：
- 重复值多 -> dictionary（字典编码）
- 连续相同 -> RLE（游程编码）
- 整数范围小 -> bit packing（位打包） / delta（差分）

**Dictionary Encoding（字典编码）**
- 列值域小（如 country 列 200 国）：

```text
原始: [China, USA, China, China, USA, ...]
Dict: {0:China, 1:USA}
编码: [0, 1, 0, 0, 1, ...]
```

- 存储：dict 表 + 整数 id 列，id 列再 bit pack。
- 解码：查 dict 得原值。

**适合**：低基数（low cardinality）string/enum 列。
**不适合**：高基数唯一值（如 uuid），dict 无收益。

---

**RLE（Run-Length Encoding，游程编码）**
- 排序或聚簇后常见连续重复：

```text
原始: [A,A,A,B,B,C,C,C,C]
RLE:  [(A,3), (B,2), (C,4)]
```

- 适合：排序键、状态列、时间序列块。
- 不适合：随机顺序高基数列。

---

**Bit Packing / Delta（位打包 / 差分编码）**
- Bit packing：值域 0–127 用 7 bit 而非 32 bit。
- Delta：存相邻差值而非绝对值，适合递增 id、timestamp。

```text
原始 timestamps: 1000, 1005, 1008, 1010
Delta:          1000, +5,   +3,   +2
```

- 解压需顺序或存 base，随机点查某 row 可能需块内 scan。

---

**压缩与 zone map（区间图 / min-max）**
- 每个 compressed block 存 min/max：

```text
Block 7: sales min=10 max=500
查询 WHERE sales > 1000 -> 跳过 Block 7
```

- 类似 lightweight（轻量）索引，无 B+ 树也能 skip I/O。
- 对 range filter 非常有效。

**初学者易错点**
- 对高基数唯一列强上 dictionary，dict 比原数据还大。
- 忘记 decompress（解压）成本：CPU 换 I/O，CPU 成为瓶颈时要调 block 大小。

---

**延迟物化（Late Materialization）**
- 早期物化（Early materialization）：先拼完整宽行，再 filter/aggregate。

```text
读 region + sales + year -> 拼 row -> filter year=2024 -> SUM sales
         ^ 可能读了不需要立即拼的列组合
```

- 延迟物化：先在各列上 filter，得到 rowid（行号）列表，最后再读需要的列拼结果。

```text
1. 读 year 列 -> filter -> rowids [3,7,9,...]
2. 读 sales 列，只取 rowids 位置 -> aggregate
3. 若 SELECT 还要 region，再按 rowids 读 region 列
```

**优点**
- 减少中间宽行 materialization（物化）。
- filter 选择性（selectivity）高时，后续只 touch 少量 rowid。

**代价**
- rowid 列表管理、两次读列、随机访问 sales[7] 可能不如顺序 scan（取决于选择性）。

**不变量**
- 各列同一 row index 必须指同一逻辑行。
- filter 后 rowid 集合在不同列上使用时必须一致。

---

**向量化执行（Vectorized Execution）**
- Volcano 模型（bustub 常见教学模型）：

```text
Next() -> 一次返回一个 tuple
```

- 向量化模型：

```text
NextBatch() -> 一次返回 N 个值的 ColumnVector（列向量）
```

- 例：对 sales 列 batch 做 SUM

```cpp
for (int i = 0; i < batch_len; i += 8)
  sum += SIMD_ADD(sales[i..i+7]);  // SIMD: 单指令多数据
```

**为何列存天然配合**
- Column chunk 已是数组，直接喂给 SIMD。
- 类型同质，无 per-row 分支解析。

**对比**
- Volcano：函数调用/虚函数开销 per tuple。
- Vectorized：摊薄循环开销，cache 友好。

**不是万能**
- 极复杂 UDF、高度不规则字符串处理，向量化收益下降。
- 短查询、极小结果集，setup batch 开销可能不划算。

---

**执行模型 vs 存储格式**
- 必须区分：
- **存储格式优化**：列存、压缩、zone map -> 减少 bytes 读入。
- **执行模型优化**：向量化、编译执行 -> 减少 per-row CPU 开销。

- 可以行存 + 向量化（部分系统），也可以列存 + 逐行（少见）。
- OLAP 常两者叠加。

---

**一条 OLAP 查询的完整路径（列存 + 延迟物化 + 向量化）**

```sql
SELECT region, SUM(sales)
FROM orders
WHERE year = 2024
GROUP BY region;
```

```text
1. 读 year 列 chunk（压缩块 decode 成 vector）
2. 向量化 filter -> 选中 mask（掩码）或 rowids
3. 读 region、sales 列，按 mask 投影
4. 向量化 hash aggregate by region
5. 输出结果 batch
```

- 全程可能 never 物化完整 50 列宽行。

---

**和行存路径对比（同一查询）**
- bustub 行存 SeqScan：

```text
对每个 tuple:
  读整行 bytes
  解析 50 列
  判断 year
  更新 aggregate
```

- I/O 与 CPU 都更贵。

---

**压缩选型决策表（直觉）**

| 列特征 | 候选编码 |
|--------|----------|
| 低基数 string | dictionary |
| 排序后重复多 | RLE |
| 小范围整数 | bit packing |
| 单调递增 | delta |
| 高基数唯一 | 轻量或无压缩 |

---

**初学者易错点**
- late materialization 的 rowid 与物理 row 顺序混淆（filter 后 index 变了）。
- SIMD 代码未处理 NULL bitmap（空值位图），结果错。
- 只压缩不记录 null，decode 语义丢。
- 以为向量化 = 多线程（其实是 batch SIMD，并行是另一层）。
