**堆表是什么**
- 堆表是最常见的表存储组织：
- 记录插入时，找到有空位的 page 就放进去。
- 不保证按主键顺序，也不保证同一列的值在磁盘上相邻。

```text
Heap Table = 多个 Page 的集合 + 插入/扫描/按 RID 定位 的策略
```

**为什么堆表是默认起点**
- 插入逻辑简单：O(1) 找到有空位的 page 即可。
- 不要求维护“按某键有序”的不变量。
- 适合 OLTP 里大量单行插入、更新、点查（配合索引）。

**堆表的代价**
- 全表扫描：要读很多 page，局部性一般。
- 范围扫描按非索引列：无法靠存储顺序获得好处。
- page 内变长更新可能产生碎片，需要后台整理。

**如果没有堆表抽象**
- 你会把“找 page 插入”散落在 executor 各处。
- 索引、扫描、删除都无法通过统一 RID 接口访问表。
- 测试无法隔离：page 布局 bug 和算子 bug 搅在一起。

---

**聚簇存储：对比着学，不必第一版就做**
- 聚簇（clustered）存储：表数据按某个键的顺序物理排列。
- 例如按主键聚簇，相近主键可能在同一 page 或相邻 page。

**聚簇的优点**
- 范围扫描局部性好：扫 `[10, 20)` 可能读更少 page。
- 某些 join 和排序可能受益。

**聚簇的代价**
- 插入/更新可能触发大量数据移动以维持顺序。
- 实现复杂，锁和并发更难。

**和 bustub 的关系**
- bustub 主线是 heap + 非聚簇索引（索引键到 RID）。
- 先把 heap 跑通，比上来就做聚簇正确得多。

**表存储与索引的接口**
- 索引和表存储之间最重要的契约：

```text
索引叶子：key -> RID
表存储：RID -> Tuple
```

- 点查完整路径：

```text
SQL: SELECT * FROM T WHERE id = 42;
  -> IndexScan on id
  -> 得到 RID{page=7, slot=3}
  -> TableHeap::GetTuple(RID)
  -> 返回 Tuple
```

**索引为什么不直接存整行**
- 行可能很大，索引页能装的条目变少，树变高。
- 更新非键列时，若索引存整行，索引页也要改；只存 RID 时索引可不动。
- 多个索引共享同一份表记录，避免重复存 row bytes。

**接口不变量**
- 只要记录未被删除，同一个 RID 必须能读回语义一致的 tuple（或明确 deleted）。
- 索引持有的 RID 必须仍指向正确记录，或删除流程同步清理索引。

**初学者易错点**
- 插入表成功但忘记插索引，点查找不到、全表扫描能找到。
- 删除只 MarkDelete 表记录，不删索引项，点查读到 deleted 或脏数据。

**表存储与 WAL 的接口**
- WAL（Write-Ahead Logging）你现在只需建立边界感，细节在恢复课程展开。
- 核心原则：`先写日志，再改 page（并最终刷盘）。`

- 表存储相关日志记录常表达：
- 在某 page 的某 slot 插入了什么
- 或删除了什么
- 或更新了什么

**为什么 WAL 常以 page 为边界**
- page 是内存与磁盘交换单位，刷盘也以 page 为粒度。
- redo 时按 page 重放，比按任意偏移重放更结构化。
- page header 里的 LSN 表示“这页上次应用到的日志位置”。

```text
事务修改 TablePage
  -> 生成 WAL record
  -> 修改内存中的 page（dirty）
  ->  eventual flush page to disk
```

**如果没有这层接口**
- 崩溃后无法判断 page 是旧版本还是 half-updated。
- 索引和表可能永久不一致。

**现在你要记住**
- `P3` 负责 page 布局正确。
- WAL 负责告诉系统“怎样在崩溃后把 page 恢复到合法状态”。
- 两者通过 LSN、redo/undo 协议配合，不是一回事。

**bustub 落点：四个核心类型**
- 下面四个名字，建议你对照源码看一遍：

**1. RID**

```cpp
// 逻辑：定位一条表记录
page_id_t page_id;
uint32_t slot_num;
```

**2. Tuple**
- 内存中的记录对象。
- 持有 raw bytes 或解析后的值。
- 需要 schema/catalog 才知道怎么解释 bytes。

**3. TablePage**
- 单个 page 的 slotted page 实现。
- 典型方法：InsertTuple、GetTuple、MarkDelete、UpdateTuple（视项目版本而定）。

**4. TableHeap**
- 表级容器。
- 管理多个 page，提供 InsertTuple、GetTuple、DeleteTuple、Iterator 扫描。

- 调用关系：

```text
Executor / Index
    -> TableHeap
         -> BufferPoolManager::FetchPage(page_id)
              -> TablePage 操作 slot
                   -> Tuple 编解码
```

**最小实现路径：我建议的切分**
- 不要一次写完整个存储引擎。按这个顺序最稳：

**阶段 0：纸上布局**
- 画 4KB page 图。
- 写清 header 字段、slot entry 格式、tuple 定长 layout。
- 列出 6 条 page 不变量。

**阶段 1：定长 + 单页**
- 只实现 `TablePage`：
  - InsertTuple
  - GetTuple
  - MarkDelete
- 不链接多页，不做 buffer pool 并发。
- 可用内存数组模拟一个 page。

**阶段 2：接 TableHeap**
- 支持多个 page，用 linked list 或 free list 找插入位置。
- 实现 Iterator 顺序扫描。

**阶段 3：接 BufferPoolManager**
- page 从“内存数组”改成通过 BPM 取页。
- 理解 FetchPage / UnpinPage / dirty 的基本语义（`P4` 会加深）。

**阶段 4：接索引（后续课程）**
- 验证 B+ 树叶子存 RID 后，点查路径完整。

- 每一阶段都要有测试，不要跳步。

**最小接口与失败条件（写代码前先写清楚）**
- 建议你在注释或设计文档里显式写出失败条件：

```cpp
// InsertTuple: 成功则写 rid，返回 true
// 失败条件：
//   - page 无足够 free space
//   - tuple 大小非法
//   - slot array 已满（若设上限）

// GetTuple: 成功则写 tuple，返回 true
// 失败条件：
//   - slot_num 越界
//   - slot 已标记删除
//   - offset/length 不合法

// MarkDelete:
// 失败条件：
//   - slot 本已删除
//   - slot_num 越界
```

- 这种“失败条件清单”是存储课最重要的工程习惯之一。
- 很多隐蔽 bug 来自“失败路径没定义，返回了随机内存”。

**推荐测试用例**
- 测试 1：空 page 连续插入 N 条定长记录，直到满。
- 测试 2：满后再 Insert，必须失败且 page 不变量仍成立。
- 测试 3：Insert -> Get -> 内容一致。
- 测试 4：MarkDelete 后再 Get，必须失败。
- 测试 5：Delete 后再 Insert，复用 free space（若你的实现支持）。
- 测试 6：故意 corrupt slot offset，GetTuple 应 fail 而不是 crash。

- 这些测试比“跑一条 SQL 看看像不像”更能定位 page 布局问题。

**调试指南：常见现象 -> 可能原因**
- `GetTuple 读到乱码`
  - schema 与 bytes layout 不一致
  - offset/length 算错
  - 把 header 区域当成 tuple 读

- `Insert 成功但 Scan 看不到`
  - 只写了 data 区，没更新 slot array
  - Iterator 跳过 deleted slot 的逻辑错了

- `RID 定位错行`
  - slot_num 与 slot array 下标混淆
  - page_id 在 TableHeap 层传错

- `更新后索引还在、表记录没了`
  - MarkDelete 了表，没维护索引

- `page 越跑越满但明明删了很多行`
  - 只 MarkDelete 不做 space reclamation，这是预期行为
  - 需要 compaction 或 insert 复用 hole（取决于实现阶段）

**并发与 latch：现在知道边界即可**
- bustub 后续会在 TablePage / BPM 上加 latch。
- 你现在至少要知道：
- page 级 latch 保护 slot array 和 data 区的一致性。
- 未 pin 的 page 可能被 evict，持有裸指针会 UAF。

- 详细并发协议在 `P4` 和并发控制课程展开。
- 但写 TablePage 时就要避免“返回指向 page 内临时区域的指针跨函数使用”。

---

**与 executor 的衔接**
- SeqScan 算子大致会：
- 向 TableHeap 要 Iterator
- 逐个 RID 读 Tuple
- 向上层 Volcano 模型返回

- IndexScan 算子大致会：
- 从索引拿 RID 列表
- 对每个 RID 调 TableHeap::GetTuple

- 所以 TableHeap 的接口稳定性，直接影响 executor 能不能写对。

**空间管理进阶（可选，非第一版）**
- free space 复用策略：
  - 线性扫描 page 找空位
  - 维护 free page list
- page 内 compaction：
  - 把有效 tuple 压实，回收 hole
- 变长 update：
  - 原地 vs 迁移

- 这些可以写在 TODO，不要阻塞第一版定长 heap。

**初学者易错点汇总**
- 在 TablePage 里直接 new/delete 磁盘文件，绕过 BufferPoolManager。
- 忘记 Unpin，导致 page 无法 evict（`P4` 典型 bug）。
- 把 LSN 更新和 page 修改顺序写反，和 WAL 协议冲突。
- 用 `sizeof(Tuple)` 当磁盘长度，忽略序列化 layout。
- 测试只覆盖插入，不覆盖删除后再读。
