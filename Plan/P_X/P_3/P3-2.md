**先给你一张 slotted page 总图**
- 工业界最常见的页内组织叫 slotted page，也叫 slot page。
- 你可以把它想成三块：

```text
+------------------------------------------+
| Page Header (元数据)                      |
+------------------------------------------+
| Tuple Data Area (从页尾往前增长)           |
|   [tuple3][tuple1][tuple2]...            |
+------------------------------------------+
| Slot Array (从页头后往前/页尾固定区增长)    |
| slot0 | slot1 | slot2 | ...              |
+------------------------------------------+
```

- 两个方向同时生长，是 slotted page 的经典设计：
- slot array 通常从 header 后面往低地址或高地址扩展（实现细节因系统而异）。
- tuple data 通常从 page 末尾往前填。
- 中间剩下的空白就是 free space。

- 为什么要这样设计？
- 插入新 tuple 时，往往只需要：
  - 在 slot array 里加一项
  - 在 free space 末尾（靠页尾侧）写入 bytes
- 不必搬动已有 slot 项的编号。

---

**Page Header：页头里通常有什么**
- 页头不是用户数据，是 page 的“自控面板”。
- 不同系统字段略有差异，但下面这些你必须认识：

```text
page_id          : 这页在文件/表中的逻辑编号
LSN              : 日志序列号，供 WAL/恢复使用（后面课程会详讲）
free_space_pointer: 指向 tuple data 区与 free space 的边界
slot_count       : 当前 slot 数量
next_page_id     : 堆表中下一页的链接（可选）
```

- 页头存在的意义：
- 让系统不用扫描整个 page，就能知道还能不能插入、有多少槽位。
- 让恢复模块知道这页上次刷盘对应哪个日志点。

**初学者易错点**
- 只改 tuple 数据，不更新 header 里的 `slot_count` 或 `free_space_pointer`。
- 把 LSN 当成“可有可无的调试字段”——后面做 WAL 时它会变成硬需求。

---

**Slot Array：RID 稳定性的关键**
- slot array 的每一项，通常记录：

```text
(offset, length, flags)
```

- `offset`：tuple 在 page 内的起始位置。
- `length`：tuple 占多少字节。
- `flags`：是否有效、是否已删除等。

- RID 的定义：

```text
RID = (page_id, slot_num)
```

- 注意：`slot_num` 是 slot array 的下标，不是物理偏移。
- 当 page 内发生这些操作时：
  - 新 tuple 插入到 free space
  - 旧 tuple 被标记删除
  - 变长 tuple 更新后写到新位置
- slot array 里对应 slot 的 `offset/length` 可以变，但 `slot_num` 不变。

- 这就是索引能存 `(key -> RID)` 而不必每次记录移动都改索引的根本原因。

**小例子**
- 假设 page 7 上：
  - slot 0 指向 offset 4020, len 80
  - slot 1 指向 offset 3940, len 60
  - slot 2 已删除，flag=invalid

```text
GetTuple(RID{7, 1})
  -> 查 slot array[1]
  -> 读 offset 3940, len 60
  -> 解析 tuple bytes
```

- 即使 slot 0 的 tuple 后来被挪到别的 offset，只要 slot array[1] 仍合法，`RID{7,1}` 就仍然有效。

---

**定长记录：最简单但仍要讲清**
- 如果 schema 里所有列都是定长，且没有 nullable 变长字段，tuple 大小固定。
- 例如：

```sql
CREATE TABLE FixedDemo (
  id INT,      -- 4 bytes
  age INT,     -- 4 bytes
  score INT    -- 4 bytes
);
```

- 定长 tuple 在 page 内的布局可以非常直接：
- 每个字段按 schema 顺序紧密排列。
- 如果有 NULL，通常用 null bitmap 标记，而不是省略字段。

**定长的优点**
- 解析快：offset 可预测。
- 插入实现简单：算 fixed size，检查 free space，写入，更新 slot。

**定长的限制**
- 真实业务大量字符串、JSON、变长文本。
- 定长 char(n) 浪费空间，varchar 才是常态。

**定长 page 的不变量**
- 每个有效 slot 的 length 应等于 schema 规定的 tuple size（或加上固定 header）。
- slot 指向的区域必须在 page 边界内。
- 有效 slot 的数据区彼此不重叠。

---

**变长记录：真正贴近工程的部分**
- 变长 tuple 才是数据库常态。
- 典型布局：

```text
+--------+--------+--------+------------------+----------+
| null   | field  | field  | varlen offsets   | payload  |
| bitmap | fixed  | lengths| or offset array  | ...      |
+--------+--------+--------+------------------+----------+
```

- 常见策略：
- 定长字段直接存值。
- 变长字段存 `(offset, length)` 或 length + bytes。
- null bitmap 指明哪些列是 NULL。

**为什么变长更难**
- 每条 tuple 长度不同，不能靠 `n * size` 定位。
- 更新时如果新版本比旧版本长，可能放不下原位置。
- 典型处理：
  - 在同一 page 找新空间写新版本
  - 更新 slot array 的 offset/length
  - 旧空间变成 hole（碎片）

- 如果 free space 不够：
  - 要么链到新 page
  - 要么做 page 内 compaction（教学第一版常先不做）

**变长插入流程（文字版状态机）**
- 1. 检查 header.free_space 是否够 `(new_tuple_size + new_slot_entry_size)`。
- 2. 在 tuple data 区分配 offset（通常从 free space 边界向页尾侧写入）。
- 3. 在 slot array 追加新 slot，记录 offset/length。
- 4. 更新 header：slot_count++，free_space_pointer 调整。

**变长读取流程**
- 1. 用 RID 找到 slot_num。
- 2. 读 slot array[slot_num] 的 offset/length/flags。
- 3. 若 invalid，返回“记录已删除”。
- 4. 否则从 offset 起读 length 字节，按 schema 解析。

---

**删除：为什么常常只 MarkDelete**
- 物理上把 tuple 清掉并把 hole 立刻合并，听起来很干净。
- 但数据库里更常见的是逻辑删除：

```cpp
bool TablePage::MarkDelete(RID rid);
```

- 做法：
- 把 slot flags 设为 deleted/invalid。
- 可选：保留 offset/length 供 undo 或 vacuum 使用。
- 不立即移动其他 tuple。

**为什么不立刻 compaction**
- compaction 要搬动 page 内 bytes，成本高。
- 并发环境下还要考虑 latch，slot 虽然编号不变，但大量移动仍然昂贵。
- 很多系统把 compaction 留给后台 vacuum 或 page 重组。

**没有 MarkDelete 会怎样**
- 若物理删除并前移所有后续数据：
  - 实现复杂
  - 锁持有时间变长
  - 某些设计下还可能影响 RID 稳定性（取决于 slot 策略）

- 所以教学型和工业型系统都常见“先标记，后整理”。

---

**RID 与索引、更新的关系**
- B+ 树叶子典型存：

```text
(key_value -> RID)
```

- 点查路径：

```text
Index Scan 找到 RID
  -> TableHeap::GetTuple(RID)
  -> 返回完整行
```

- 更新路径（简化）：
- 若新版本仍 fits 原 slot 且原地更新可行：可能原地覆盖。
- 若不行：新位置写入，更新 slot array，RID 不变。
- 索引不需要改 key->RID 映射（只要 key 没变）。

- 如果 key 变了：
- 索引要删旧插新。
- 但 RID 仍可指向表记录的新 bytes 位置。

**初学者易错点**
- 更新后改了 RID，却没改索引项——读出来就是幽灵记录或找不到记录。
- 把 slot_num 当成“当前有效记录计数”，忽略了删除后 slot 仍占编号。

---

**堆表 page 链：一张表如何跨多页**
- 单 page 放不下所有记录时，堆表用 page 链表或 page 目录扩展：

```text
Page 0 -> Page 3 -> Page 9 -> INVALID_PAGE
```

- `TableHeap` 的责任：
- 找到有空位的 page 插入。
- 扫描时遍历所有 page。
- 按 RID 定位到具体 page。

- `next_page_id` 常出现在 page header，用于串起堆文件。

---

**page 不变量清单（这一段必须背下来）**
- 下面任何一条被破坏，page 都可能整体不可信：

- `I1`：slot array 中每个有效项的 `[offset, offset+length)` 都在 page 范围内。
- `I2`：任意两个有效 tuple 的数据区间不重叠。
- `I3`：free space 区域不与任何有效 tuple 重叠。
- `I4`：`slot_count` 与 slot array 实际项数一致。
- `I5`：header 中的 free space pointer 与真实剩余空间一致。
- `I6`：对已删除 slot，GetTuple 必须明确失败或返回 deleted 语义，不能读 garbage。

- 调试 page bug 时，先问：上面哪一条 invariant 被打破了。
