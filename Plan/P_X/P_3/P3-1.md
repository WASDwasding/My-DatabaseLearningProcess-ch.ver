**先给你一张总图**
- 先把存储层想成 4 层嵌套：

```text
表 (Table)
  └─ 文件 / 堆 (File / Heap)
       └─ 页面 (Page, 通常 4KB 或 8KB)
            └─ 槽 + 元组 (Slot + Tuple)
```

- 每一层解决一个不同粒度的问题：
- 表：给用户和 catalog 看的逻辑对象。
- 文件：把一张表的数据持久化到磁盘上的容器。
- 页面：磁盘和内存之间交换的最小单位。
- 元组：页面里真正存放的一条记录。

- 注意：用户和 SQL 层几乎看不到后面三层。
- 这正是 `P1` 里说的“逻辑语义独立于物理存储”在工程上的体现。

---

**问题定义**
- 什么是 page？
- 简单说：`page 是数据库与磁盘 I/O 交互时使用的固定大小数据块。`

- 什么是 tuple？
- 简单说：`tuple 是页面里存放的一条逻辑记录，对应关系模型里的一行元组。`

- 什么是 RID？
- 简单说：`RID（Record Identifier）是定位一条表记录的稳定物理地址，通常由 (page_id, slot_num) 组成。`

- 这三个概念不是并列的术语表条目。
- 它们共同回答一个问题：
- `怎样在保持逻辑记录稳定可用的前提下，高效地和慢速磁盘打交道。`

---

**为什么不能按记录直接读写磁盘**
- 先从第一性原理来问：
- 磁盘慢在哪里？

- 一个很朴素的对比：
- CPU 和内存操作：纳秒到微秒级。
- 磁盘随机读：常常微秒到毫秒级，差几个数量级。
- 如果每次只读一条记录，系统会花大量时间在“寻道 + 旋转 + 协议开销”上，而不是真正搬运有用数据。

- 所以数据库的第一个工程结论：
- `I/O 必须批量做，不能按单条记录做。`

- 那批量做，批量单位选什么？

- 如果选“整张表一次读进来”：
- 表一大，内存根本放不下。
- 改一条记录却要重写整张表，代价 absurd。

- 如果选“每条记录单独一个文件块”：
- 记录大小不固定，磁盘块利用率差。
- 元数据管理爆炸：百万行就要百万次寻址。
- 更新、删除、碎片整理都极难做。

- 所以工业界几乎统一选择：
- `固定大小的 page 作为 I/O 和缓存的基本单位。`

- 典型大小：4KB、8KB，有的系统用 16KB。
- 这不是魔法数字，而是“足够大以摊薄 I/O 成本，又足够小以便放进内存管理”的折中。

---

**为什么 page 还不够，还需要 tuple layout**
- 有了 page，只是把 I/O 单位定下来了。
- 但 page 内部怎么放记录，仍然是大问题。

- 初学者最容易犯的错：
- 把 page 想成“一个大数组，记录从前往后塞进去就行”。

- 为什么这不行？

- 第一个问题：`删除和更新`
- 如果记录是变长的，删除中间一条后，后面所有记录要不要整体前移？
- 如果每次更新都让更长的新版本插入，旧洞怎么处理？
- 简单数组会让 page 内碎片和移动成本失控。

- 第二个问题：`如何快速定位第 N 条记录`
- 如果记录长度不固定，你不能用 `offset = n * record_size` 直接算位置。
- 你需要某种目录结构，也就是后面的 slot array。

- 第三个问题：`RID 必须稳定`
- 索引叶子节点通常存的是 `(key -> RID)`。
- 如果记录在 page 内移动，RID 也跟着变，所有指向它的索引项都要更新。
- 这在高并发系统里是灾难。

- 所以第二个工程结论：
- `page 解决 I/O 粒度；tuple layout + slot 解决 page 内组织、定位与 RID 稳定性。`

**核心术语入门**
- 下面这几个词，后面整节课都会反复出现。现在先建立直觉，细节留到 `P3-2`。

**1. File / Heap**
- 一张表的数据，在磁盘上通常对应一个或多个文件。
- 堆表（heap table）是最常见的组织方式：记录插入时找有空位的 page 放进去，不保证顺序，也不按某个键聚簇。
- 优点：插入简单。
- 代价：全表扫描时局部性可能差。

**2. Extent**
- 有些系统把多个连续 page 组成 extent，便于空间分配和预读。
- 初学阶段你可以先知道有这层，不必深挖；`bustub` 教学主线里 extent 不是第一优先级。

**3. Page**
- 固定大小的字节块。
- 在磁盘上由 `page_id` 标识。
- 读入内存后，会放进 buffer pool 的某个 frame。

**4. Page Header**
- 页头保存元数据，不是用户数据。
- 常见字段：page id、LSN、free space pointer、slot count、next page id 等。
- 页头存在的意义：让系统能在不扫描整个 page 的情况下知道“这页还能不能插、槽位状态如何”。

**5. Slot / Slot Array**
- slot 是 page 内的逻辑槽位编号。
- slot array 是页尾（或页头附近）的一张小表，记录每个 slot 对应 tuple 在 page 内的偏移和长度。
- 关键性质：`RID = (page_id, slot_num)`，slot_num 不变，即使 tuple 在 page 内物理位置变了，RID 仍可稳定。

**6. Tuple**
- 一条记录的物理表示。
- 包含各列的值，可能有 null bitmap、变长字段长度前缀等。
- 逻辑上对应 `P1` 里的一个元组。

**7. RID**
- Record Identifier。
- 在 `bustub` 里大致是：

```cpp
struct RID {
  page_id_t page_id;
  uint32_t slot_num;
};
```

- 索引、某些执行算子、调试工具都通过 RID 回到表记录。

---

**不变量：现在就要建立的 3 条**
- 即使还没画具体布局，你也应该先记住这些“不能破”的规则：

- `不变量 1：page 是 I/O 和 WAL/redo 的常见边界单位`
- 后面你会学到，很多恢复逻辑以 page 为粒度重放。
- 如果 page 内布局不合法，恢复后整个 page 都不可信。

- `不变量 2：slot 目录和 tuple 数据区不能互相覆盖`
- slot array 记录的 offset/length 必须指向 page 内合法且不重叠的区域。
- 这是 page 内最容易写坏的边界。

- `不变量 3：对外暴露的 RID 在记录未被删除/迁移出页时应保持稳定`
- 索引依赖这一点。
- 如果破坏它，不是“性能差一点”，而是索引和表数据可能对不上。

---

**没有 page/tuple 抽象会怎样**
- 假设你写一个“最小数据库”，直接让 SQL 层读文件偏移：

```text
Student 表：record #17 在文件 offset 8832
```

- 会发生什么？

- 换页大小、换压缩、换聚簇策略，上层全崩。
- 加索引后，每次记录移动都要全局更新索引项。
- buffer pool 无法工作：它缓存的是 page，不是任意偏移。
- WAL 难以表达：你很难对“半条记录”做原子 redo。

- 所以 page/tuple/RID 不是考试名词。
- 它们是后续所有存储模块能分层协作的前提。

---

**和 bustub 的第一次对齐**
- 在 `bustub` 里，这节课最直接的落点是：
- `TableHeap`：表级接口，负责跨 page 插入、扫描、更新、删除。
- `TablePage`：单页布局与 slot 管理。
- `Tuple`：记录的内存表示，知道 schema 才能解析字节。
- `RID`：定位记录。

- 你可以先建立这条调用直觉：

```text
Executor 需要读一条记录
  -> TableHeap::GetTuple(RID)
       -> BufferPoolManager 取 page
            -> TablePage 按 slot 找 offset
                 -> 解析 Tuple
```

- 现在还不需要写代码。
- 但你要看见：`P3` 不是孤立的一节存储课，而是 executor 最终落地的物理层。

**初学者易错点**
- `易错点 1：把 page 和 frame 混为一谈`
- page 是磁盘上的逻辑页；frame 是内存里的槽位。
- 这个区分在 `P4` 会展开，但现在先记住：同名不同物。

- `易错点 2：以为 RID 是“记录在文件里的字节偏移”`
- 在 slot page 设计里，RID 通常是 `(page_id, slot_num)`。
- 物理偏移藏在 slot array 里，可以变；slot_num 不变。

- `易错点 3：忽略页头元数据`
- 写 InsertTuple 时如果只改数据区、不更新 free space pointer 和 slot count，page 很快内部状态全乱。

- `易错点 4：把堆表当成“数组表”`
- 堆表不保证按主键顺序存放，也不保证插入顺序等于逻辑顺序。

**最小实现视角（先建立目标，不急着写）**
- 如果只做教学型最小表存储，第一版目标可以很克制：
- 定长记录
- 单页 slot page
- 支持 Insert / Get / MarkDelete
- 先不做 compaction

- 你最终会在纸上或代码里实现类似接口：

```cpp
bool TablePage::InsertTuple(const Tuple &tuple, RID *rid);
bool TablePage::GetTuple(RID rid, Tuple *tuple);
bool TablePage::MarkDelete(RID rid);
```

- `P3-3` 会带你把这条最小路径走完整。
- 现在只要知道：这些接口的存在，是为了把“关系模型里的一行”变成“磁盘上可定位、可修改的对象”。
