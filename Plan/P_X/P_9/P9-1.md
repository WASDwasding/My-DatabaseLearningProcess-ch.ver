**今天这次的目标**
- 我们现在正式开始 `P9`，主题是：`向量索引 + 倒排索引 + 跳表 + 布隆过滤器`。
- 这一段你要建立的是**选型思维**，而不是四种结构各背一段定义。
- 你学完 `P9-1` 后，应该能回答 3 个问题：
- 为什么不存在一种索引通吃所有查询。
- 精确索引和近似索引在正确性目标上差在哪里。
- 这些结构和 `P7` hash、`P8` B+Tree 在数据库系统里各居什么位置。

**先把 `P8` 和 `P9` 接起来**
- `P7`、`P8` 教的是关系型数据库的**主力精确索引**：
- hash：等值
- B+Tree：有序、范围

- 真实系统里还有很多查询类型：

```sql
-- 全文
SELECT * FROM docs WHERE content MATCH 'database index';

-- 成员测试（可能）
SELECT * FROM huge_table WHERE id IN (...);

-- 向量相似度
SELECT * FROM images ORDER BY embedding <-> query_vec LIMIT 10;
```

- 这些查询的 access pattern 和 B+Tree 假设（key 全序、精确匹配）不一致。
- `P9` 就是让你看到：**内核工程师先读 workload，再选结构**。

**先给你一张总图**
- 把索引结构按“回答什么问题”分类：

```text
                    查询需求
                       |
     +--------+--------+--------+--------+
     |        |        |        |        |
  精确等值  精确有序  全文检索  成员测试  近似近邻
     |        |        |        |        |
   Hash    B+Tree    倒排     Bloom     向量 ANN
   (P7)     (P8)    (P9)      (P9)       (P9)
```

- 还有一类**内存有序结构**（跳表）常出现在 LSM、MemTable 等写优化层——也在 P9 视野内。

- bustub 主线不实现倒排/向量索引，但理解 P9 后你会更清楚：
- `B+Tree 是“有序精确查找”的折中优选，不是普适解。`

---

**问题定义**
- 什么是“扩展索引结构”？
- 简单说：
- `在 B+Tree/hash 之外，为特定 workload 设计的辅助或专用索引与过滤器。`

- 两类划分你要始终带着：

**1. 精确 vs 近似**
- 精确：结果必须正确，无漏报无错报（在结构能力范围内）。
- 近似：允许牺牲一点正确性换延迟/空间（如 ANN 召回率、Bloom 假阳性）。

**2. 主索引 vs 辅助结构**
- 主索引：直接回答查询（B+Tree、倒排 posting list）。
- 辅助：减少无效 I/O，不单独完成查询（Bloom 在 LSM 前过滤 SSTable）。

---

**为什么不存在万能索引**
- 第一性原理：索引是在**空间、更新代价、查询延迟、正确性**之间做 trade-off。

- B+Tree 假设：
- key 可比较全序
- 查询是精确范围或点查
- 磁盘 page 随机读可接受

- 全文检索假设：
- 文档由 term 组成
- 查询是 term 布尔组合
- 需要 term -> doc list，而不是 doc id 全序

- 向量检索假设：
- 高维空间无 meaningful 全序
- 查询是“最近邻”，精确扫描 O(N) 不可接受
- 接受近似：召回率 95% 换 10x 加速

- 若强行用 B+Tree 做向量 ANN：
- 没有自然 key 顺序，范围查询无意义。

- 若强行用倒排做 primary key 点查：
- 大材小用，更新 posting 代价高。

---

**workload 驱动选型框架**
- 遇到新查询，按这 5 步想：

```text
1. 查询类型：点查 / 范围 / 全文 / 相似度 / 存在性？
2. 正确性：必须精确还是可以近似？
3. 更新频率：读多写少还是写多读少？
4. 数据规模：内存放得下还是必须磁盘？
5. 访问局部性：顺序扫还是随机跳？
```

- 小例子：

```text
主键 OLTP 点查        -> B+Tree 聚簇索引
日志时间范围          -> B+Tree 或 时间分区 + B+Tree
电商搜索 "手机 壳"    -> 倒排 + 评分
图像 "找相似"         -> 向量 ANN (HNSW/IVF)
LSM 读 path 过滤      -> Bloom 减少 SSTable 打开
内存 MemTable         -> 跳表（有序 + 并发友好）
```

---

**倒排索引（术语入门）**
- 是什么：
- `term -> posting list（出现该 term 的 doc id 及可选位置/频率）`

- 为什么：
- 全文查询先拆 term，再求 posting 交集/并集。

- 小例子：

```text
Doc1: "database index"
Doc2: "index card"

倒排：
  "database" -> [1]
  "index"    -> [1, 2]
  "card"     -> [2]

查询 "index" -> doc 1,2
查询 "database AND index" -> doc 1
```

- 没有倒排：
- 只能逐 doc 扫描 content，O(docs)。

- 不变量：
- 每个 term 的 posting 有序（便于 merge 交集）。
- doc 更新时 posting 增删一致。

- 易错点：
- 分词、大小写、停用词会改变 term 集合——索引与查询必须使用同一 pipeline。

---

**布隆过滤器（术语入门）**
- 是什么：
- `位数组 + 多个 hash 函数，用于“可能存在 / 一定不存在”的成员测试。`

- 为什么：
- 空间极小，查询 O(k) 位检查，用来**跳过**不可能的分支。

- 特性（必须背准）：
- **无漏报**（配置正确时）：说“不存在”则一定不存在。
- **有误报**：说“可能存在”时可能实际不存在。

- 小例子：

```text
Bloom 说 "key 不在 SSTable-3" -> 肯定不在，不用读盘
Bloom 说 "key 可能在"         -> 打开 SSTable 确认
```

- 没有 Bloom：
- LSM 读要查多层 SSTable，I/O 多。

- 不变量：
- 只 insert，不 delete（标准 Bloom；Counting Bloom 可删但复杂）。
- 假阳性率随插入增多而上升（固定位数组时）。

---

**跳表（术语入门）**
- 是什么：
- `多层有序链表，上层是下层子集，查找时从高层“跳”向低层。`

- 为什么：
- 内存中有序 map 的替代：实现比平衡树简单，并发友好变体多（Redis ZSET、LevelDB MemTable 历史）。

- 小例子（整数键）：

```text
Level 2:  1 ------------------------> 7
Level 1:  1 ----> 4 ----> 7 ----> 9
Level 0:  1 -> 3 -> 4 -> 7 -> 9 -> 12  (全部 key)
```

- 查找 7：从 L2 跳到 7，期望 O(log N)。

- 没有跳表时 MemTable 可选：
- 红黑树、B+Tree 内存版——都可以，跳表是工程折中。

- 易错点：
- 概率层高随机；实现要固定 random level 分布（如 p=0.25）。

---

**向量 ANN（术语入门）**
- 是什么：
- `Approximate Nearest Neighbor，在高维空间找与 query 向量最近的 top-K。`

- 为什么：
- 精确 kNN 要算 N 次距离，亿级向量不可行。

- 常见结构：
- IVF（聚类 + 倒排 list）
- HNSW（图导航）
- LSH（局部敏感哈希）

- 正确性目标：
- **召回率 recall@K**：真 top-K 有多少出现在结果里。
- 不是“零误报”，而是“尽量接近真最近邻”。

- 小例子：

```text
query q，真最近邻是 {a,b,c}
ANN 返回 {a,x,c} -> recall@3 = 2/3
```

- 和 B+Tree 对比：
- B+Tree：精确；向量 ANN：故意近似。

**易混点：向量 ANN 到底在查什么（先钉死）**

**一句话**
- `B+Tree/hash 查的是标量 key 是否等于/落在某范围；ANN 查的是高维向量与 query 有多像（top-K 近邻）。`

**为什么不用 B+Tree**
- B+Tree 需要 key 能排成**一条线**（全序）。
- 向量是几百维的点，「按某一维排序」≠「按相似度排序」；没有简单的一维 key 能代表几何邻近性。
- 暴力做法：query 与 **每一个** 向量算距离 → N 很大时不可行。
- ANN 做法：**故意少算一部分**，换速度；用 **recall@K** 验收，不是「必须精确 top-K」。

**IVF vs HNSW（只记分工，细节见 P9-2）**

| | IVF | HNSW |
|--|-----|------|
| 像什么 | 图书馆分区 / 聚类 + posting list | 多层地图 / 图上贪心走路 |
| 怎么快 | 只扫离 q 最近的几个「区」 | 顶层大跳、底层细搜 |
| 为什么会漏 | 真近邻在「没被选中的区」 | 贪心没走到真近邻所在边 |

**类比**
- IVF：猜 query 在「宠物区、动物区」，只在这两区里翻——快，但猫图若被错分到别的区会漏。
- HNSW：在高速路看路牌大跳，到了附近再步行比——走路姿势像跳表，但走的是**相似度图**，不是有序链表。

**易混点：跳表 vs HNSW 像不像？**

**像的地方（所以常被一起提）**
- 都有**多层**：上层少、跳得远；下层全、搜得细。
- 查找都像：从最高层出发 → 尽量往目标方向走 → 走不动就**降一层** → 重复。

```text
跳表:  L2:  1 ---------> 7 ---------> 19
       L0:  1-3-4-5-7-8-10-19   （一维有序链表）

HNSW:  顶层稀疏长跳 → 底层稠密细搜   （高维相似度图）
```

**不像的地方（别混）**

| | 跳表 | HNSW |
|--|------|------|
| 空间 | **一维**，key 能全序比较 | **高维**，靠距离「像不像」 |
| 层里连什么 | 有序链表上的前驱/后继 | 与几何上近的点连**边**（图） |
| 查什么 | `key=7`、范围（**精确**） | 与 q 最相似的 top-K（**近似**） |
| 层怎么来 | 插入时**随机**定层高 | 建图时按规则分层 |
| 为何精确/近似 | Level 0 **不漏** key，全序导航 | **贪心**走图，不扫全库，不保证全局真 top-K |

**一句话**
- `跳表 = 一维有序链表上的 express lane，精确；HNSW = 高维图上的多层贪心导航，近似（看 recall@K）。`
- HNSW 常被说成「图上的跳表式**导航**」——**走路径的方式像**，不是同一种数据结构。

**精确索引 vs 近似索引**
- 表格直觉：

```text
结构          精确性        典型误报/漏报
------------------------------------------
B+Tree        精确          无（在键存在性上）
Hash          精确          无
倒排          精确 term 匹配  分词语义层面另有 NLP 问题
Bloom         辅助          假阳性有，漏报无
向量 ANN      近似          可能漏掉真近邻（低 recall）
```

- 设计系统时必须先问：
- `用户能接受什么性质的错误？`

---

**常见错误理解**
- `误区 1：Bloom 可以代替 hash index`
  - 不对，Bloom 有误报，不能单独答“值是什么”。

- `误区 2：倒排索引适合主键点查`
  - 不对，维护成本高，点查用 B+Tree。

- `误区 3：ANN 结果和精确 kNN 一样`
  - 不对，要显式谈 recall/latency trade-off。

- `误区 4：跳表是磁盘索引`
  - 通常内存结构；磁盘有序仍是 B+Tree。

- `误区 5：跳表和 HNSW 是一回事`
  - 不对。多层查找**姿势像**，但跳表是一维有序链表的**精确**查找；HNSW 是高维图上的**贪心近似**近邻，不保证找到全局真 top-K。

- `误区 6：ANN 可以用 B+Tree 按某一维排序代替`
  - 不对。一维排序丢失高维几何邻近性；ANN 要的是距离，不是标量范围 scan。

---

**今天你必须真正吃透的 4 句话**
- `没有万能索引；先 workload，后结构。`
- `B+Tree/hash 是关系型精确索引主力；P9 是专用与辅助结构。`
- `Bloom 无漏报有误报；ANN 追 recall 不追零误差。`
- `倒排服务 term 检索；向量索引服务相似度，不是范围 scan。`
- `跳表精确（一维全序）；HNSW 近似（高维贪心）——多层像，本质不同。`

- 查找 7：从 L2 跳到 7，期望 O(log N)。

- 没有跳表时 MemTable 可选：
- 红黑树、B+Tree 内存版——都可以，跳表是工程折中。

- 易错点：
- 概率层高随机；实现要固定 random level 分布（如 p=0.25）。

---

**向量 ANN（术语入门）**
- 是什么：
- `Approximate Nearest Neighbor，在高维空间找与 query 向量最近的 top-K。`

- 为什么：
- 精确 kNN 要算 N 次距离，亿级向量不可行。

- 常见结构：
- IVF（聚类 + 倒排 list）
- HNSW（图导航）
- LSH（局部敏感哈希）

- 正确性目标：
- **召回率 recall@K**：真 top-K 有多少出现在结果里。
- 不是“零误报”，而是“尽量接近真最近邻”。

- 小例子：

```text
query q，真最近邻是 {a,b,c}
ANN 返回 {a,x,c} -> recall@3 = 2/3
```

- 和 B+Tree 对比：
- B+Tree：精确；向量 ANN：故意近似。

**精确索引 vs 近似索引**
- 表格直觉：

```text
结构          精确性        典型误报/漏报
------------------------------------------
B+Tree        精确          无（在键存在性上）
Hash          精确          无
倒排          精确 term 匹配  分词语义层面另有 NLP 问题
Bloom         辅助          假阳性有，漏报无
向量 ANN      近似          可能漏掉真近邻（低 recall）
```

- 设计系统时必须先问：
- `用户能接受什么性质的错误？`

---

**常见错误理解**
- `误区 1：Bloom 可以代替 hash index`
  - 不对，Bloom 有误报，不能单独答“值是什么”。

- `误区 2：倒排索引适合主键点查`
  - 不对，维护成本高，点查用 B+Tree。

- `误区 3：ANN 结果和精确 kNN 一样`
  - 不对，要显式谈 recall/latency trade-off。

- `误区 4：跳表是磁盘索引`
  - 通常内存结构；磁盘有序仍是 B+Tree。

---

**今天你必须真正吃透的 4 句话**
- `没有万能索引；先 workload，后结构。`
- `B+Tree/hash 是关系型精确索引主力；P9 是专用与辅助结构。`
- `Bloom 无漏报有误报；ANN 追 recall 不追零误差。`
- `倒排服务 term 检索；向量索引服务相似度，不是范围 scan。`
