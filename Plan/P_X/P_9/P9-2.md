**一、倒排索引深讲**

**是什么**
- `词典 term -> posting list；list 中每项记录 doc_id（+ tf、位置等）。`

**为什么**
- 查询 `t1 AND t2` = posting(t1) ∩ posting(t2)。
- 查询 `t1 OR t2` = posting(t1) ∪ posting(t2)。
- posting 有序时，交集可双指针线性 merge，类似 merge join。

**没有会怎样**
- 全文扫描每篇 doc，CPU 和 I/O 爆炸。

**核心机制：构建**
- 文档入库 -> 分词 -> 对每个 term：

```cpp
inverted_index[term].push_back({doc_id, tf, positions});
```

- 批量构建后可压缩 posting（差分编码 doc_id、变长整数）。

**核心机制：查询**
- 单 term：直接取 list。
- 多 term AND：

```text
list1: 1, 5, 9, 20
list2: 5, 7, 9, 11
交集:  5, 9     (双指针)
```

**不变量**
- 同一 term 的 posting 中 doc_id 递增（或按约定有序）。
- 词典中 term 唯一映射到 list。

**易错点**
- 未 normalize：`Index` vs `index` 变成两个 term。
- 更新 doc：要从旧 term 的 posting 删除 doc_id，向新 term 插入——和 B+Tree 更新一样麻烦。

**小 SQL 类比**

```sql
-- 逻辑上不是 SQL，而是 IR 查询
term:database AND term:index
```

**二、布隆过滤器深讲**

**是什么**
- 位数组 `m bits`，`k` 个独立 hash 函数 `h1..hk`。
- Insert(x)：对 i=1..k，置位 `bits[hi(x)] = 1`。
- Query(x)：若所有 `bits[hi(x)]` 为 1，则“可能存在”；否则“一定不存在”。

**为什么**
- 空间远小于存完整 key 集合；常嵌入 LSM SSTable 元数据。

**没有会怎样**
- 读放大：每个 SSTable 都要打开查一遍。

**假阳性率直觉**
- 位数组越满，误报越高。
- 经典近似公式（独立 hash 理想情况）：

```text
p ≈ (1 - e^(-kn/m))^k

m: 位数
n: 已插入元素数
k: hash 函数个数
```

- 给定 n 和目标 p，可反推 m 和最优 k ≈ (m/n) ln 2。

**小例子**

```cpp
class BloomFilter {
  std::vector<bool> bits;
  int k;
  void Insert(uint64_t key) {
    for (int i = 0; i < k; i++)
      bits[hash(key, i) % bits.size()] = true;
  }
  bool MaybeContains(uint64_t key) {
    for (int i = 0; i < k; i++)
      if (!bits[hash(key, i) % bits.size()]) return false;
    return true;  // 可能误报
  }
};
```

**不变量**
- 标准 Bloom 不支持 delete（删一位可能误伤其他 key 的位）。
- 查询 false 时 key 一定未 insert 过（无漏报）。

**易错点**
- hash 不够独立 -> 假阳性高于理论。
- 插入超过设计 n 仍不换更大 m -> 误报失控。
- 把 MaybeContains=true 当成“一定存在”——必须二次确认。

**三、跳表深讲**

**是什么**
- 底层 Level 0 包含全部 key 有序链表。
- Level i+1 是 Level i 节点的随机子集（通常以概率 p 晋升）。
- 头节点维护各层 head 指针。

**为什么**
- 期望 O(log N) 查找/插入，实现比红黑树直观。
- 并发跳表可通过细粒度锁或 CAS 做 lock-free 变体。

**查找路径**
- 从最高层 head 开始，向右直到 next.key >= target，再向下层。
- 类似在“ express lane ”上跳跃。

```text
Find(7):
  L2: 1 -> (跳) -> 7  停，7==target
```

**插入**
- 先 Find 定位 Level 0 前驱。
- random 生成层高 h（几何分布）。
- 在 0..h 层插入节点并 splice 指针。

```cpp
int RandomLevel() {
  int lvl = 0;
  while (rand() % 4 == 0 && lvl < MAX_LEVEL) lvl++;
  return lvl;
}
```

**没有会怎样**
- MemTable 若用无序 vector，flush 前排序 O(N log N)；或每次插入 O(N)。

**不变量**
- Level 0 包含所有 key，严格递增。
- 高层节点在 Level 0 必有对应节点；高层 next 指向同层下一 key。

**易错点**
- 插入时某层忘了更新指针 -> 链表断。
- MAX_LEVEL 太小，高 N 时退化成链表。

**易混点：跳表为什么精确（一维全序）**
- 数据在 **一维全序** 上：key 能比较大小，Level 0 是 **包含全部 key 的严格递增链表**。
- 上层只是 Level 0 子集的「快车道」，**不会漏节点**。
- 查找规则固定：`next.key < target` 就右移，否则下降 → 一定能找到或确定不存在。
- 因此是 **精确** 有序查找（期望 O(log N)），不是近似结构。
- 典型用途：MemTable 等 **内存写路径** 的有序 map，不是磁盘主索引。

**四、向量 ANN 深讲**

**是什么**
- 数据：向量 v ∈ R^d。
- 查询：找与 q 距离最小的 top-K（L2、内积、余弦）。

**为什么不用 B+Tree**
- 高维空间“最近邻”无简单全序 key；一维排序丢失几何邻近性。
- 精确 kNN：query 与 **每个** 向量算距离，O(N)——亿级不可行。
- ANN：**缩小候选集**，只在候选里算距离 → 快，但可能漏真近邻。

**2D 手推直觉（把高维想成平面）**
- 平面上有很多点；query 是 q。
- **暴力**：和每个点算距离 → 精确，慢。
- **IVF**：先画几个「区中心」，每个点归最近区；q 只去最近的 1～2 个区里比距离 → 若真近邻落在「没选中的区」就**漏**。
- **HNSW**：点之间连边，顶层沿边 **贪心** 走向离 q 更近的邻居，再下沉细搜 → 若贪心走进「局部最优」、真近邻在图另一侧就**漏**。

**IVF 直觉（Inverted File Index）**
- 训练 k 个聚类中心 {c1..ck}。
- 每个向量归到最近中心，形成 posting list。
- 查询：找与 q 最近的几个中心 -> 只在这些 list 里算距离。

```text
centroid_1 -> [v3, v9, ...]
centroid_2 -> [v1, v7, ...]
query q -> 最近 centroid_1,2 -> 只扫描这两堆
```

- 没有 IVF：暴力 N 次距离。
- 易错点：聚类质量差 -> recall 低。

**HNSW 直觉（Hierarchical NSW）**
- 多层图，上层稀疏长跳，下层稠密短跳。
- 查询从顶层 greedy 走向 q，再下沉细搜。

- 没有 HNSW：要么暴力要么 IVF 单级。
- 不变量：图连通性、层级 entry point 维护。

**正确性：recall@K**
- 评估 ANN 不用“是否精确 top-K”，而用 recall：

```text
recall@K = |返回的K ∩ 真topK| / K
```

**易错点**
- 把 ANN 当精确索引向用户承诺。
- 维数灾难：d 很大时任何结构都变难，要配合量化 PQ。

**易混点：跳表 vs HNSW（机制层对照）**

**查找过程对比**

```text
跳表 Find(7):                    HNSW Find(q):
  L2: 1 --------> 7  命中          顶层: 沿边走向离 q 更近的点
  规则: next.key < 7 右移           规则: 选邻居中距离 q 最小的
        否则下降                   走不动 → 降层 → 底层细搜
  结果: 精确命中或 not found        结果: 近似 top-K（recall@K）
```

**为何跳表精确、HNSW 不保证全局最优**

| | 跳表 | HNSW |
|--|------|------|
| 结构 | 一维 **有序链表** + 多层指针 | 高维 **相似度图** + 多层边 |
| 导航依据 | 全序比较 `key < target` | 距离 metric 上的 **贪心** |
| 候选集 | Level 0 必含全部 key | 只沿边访问一部分点 |
| 正确性 | **精确** membership / 有序 | **近似**；真 top-K 可能漏 |
| 验收 | 找到即对 | **recall@K**，不是零误差 |

**最容易说错的两句**
- 错：`HNSW 多层像跳表，所以也是精确 O(log N) 查找。`  
  对：多层**导航姿势**像；HNSW 解决的是 **近似近邻**，贪心 + 图结构不保证全局真 top-K。
- 错：`跳表和 HNSW 可以互相替换。`  
  对：跳表管 **一维 key 有序**（MemTable）；HNSW 管 **向量相似度**——问题定义不同。

**口诀**
- `跳表：一维、链表、精确；HNSW：高维、图、贪心、近似。`

**五种结构横向对比**

```text
结构      查询类型        存储      更新      精确性
------------------------------------------------------
Hash      等值           磁盘/内存  中        精确
B+Tree    有序范围       磁盘      中        精确
倒排      term 布尔      磁盘      难        精确(term级)
Bloom     存在性过滤     内存/磁盘  只增      辅助(误报)
跳表      有序 key       内存      易        精确
ANN       相似度 top-K   内存/磁盘  中-难     近似
```

**组合使用（工业直觉）**
- Elasticsearch：倒排 + 压缩 posting + 可选 ANN 插件。
- RocksDB/LevelDB：MemTable 跳表 + SSTable + Bloom。
- Pinecone/Milvus：向量 ANN + 元数据 B+Tree 过滤。

- 关键思想：
- `主结构回答查询主体，辅助结构减少无效工作。`

**今天你必须真正吃透的 5 句话**
- `倒排 = term -> posting list；AND 是 sorted list 交集。`
- `Bloom：false 一定不存在，true 要二次确认；假阳性随负载升。`
- `跳表：随机层高 + 多层指针，期望 O(log N)；一维全序故精确。`
- `ANN：IVF 用聚类缩小候选；HNSW 用图 greedy 导航；二者都可能漏真近邻。`
- `跳表 vs HNSW：多层查找像，但链表精确、图贪心近似——别混为一谈。`
- `扩展结构常和 B+Tree 组合，而不是替换一切。`
