**今天这次的目标**
- 我们现在正式开始 `P12`，主题是：`哈希连接、排序合并连接、嵌套循环连接`。
- 这一段先不急着写 hash table，而是先把总问题打透：
- `逻辑上“两表按条件拼行”只有一句话，物理上为什么有好几种算法、且没有 universal winner？`
- 你学完这一段后，应该能回答 3 个问题：
- 内连接、外连接、半连接、反连接在结果语义上差在哪里。
- 为什么 join 是优化器与执行器的性能与 bug 热点。
- join 算法选择 与 join order 选择 是不是同一回事。

**先把 `P11` 和 `P12` 接起来**
- `P11` 的 hash table 你在 agg 里见过：key → state。
- Join 的 hash 路径里也会出现 hash table，但 value 通常是`build 侧匹配行的集合或指针`，语义完全不同。
- 典型查询：

```sql
SELECT E.name, D.dept_name
FROM Employee E
JOIN Department D ON E.dept_id = D.id
WHERE E.salary > 50000;
```

- 逻辑：对满足连接谓词的行对 `(e, d)` 做组合输出。
- 物理：可选 NLJ、Index NLJ、Hash Join、Sort-Merge Join——代价差几个数量级。

- 如果 `P12` 没学稳，你会：
- 解释不清为什么大表 join 大表 NLJ 不可接受。
- 写外连接时漏 NULL padding。
- 把 “join order” 和 “hash vs merge” 混为一谈。

---

**先给你一张总图**
- 一次两表 join 的执行树骨架：

```text
        Join (E.dept_id = D.id)
       /                    \
 SeqScan(E)            SeqScan(D)
   + Filter               (或 IndexScan)
```

- 优化器还要决定：
- 谁做 outer/build、谁做 inner/probe（order）。
- 用哪种 join 算法（algorithm）。
- 连接谓词能否用 hash（等值）还是只能 NLJ（任意谓词）。

```text
         [Join Order]          [Join Algorithm]
              │                        │
    先 E 还是先 D？          NLJ / Hash / Merge？
    三表以上排列顺序？        能否用 index？
```

- 两个维度独立又耦合：小 build 侧 + hash 往往更优；已排序输入 + merge 可能更优。

---

**问题定义：连接在算什么**
- 什么是 join（连接）？
- 简单说：`Join 根据连接条件，从两个（或多个）输入关系中，组合出满足条件的行对（或行），形成更宽的结果关系。`

- 最常用的是`等值连接（equi-join）`：

```sql
ON E.dept_id = D.id
```

- 也有非等值：

```sql
ON E.salary > D.min_salary AND E.salary < D.max_salary
```

- 非等值往往限制你能用的物理算法（hash 通常不行，NLJ 或 special merge 结构）。

---

**连接类型：语义必须先分清**
- 这些不是“实现细节”，而是`结果集定义`不同，写错 executor 会 silent wrong。

**1. 内连接（Inner Join）**
- 只输出两边谓词为真的匹配行。
- 无匹配 → 该行不出现在结果中。

**2. 左外连接（Left Outer Join）**
- 左表每一行至少出现一次。
- 右表无匹配 → 右表列填 NULL（padding）。

**3. 右外连接（Right Outer Join）**
- 对称于左外；实践中常改写成 left outer 交换表顺序。

**4. 全外连接（Full Outer Join）**
- 两边 unmatched 行都要保留，对侧 NULL padding。

**5. 半连接（Semi Join）**
- 只关心“左表行是否存在右表匹配”，输出通常只有左表列（或 key），且`每个左行最多输出一次`。
- 典型：`WHERE EXISTS (SELECT 1 FROM D WHERE ...)`

**6. 反连接（Anti Join）**
- 输出左表中`没有`右表匹配的行。
- 典型：`WHERE NOT EXISTS (...)` 或 `NOT IN`（注意 NULL 陷阱）。

- 例子：
- 左表 E：`(1, Sales), (2, IT)`
- 右表 D：`(Sales, NYC)` only
- Inner: `(1, Sales, Sales, NYC)` only
- Left outer: 再加 `(2, IT, NULL, NULL)`
- Semi on E: `(1, Sales)` only（不因多个右匹配重复左行，除非语义要求）
- Anti on E: `(2, IT)`

---

**为什么 join 如此昂贵**
- 从第一性原理看，join 是`组合爆炸`风险最高的算子之一。

- 若无有效谓词（笛卡尔积）：
- |E| = n, |D| = m → 输出最多 n×m 行。
- n = m = 10^5 → 10^10 行，不可接受。

- 即使有等值谓词：
- 若 dept_id 无索引、无 hash，NLJ 要 O(n×m) 次比较。
- I/O：两表扫描次数与算法、order、缓存相关。

- 所以工业界 spent 大量精力在：
- join order enumeration（顺序）
- join algorithm selection（算法）
- statistics（基数估计、NDV、skew）

---

**为什么有多种 join 算法**
- 一句话：`没有单一算法在所有数据规模、排序状态、谓词类型、内存大小下都最优。`

| 算法 | 核心思想 | 典型前提 | 主要代价 |
|------|----------|----------|----------|
| Nested Loop Join (NLJ) | 外层每一行扫内层 | 通用，任意谓词 | O(n×m) 比较 |
| Index NLJ | 外层行用索引查内层 | 内层连接键有索引 | O(n × log m) 或 O(n × k) |
| Hash Join | build 小表 hash，probe 大表 | 等值连接，build 能进内存或 spill | O(n+m) 期望，内存敏感 |
| Sort-Merge Join | 两边按 join key 排序后 merge | 等值/范围，输入可排序或已有序 | sort 成本 + 线性 merge |

- 优化器的工作：在 logical join tree 上选 physical plan。

---

**join 算法选择 vs join order**
- 初学者极易混淆，必须拆开：

- **Join order**：多表时谁先和谁 join，例如 `(E JOIN D) JOIN P` vs `E JOIN (D JOIN P)`。
  - 影响中间结果大小（row count width）。
  - 搜索空间阶乘级，靠动态规划 + 启发式。

- **Join algorithm**：对`某一对`输入，用 NLJ 还是 hash。
  - 影响这一对的操作代价，不改变逻辑语义（在等价前提下）。

- 例子：
- 三表 E, D, P。
- Order 1：`((E ⋈ D) ⋈ P)` 中间可能很大。
- Order 2：`(E ⋈ (D ⋈ P))` 若 D⋈P 很小，可能更优。
- 对 `E ⋈ D` 这一步，仍要再选 hash 或 NLJ。

---

**输出 schema 与 NULL padding（外连接的坑）**
- Join 输出列 = 左列 + 右列（或 planner 投影后子集）。
- 外连接 unmatched 侧列必须为 NULL typed correctly。

- 易错：
- 用 inner join executor 逻辑跑 outer join → 丢行。
- NULL padding 时未带正确 schema/null bitmap → 下游 agg 把 NULL 当 0。

- bustub 里 join executor 通常要拼接两个 child tuple 的 bytes / values，按 plan 的 output schema 排列。

**和 bustub 的接点（地图）**
- 常见 executors：
- `NestedLoopJoinExecutor`
- `HashJoinExecutor`（build/probe）
- `SortMergeJoinExecutor`（若课程包含）

- binder/planner：
- 解析 `ON` 条件是否为 equi-join。
- 决定能否生成 hash join plan node。

- 读代码时问：
- 左 child、右 child 在 plan 里如何标记 build/probe？
- outer join 标志位在哪？
- 匹配多条时如何输出（inner 会乘积；semi 可能 dedup）？

---

**关键不变量（P12 整课）**
- `J1`：Inner join 输出每一行必须满足 join predicate。
- `J2`：Outer join 左表每行至少出现一次；无匹配时右列为 NULL。
- `J3`：Semi join：左行若有多右匹配，输出一次（标准 EXISTS 语义）。
- `J4`：Anti join：仅无匹配的左行输出。
- `J5`：算法切换（NLJ/hash/merge）不得改变逻辑结果，只改代价。

---

**常见错误理解**
- “join 就是两个 for 循环”——只是 NLJ 一种；生产大表几乎不用裸 NLJ。
- “hash join 只能 inner”——outer 可在 probe 后补 unmatched build 行（或 role swap），实现复杂但可行。
- “半连接和 inner join 再 project 一样”——inner 会因右表多行重复左行；semi 不会。
- “merge join 不需要排序”——两边必须按 join key 有序（或先 sort）。

---

**今天你必须真正吃透的 3 句话**
- `Join 语义由 inner/outer/semi/anti 定义；算法只是物理实现。`
- `Join order 决定中间结果大小；join algorithm 决定对一对输入怎么匹配。`
- `等值 join 打开 hash 与 merge；任意谓词常退回 NLJ 或专用结构。`

**Join 在优化器搜索空间里的位置（直觉）**
- 三表 E、D、P：可能的 join order 是 `(E⋈D)⋈P`、`E⋈(D⋈P)` 等；每步还要选 NLJ/Hash/SMJ。
- 中间结果宽度（列数）与行数（cardinality）共同决定内存与 I/O；join order 选错比 algorithm 选错更致命的情况并不少见。
- 统计信息（表大小、NDV、直方图）是代价模型的输入——执行层算法正确，plan 选错仍会慢。
