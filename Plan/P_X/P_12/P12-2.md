**朴素 NLJ 算法**
- 输入：outer 关系 R，inner 关系 S，谓词 `pred(r, s)`

```text
for each tuple r in R:
  for each tuple s in S:
    if pred(r, s):
      emit (r, s)
```

- 复杂度：
- 比较次数：|R| × |S|（最坏）。
- I/O（若每次内层扫 S 都冷读）：O(|R| × |S|) page reads 量级——非常恐怖。

- 例子：
- |R| = 10^4, |S| = 10^4 → 10^8 次比较。
- 现代 CPU 每秒十亿次比较看似能扛，但 cache miss + 无 index 全表扫 S 会把磁盘打满。

---

**NLJ 何时“还可以接受”**
- outer 很小：|R| = 10，|S| = 10^8 → 10 × 全表扫 S，若 S 有 index on join key 则变 Index NLJ。
- 强过滤后 outer 极小：WHERE 后 R 剩几行。
- 非等值谓词且无更好结构：range join 有时只能 NLJ 或 sort-merge 特化。
- 教学与正确性：第一版 join executor 几乎总是 NLJ——先对再快。

---

**块 NLJ（Block Nested Loop Join）思想**
- 问题：朴素 NLJ 对每个 r 都完整扫描 S，S 的热 page 无法复用。
- 思路：一次读 outer 的`一批 block`进内存，inner 只扫 S 一次 per batch。

```text
for each outer block Br (能放进内存的若干 r):
  for each tuple s in S:
    for each r in Br:
      if pred(r,s): emit
```

- 效果：
- 内层 S 扫描次数从 |R| 次降为约 |R|/batch_size 次。
- 仍是 O(|R|×|S|) 比较，但 I/O 常数显著下降。

- 你要记住的是`摊销 inner 扫描`的直觉，而不是死记公式。

---

**Index Nested Loop Join（Index NLJ）**
- 前提：inner 表 S 在 join key 上有索引（B+树、hash index 等）。
- 算法：

```text
for each tuple r in R:
  use index on S to find all s where s.key = r.key  // equi-join
  for each such s:
    if other preds(r,s): emit (r,s)
```

- 复杂度（直觉）：
- 每个 r：一次 index probe O(log |S|) 或 O(1) + 输出匹配行数 k_r。
- 总：O(|R| × (log |S| + k_r))。

- 何时极优：
- |R| 小，|S| 大，selective equi-join。
- 例子：订单表 1 行查 1000 万行用户表的主键 —— 点查。

- 何时仍差：
- |R| 大，index probe 次数 = |R|，随机 I/O 多。
- join key 不是 index key 前缀，退化成 scan+filter。

---

**NLJ 与连接类型**
- **Inner**：如上 emit 匹配对。
- **Left outer**：
  - 对每个 outer r，记录是否至少匹配一次。
  - 若无匹配，emit `(r, NULL_S)`。
  - 实现：内层循环后检查 flag。

```text
for each r in R:
  matched = false
  for each s in S:
    if pred(r,s):
      matched = true
      emit (r,s)
  if not matched:
    emit (r, null_pad(S))
```

- **Semi**：
  - 找到第一个匹配即可 emit r 并 break inner loop（若谓词只依赖存在性）。
- **Anti**：
  - 若无匹配 emit r；有匹配则 skip r。

- 这些在 NLJ 框架里只改`emit 规则`，说明 NLJ 是理解语义的好载体。

---

**谓词拆分：join pred vs filter pred**
- 计划里常分：
- `join predicate`：等值 key（可 hash/merge/index）。
- `other predicate`：salary > x 等（post-join filter 或 loop 内检查）。

```sql
FROM E JOIN D ON E.dept_id = D.id AND E.salary > D.avg_salary
```

- 混合谓词可能阻止纯 hash join（非纯 equi），优化器可能：
- equi 部分 hash join + 上层 filter
- 或 NLJ 在 loop 内测完整 pred

---

**bustub：NestedLoopJoinExecutor 怎样读**
- 典型状态机：

```cpp
class NestedLoopJoinExecutor : public AbstractExecutor {
  void Init() override {
    left_->Init();
    right_->Init();
    // 读 left 第一行；准备内层扫描
  }
  bool Next(Tuple *out) override {
    while (有 left tuple) {
      while (有 right tuple) {
        if (Match(join_pred, left, right)) {
          组装 out; return true;
        }
        advance right
      }
      advance left; reset right scan (right_->Init())
    }
    return false;
  }
};
```

- 关键点：
- 每换一行 left，必须`重置 right child`（重新 Init + 全扫描）。
- 这是 NLJ 慢的根源，也是正确性要点：漏 reset 会漏匹配。

- 输出 tuple：
- 通常 `Tuple::Concat` 或按 output schema 填 left+right columns。
- outer join NULL pad：右 schema 列填 null value。

---

**NLJ 的不变量与易错 bug**
- `N1`：对每个 outer 行，inner 必须完整枚举（或 index 给出完整匹配集），除非 semi 提前 break 且语义允许。
- `N2`：left/right 角色与 outer/inner 一致；swap 影响 IO 但不影响 inner join 语义（equi 对称时）。
- `N3`：right child 重置必须从头开始；保存 stale iterator 会漏行。
- `N4`：outer join 的 unmatched outer 行恰好输出一次。

- 典型 bug 现象：
- 结果行数偏少 → 常是 inner 没 reset。
- outer join 缺 NULL 行 → 未 track matched flag。
- 重复行异常多 → semi 误用 inner emit 逻辑。

---

**NLJ vs Hash Join：何时 NLJ 仍赢**
- |R| 极小（个位数），|S| 极大，S 有 index → Index NLJ。
- 非 equi join，无 merge 结构 → NLJ 或专用算法。
- hash 建表成本 > 直接 probe：例如 R 只有 1 行。

- 何时必输：
- 两表都无 index，|R|≈|S| 大，equi join → hash join 或 sort-merge。

**Cardinalities 手算模板（Inner Equi-Join）**
- 设 |R|=n，|S|=m，右表 join key 唯一（主键）：inner 结果行数 ≤ n（每个 outer 最多一个匹配）。
- 若右表 join key 不唯一，某 key 在 S 有 k 条，R 中 c 条该 key → 贡献 c×k 行。
- 手算练习：R 两行 key=1，S 三行 key=1 → inner 输出 2×3=6 行；semi 只输出 R 的两行各一次。

**NLJ 调试检查表**
- 每 advance outer：是否 `right_->Init()`？
- outer join：是否每 outer 检查 matched？
- semi：匹配后是否 break inner？
- 输出 schema：左列偏移 + 右列偏移是否与 plan 一致？
