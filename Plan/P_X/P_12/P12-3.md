**先把 `P12-2` 和这一段接起来**
- NLJ：O(|R|×|S|) 比较。
- Hash Join：等值条件下期望 O(|R|+|S|) + build hash 表成本——当 build 能进内存且无极端 skew 时，大表 join 的默认答案之一。

---

**Hash Join 总图**

```text
         Build 侧（通常较小）              Probe 侧（通常较大）
                 │                                │
                 ▼                                ▼
        读入全部 build 行                 流式读 probe 行
        hash(join_key) ->                   对每行 hash key
        bucket 链表/数组                       查 build HT
        存 build tuple 副本/指针                  │
                 │                                │
                 └────────── probe 匹配 emit ─────┘
```

**Phase 1 — Build**
- 扫描 build 侧所有 tuple。
- 提取 join key，`ht.insert(key, build_tuple)`。
- 同一 key 多行：chain 上挂多行（inner join 会输出笛卡尔积匹配数）。

**Phase 2 — Probe**
- 扫描 probe 侧。
- 对每 probe 行，查 ht 中同 key 的所有 build 行。
- 对每条匹配 emit `(build, probe)`（列顺序依 plan）。

- 不变量 `HJ1`：
- 所有 key 相等的 (b,p) 对必须被 emit 恰好一次（inner 语义下）。

---

**为什么 build 选小表**
- 内存：hash table 大小 ∝ build 行数 × 行宽。
- 若 build 大于可用 memory → spill（Grace hash join 思想：partition 两边到磁盘，逐分区 in-memory hash join）。
- probe 侧流式，不必全进内存。

- 优化器估算：
- 选 cardinality 小的一侧做 build（在 equi join 对称时 swap 角色）。

- 例子：
- Employee 1000 万行，Department 200 行 → build Department，probe Employee。

---

**Hash Join 是阻塞算子（build 侧）**
- Probe 开始前，通常必须完成 build phase（或至少当前 partition 的 build）。
- 与 `P11` Sort 类似，打断 pipeline：
- build child 必须被消费完，probe 才能开始有效输出（单 partition 视角）。

- Volcano 接口实现常见模式：
- `Init`：跑完 build child，建好 HT。
- `Next`：从 probe child 拉行，查 HT emit。

---

**Hash Join 与 Outer / Semi / Anti**

**Left Outer Hash Join（思路）**
- Probe 阶段：对每条 probe 行（若 probe 是 preserved side）记录是否匹配。
- 或者：build 是 preserved side 时，probe 后扫描 HT 中未被 visit 的 build 行 emit NULL pad。
- 角色取决于哪一侧是 outer preserved table；实现要 mark matched bit on build entries 或 probe-side flag。

**Right Outer**：常改写为 swap + left outer。

**Semi Join**
- Probe 命中 key 且谓词满足 → emit probe 行（仅左列）一次，不再 emit 同 probe 行的其他 build 匹配（若 EXISTS 语义）。
- 实现：对该 probe 行 first match 后 skip 剩余 build chain。

**Anti Join**
- Probe 无匹配 → emit probe 行；有匹配 → 不 emit。

- 易错：semi 用 inner emit 导致重复左行。

---

**Sort-Merge Join（SMJ）**

**前提**
- 两输入按 join key 有序（或先 Sort，代价计入计划）。

**Merge 过程（equi-join）**

```text
指针 l, r 分别指向左右有序流当前行
while l and r not EOF:
  if key(l) < key(r): advance l
  elif key(l) > key(r): advance r
  else: // 键相等，处理 equal run
    gather all l rows with key k
    gather all r rows with key k
    emit Cartesian product of two runs (inner)
    advance l,r  past run
```

- 对 equal run 的处理：
- 若 l 侧 key=k 有 p 行，r 侧 q 行 → inner 输出 p×q 行。

- 复杂度：
- merge 扫描 O(|L|+|R|)，若需 sort 则加 sort 成本。

**SMJ 何时 attractive**
- 输入已经有序（index scan 按 join key，或上游 sort）。
- 需要输出有序结果（ORDER BY join key）。
- 非等值 range join：`key_l <= key_r` 型 merge 变种（进阶）。

**SMJ vs Hash Join**

| | Hash Join | Sort-Merge Join |
|---|-----------|-----------------|
| 需要排序 | 否 | 是（除非已有序） |
| 内存 | build HT | merge buffer 小 |
| skew | 敏感 | merge 按序扫描，较稳 |
| 输出顺序 | 无序 | 可按 key 有序 |

---

**Grace Hash Join / spill（思想）**
- 当 build HT 装不下：
- 用 hash 函数 h 将 R、S 分成 B 个分区 R0..Rb-1, S0..Sb-1。
- 保证：R_i 中 key 只会与 S_i 中 key 匹配。
- 逐分区加载 Ri 进内存 hash join Si。

- 与 `P11` external hash agg 同族：partition → spill → 递归。

---

**Join 输出 schema 与谓词**
- 输出宽度 = 左列 + 右列（减 projected away）。
- 剩余 join 谓词（非 pure key equi）可在：
- emit 前测试
- 或 HashJoin 后 Filter 节点

- NULL 行为：
- `NULL = NULL` unknown → inner join 不 match。
- outer join 保留侧无匹配时，对侧 NULL 不是“NULL = NULL 匹配”，是 padding。

---

**bustub HashJoinExecutor 阅读要点**
- Plan node 字段：
- `join_type_`：INNER, LEFT, etc.
- `build_side_` 或 child index 标记 build child。
- `join_key_` 表达式。

- Init：
- `build_child_->Init()`; drain to HT。
- `probe_child_->Init()`。

- Next：
- `probe_child_->Next` → hash probe → 若 multi-match 需 cursor 状态 emit 完再拉下一条 probe。

- 状态机复杂度：
- 同一 probe 行对 HT 中 chain 多条 build，要 nested cursor：

```text
current_probe_
current_build_chain_iterator_
```

- 漏这个 iterator 会只输出第一条匹配。

---

**关键不变量（本段）**
- `M1`：Inner hash join 不丢、不多匹配对（在 equi 语义下）。
- `M2`：Build HT 在 probe 期间只读（除非 outer mark）；probe 不应修改 key。
- `M3`：SMJ equal-run 必须处理完整 run 再 advance，不能只配第一对。
- `M4`：Outer preserved 侧每行至少输出一次。
- `M5`：算法选择与 join order 正交，但 build 侧大小影响 memory。

---

**常见错误理解与 bug**
- 以为 hash join 不需要等值谓词 —— 需要 hashable equi keys。
- probe 阶段 build 侧还在写 —— 竞态或结果错。
- SMJ 在 key 相等时只 emit 一对 —— 漏 Cartesian within run。
- 把 build/probe 侧固定为 SQL 文本左/右，而非 optimizer 选择的小表侧。
- Hash 冲突未比 full key，只比 hash code —— 灾难性错误。

**今天你必须真正吃透的 3 句话**
- `Hash Join = build 小表 HT + probe 大表流式查表；等值 join 的 O(n+m) 期望解。`
- `Sort-Merge = 有序双指针 + equal run 笛卡尔；已有序输入时常常很省。`
- `Outer/Semi/Anti 改的是 emit 规则，不是换算法名字那么简单。`

**Grace Hash Join 与 P11 External Sort 的对照**
- 两者都用“分区 +  spill + 分阶段处理”应对内存不足：sort 分 run 再 merge；join 分 partition 再 local hash join。
- 不变量都是：划分边界必须保证“该在一起的数据不会被打散到错误分区”。

**SMJ 与 ORDER BY 的复用**
- 若优化器已生成 `Sort(E, join_key)` 与 `Sort(D, join_key)` 供 merge join，同一有序流有时可被下游 `ORDER BY join_key` 复用，避免第三次排序——这是 sort agg / sort merge 类优化的同族思路。

**Hash Join 输出阶段状态机（复习）**
- 状态：`PROBE_NEXT`、`EMIT_CHAIN`、`ADVANCE_PROBE`。
- 漏 `EMIT_CHAIN` 只输出每 probe 第一个 build 匹配 → 结果行数偏少，是 bustub 高频 bug。

**Join 算法与 P13 Executor 接口**
- HashJoin Init drain build child = P13 阻塞算子在 Init 的典型例子。
- SMJ 可实现为：两 child 各一个 sorted iterator，Next 时比较 advance——状态机在 Next 而非一次性 Init drain（若输入已有序）。
