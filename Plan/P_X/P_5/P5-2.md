| 英文 | 意思 |
|------|------|
| MemTable | 内存表：写先进入的内存结构 |

**最小 append-only KV 模型**
- 磁盘文件：顺序 append 记录，每条：

```text
| key_len | key | val_len | value | type |
```

- type 可以是 PUT（写入）或 DELETE（tombstone，删除墓碑）。

- 内存索引（memtable 内存表 / hash）：

```text
key -> (file_id, offset, length, seq)
```

- seq（序号）或 timestamp（时间戳）解决同 key 多版本：取最大 seq 为最新。

**Put 路径**
- 1. 序列化记录，append 到 active segment（当前活动段）末尾。
- 2. 更新内存索引指向新 offset。
- 3. 可选：WAL 先持久化 memtable 变更（实现相关）。
- 4. segment 满则 seal（封存），开新 segment。

**Get 路径**
- 1. 查内存索引得最新 offset。
- 2. 若索引未命中，查 on-disk index（磁盘索引）或 scan segment（慢路径）。
- 3. 读 offset 处 record，若 type=DELETE 返回 not found。

**Delete 路径**
- 不擦除旧 PUT，append 一条 DELETE tombstone。
- 索引更新为 tombstone 位置或标记 key 不存在。
- compaction（合并整理）时才物理清除旧 PUT。

---

**为什么读可能变慢：读放大**
- 场景 A：索引准确指向最新 -> 一次磁盘读，读放大低。
- 场景 B：索引只在 memtable，未 flush（刷盘），crash 后 rebuild scan 全文件 -> 读放大高。
- 场景 C：LSM 多层，点查要查 memtable + L0 多个 SST + L1... -> 多次 IO。

```text
Get(key):
  memtable -> L0 SST files (可能多个) -> L1 -> L2 -> ...
```

- Bloom filter（布隆过滤器）、block index（块索引）用来减少无效读，但机制复杂度上升。

**如果没有读路径优化**
- 每次 Get scan 全文件，O(文件大小)，不可用。

---

**写放大从哪来**
- 用户写 1 次 PUT，磁盘可能写：
- append 1 条 record（正常）
- segment 满 flush memtable 写整块 SST（batch 写，摊薄）
- compaction 把旧 SST 合并重写，同一 key 历史版本被多次重写

- LSM 经典矛盾：
- 为了写顺序和 batch，后台 compaction 造成写放大。
- leveled vs tiered compaction（分层合并 vs 分层/成批合并）是在写放大、读放大、空间放大之间 tradeoff（权衡）。

**页式对比**
- 页式小更新：写 1 page（可能 4KB）改几个字节 -> 写放大高。
- LSM：append 一条 record 可能写放大低，但 compaction 补账。

---

**空间放大从哪来**
- 旧版本未 compaction：同一 key 多条 PUT 共存。
- tombstone 未清理：DELETE 记录占空间，旧 PUT 也在。
- segment 内部碎片：padding（填充）、对齐、未写满块。

```text
有效数据: 100MB
磁盘占用: 350MB
空间放大 ≈ 3.5x
```

- 监控指标：live bytes（有效字节） vs total bytes（总占用）。

---

**segment / SST 组织**
- segment 写满后 seal，变为只读：

```text
+---------------- segment 100MB ----------------+
| block | block | block | index | bloom | footer |
+------------------------------------------------+
```

- block：数据块，内部有序或无序 key（视实现）。
- index：block 边界 -> offset，加速 lookup（查找）。
- bloom：probabilistic（概率性）判断 key 是否可能存在。
- footer：文件尾元数据、magic（魔数校验）。

**为何 immutable（不可变）**
- 并发读无需锁整块文件。
- compaction 输入确定，输出新文件，原子 swap（切换）。
- 崩溃恢复：未完成 segment 可 truncate tail（截断文件尾）。

---

**memtable 与 flush**
- 写先进 memtable（内存结构：skiplist 跳表 / hash）。
- memtable 满 -> flush 成 L0 SST（顺序写大文件）。
- 读先查 memtable，再查磁盘层。

```text
Put -> memtable
memtable full -> flush -> L0 SST (append)
L0 太多 -> compaction -> L1
```

- 这是 LSM 树的标准节奏；mini 项目可只做 memtable + 单文件 append。

---

**tombstone 与可见性**
- DELETE 必须 append tombstone，否则旧 PUT 仍可见。
- compaction 规则示例：
- 同一 key 多条记录，保留 seq 最大。
- 若最大是 tombstone，则 key 删除，旧 PUT 可丢弃。

**初学者易错点**
- compaction 只保留最大 PUT，忽略 tombstone -> 已删 key 复活（resurrect）。
- tombstone 在跨 level merge 时过早丢弃，而旧 level 还有 PUT。

---

**范围扫描（Scan）更贵**
- 页式 heap：按 page 扫 tuple。
- LSM：多 layer（层）多文件 merge 有序输出。

```text
Scan [a, c):
  merge iterator over:
    memtable iterator
    SST1 iterator
    SST2 iterator
    ...
```

- 读放大和 CPU merge 成本都高，但 batch analytics（批量分析）有时仍合适（尤其列存结合）。

---

**一致性快照（简要）**
- 多版本并发读可能需要 snapshot seq（快照序号）：
- 只能看到 seq <= snapshot 的最新版本。
- compaction 不能删掉仍被 snapshot 需要的旧版本。

- 工业系统复杂；教学 mini-LSM 可先单线程、无 snapshot。

---

**Leveled vs Tiered Compaction（直觉）**
- Tiered（成批/分层堆积）：同层保留多个 overlapping（范围重叠）SST，读放大高，写放大相对低。
- Leveled（分层整理）：L1+ 层 key 范围不重叠，读放大低，compaction 写放大高。

- 选型 = 负载是读密集还是写密集。

---

**纸上例子：三次更新同一 key**
- 操作：PUT k=v1, PUT k=v2, DELETE k

```text
文件内容顺序:
  [k=v1 @100]
  [k=v2 @200]
  [DELETE k @300]

索引: k -> @300 (DELETE)
Get(k): not found

compaction 后文件可能只剩:
  (空，或 meta 表明 k 不存在)
```

- Compaction 前空间：3 条记录占空间。
- Compaction 后：0 或 1 条 meta。

**和页式 bustub 的对比表**

| 维度 | 页式 heap | 日志结构 |
|------|-----------|----------|
| 写 | 原地改 page | 末尾 append |
| 读点查 | RID/索引+page | 索引+可能多层 |
| 删除 | MarkDelete slot | tombstone append |
| 空间回收 | page compaction/vacuum | segment compaction |
| 崩溃恢复 | WAL redo page | replay tail / rebuild index |
