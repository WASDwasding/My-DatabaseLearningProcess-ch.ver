**今天这次的目标**
- 我们现在正式开始 `P5`，主题是：`日志结构数据库存储`。
- 这一段建立总框架，不急着写 LSM 树。
- 你学完这一段后，应该能回答 3 个问题：
- 为什么顺序写通常比随机写更友好。
- append-only 存储的核心思想是什么。
- 日志结构主存储和 WAL 恢复日志是不是一回事。

**先把 `P4` 和 `P5` 接起来**
- `P3/P4` 主线（bustub 默认）：页式 heap + 原地更新 page + BPM 缓存。
- 页式更新的典型代价：
  - 随机写分散在文件各处
  - 小更新也要整页写回（写放大）
  - 对 SSD 仍可能触发大量 erase/program 单元

- 日志结构路线的出发点：
- `能不能让写路径尽量变成在文件末尾顺序追加？`

- bustub 默认不是 LSM 主存储，但这节课帮你：
- 理解 RocksDB、LevelDB、Cassandra 等系统的设计动机
- 分清 WAL（预写日志）与 data file（数据文件）的职责
- 若以后扩展教学库做 append-only heap，有理论基础

**本课英文名词速查（先看这一段再往下读）**
- P5 英文词特别多。下面按“中文意思 → 它在系统里干什么”解释；后文再出现时你可随时回查。

| 英文 | 中文意思 | 一句话 |
|------|----------|--------|
| Log-Structured Storage | 日志结构存储 | 更新不当场覆盖，而是往日志末尾追加新版本 |
| append-only | 只追加 | 文件主要往后长，中间旧内容一般不原地改写 |
| in-place update | 原地更新 | 找到旧位置直接改（P3/P4 页式常见） |
| LSM / LSM-Tree | 日志结构合并树 | 先写内存，再刷成不可变磁盘文件，后台再合并 |
| MemTable | 内存表 | 最新写入先落在内存里的草稿本 |
| flush | 刷盘 | 把 MemTable 写成磁盘上的 SST/segment |
| SSTable / SST | 有序字符串表 | 磁盘上有序、通常不可变的数据文件（LSM 主数据形态） |
| segment | 段 / 日志段 | 一段可封存的数据文件；写满后常变成只读 |
| seal | 封存 | 当前段写满，关闭追加，再开新段 |
| immutable | 不可变 | 封存后内容固定，便于并发读与后台合并 |
| compaction | 压缩 / 合并整理 | 后台合并旧文件，丢掉过期版本，回收空间 |
| GC (Garbage Collection) | 垃圾回收 | 清掉逻辑上已无用但仍占磁盘的旧数据；常靠 compaction |
| garbage | 垃圾数据 | 已被新版本盖过、或已删除但仍留在文件里的旧记录 |
| tombstone | 墓碑 / 删除标记 | 删除时不擦旧值，而是追加一条“此 key 已删” |
| WAL (Write-Ahead Log) | 预写日志 | 为崩溃恢复先记账；不等于 LSM 的主数据文件 |
| Write Amplification | 写放大 | 用户写 1 份，磁盘实际写了多少倍 |
| Read Amplification | 读放大 | 用户读 1 条，实际读了多少块/多少文件 |
| Space Amplification | 空间放大 | 有效数据占 1，磁盘实际占多少 |
| Bloom filter | 布隆过滤器 | 快速判断“key 大概不在这文件”，减少白读 |
| seq / sequence | 序号 | 用来判断同 key 哪条更新、更新 |
| supersede | 覆盖 / 取代 | 新版本让旧版本变成 garbage |
| resurrect | 复活 | compaction 做错时，已删 key 又被读出来（要避免） |
| OLTP | 联机事务处理 | 高频小事务、强调点查与低延迟的一类负载 |

- 最容易混的一对：
  - `WAL`：保险单（恢复用）
  - `SST / segment`：仓库本身（主数据）
- 两者都可以“append-only 风格写”，但职责完全不同。

```text
页式更新 (bustub 主线)          日志结构 (本课)
----------------------          ----------------
找到 page                       追加新记录到 log/segment 末尾
原地改 tuple                    旧版本仍留在文件中
索引 -> RID -> page             内存/磁盘索引 -> 最新版本位置
BPM 缓存 page                   读可能要合并多个版本
```

- 两种都是“数据库怎么持久化”，但写路径哲学相反。

---

**问题定义**
- 什么是日志结构存储（Log-Structured Storage，日志结构存储）？
- `把更新视为向日志末尾追加新版本，而不是覆盖旧数据位置；读取通过索引找到最新有效版本。`

- 什么是 append-only（只追加）？
- `文件只增长、不在中间原地改写旧内容（或极少原地改）；新状态写新位置。`

- 注意：append-only 是写策略；日志结构是更广的存储组织家族，常含 segment（段）、compaction（合并整理）、多级结构。

---

**为什么顺序写更友好**
- 磁盘与 SSD 的常见特性：
- HDD：顺序读写的寻道成本低，随机写慢。
- SSD：没有磁头，但随机写仍可能导致写放大、GC 压力；顺序写对大写入更友好。

- 数据库写负载常常是大量小更新：
- 页式：每个更新可能触发一次 page 随机写。
- 日志结构：多个更新 batch 成顺序 append，摊薄 I/O 开销。

**第一性原理结论**
- `写路径优化目标：把随机写变成顺序写，即使读和空间后面变贵。`

---

**append-only 的核心机制（直觉）**
- 假设 KV 存储，key=`user:1:balance`：

```text
初始:  ... [user:1:balance=100 @offset 8000]
更新:  ... [user:1:balance=150 @offset 12000]  // 追加，不覆盖 8000
```

- 内存里维护：

```text
user:1:balance -> 最新 offset 12000
```

- 读：查索引得最新 offset，读一条记录。
- 旧版本仍在文件里，成为 garbage（垃圾数据），直到 compaction（合并整理）清掉。

**优点**
- 写简单：锁文件尾 append，批量 fsync（刷到持久存储）。
- 崩溃恢复有时更简单：重放 tail（文件尾）或 scan 重建索引。

**代价**
- 读放大：可能要跳过旧版本（若索引只指最新则读一次，但 range scan 范围扫描更复杂）。
- 空间放大：旧版本占磁盘直到 GC（垃圾回收）。
- 需要后台 compaction：否则文件无限膨胀。

---

**读放大、写放大、空间放大（入门）**
- 三个“放大”是评价存储引擎的核心指标：

**写放大（Write Amplification）**
- 用户写 1 字节，磁盘实际写了多少字节。
- 页式：小改可能写整页。
- LSM：compaction 时同一数据可能被重写多次。

**读放大（Read Amplification）**
- 用户读 1 条，实际读了多少条/块。
- LSM：多层 level（层级）查多个 SST（有序数据文件），或 scan 合并版本。

**空间放大（Space Amplification）**
- 有效数据 1GB，磁盘占 3GB，空间放大 3×。
- 旧版本、padding（填充对齐）、未 compaction 的 tombstone（删除墓碑）都贡献空间放大。

- 没有免费午餐：日志结构常常写路径好看，读和空间要还账。

---

**segment 与 compaction（先建立名词）**
- 文件常被切成 segment（段；也可叫 SSTable / SST，有序字符串表）：
- 不可变块，顺序写满 seal（封存），再开新 segment。

```text
seg1.log  seg2.log  seg3.log  ...
[旧数据]  [混合]    [最新]
```

- compaction / GC（合并整理 / 垃圾回收）：
- 扫描旧 segment
- 保留每个 key 最新版本（和未删除项）
- 写成新 segment，删旧 segment

- 细节在 P5-2/P5-3；现在要知道：没有 compaction，append-only 不可长期运行。

---

**日志结构主存储 vs WAL：必须分清**
- 这是本课最高频混淆之一。

**WAL（Write-Ahead Log，预写日志）**
- 用途：崩溃恢复，保证 durability（持久性）与 atomicity（原子性）。
- 内容：对 page 或操作的 redo/undo（重做/撤销）记录。
- bustub 页式存储：改 page 前先写 WAL，数据仍在 page 文件里。

**日志结构主存储**
- 用途：数据本身就这样组织，最新值靠 append。
- 数据文件就是“大日志”，不是辅助 recovery（恢复）的旁路文件。

```text
页式 + WAL:
  data file = pages          // 主数据仍是页文件
  wal file  = 恢复日志       // WAL 只是保险

LSM 主存储:
  SST/segment = 主数据       // 仓库本身
  可能另有 WAL 用于 memtable（内存表）刷盘前恢复（实现相关）
```

- 两者都可能“append-only 风格”，但职责完全不同。
- 混淆会导致：以为 bustub WAL 就是 LSM，或以为 LSM 不需要 WAL。

---

**页式存储、LSM、WAL 三者关系（总整理）**
- 这一段把 P3/P4 的页式主线，和本课的日志结构主线，以及两边都可能出现的 WAL，放在同一张图里看。
- 先记一句总纲：

```text
“日志结构”描述怎么组织主数据；
“WAL”描述有没有另写一份恢复保险；
两者都可以 append，但不是同一类文件。
```

**1. 先分清三个角色**

| 名字 | 它是什么 | 平时 Get 会读它吗 |
|------|----------|-------------------|
| 页式 data file（page 文件） | 页式系统的主仓库 | 会（经 BPM） |
| LSM 的 SST / segment | LSM 的主仓库（常不可变、追加形成） | 会 |
| WAL | 崩溃恢复用的保险单 | 通常不会 |

- 所以：不能因为 segment“长得像日志”，就说“LSM 平时靠读 WAL 拿数据”。
- 更准确：LSM 平时读的是 **用日志结构组织起来的主数据文件**（MemTable miss 后读 SST/segment）。

**2. 写路径：真正不像的地方在这里**

```text
页式：
  （常先写 WAL）
  -> 在某个 page 里原地更新
  -> page 变 dirty
  -> BPM 之后 flush 回 data file

LSM：
  （常先写 WAL，保护还没 flush 的 MemTable）
  -> 写入 MemTable（内存最新层）
  -> MemTable 满了 flush 成新的 SST/segment
  -> 旧文件一般不原地改
  -> 后台 compaction 合并整理主数据文件
```

- 核心差别不是“有没有日志”，而是：
  - 页式：**改原件**（in-place）
  - LSM：**写新件，再定期整理**（append + compaction）

**3. 读路径：表面很像，细节不同**

```text
页式：
  page_id
    -> 查 BPM page table（内存有没有这页）
       有：返回 frame 里的 page
       没有：选 frame（可能 evict）-> 从磁盘读入 -> 建映射 -> 返回

LSM：
  key
    -> 先查 MemTable
       有：返回最新值，或 tombstone（已删）
       没有：再去磁盘各层 SST/segment 找最新版本
```

- 两边都是“先内存、后磁盘”，所以看起来像缓存系统。
- 但内存层身份不同：
  - BPM 中的 page：磁盘页的**缓存副本**
  - MemTable：首先是**写缓冲区 / 最新数据源**，不只是镜子

- miss 之后也不完全一样：
  - 页式 miss：通常把整页**装进 buffer pool 并建立长期映射**，直到被 evict
  - LSM 的 MemTable miss：去读 SST/segment；数据会进入内存供本次使用，教学版可不做长期缓存，工业版常有 block cache

**4. 一张定心对照表**

| 维度 | 页式存储 | LSM / 日志结构主存储 | WAL |
|------|----------|----------------------|-----|
| 主要职责 | 主数据（按 page） | 主数据（按追加文件） | 恢复保险 |
| 更新方式 | 常原地改 page | 追加新版本 | 追加记录 |
| 内存先触点 | BPM frame | MemTable | 一般不参与正常读 |
| 磁盘主文件 | page data file | SST / segment | wal file |
| 删除常见形态 | MarkDelete | tombstone | 记录删除意图（若需要） |
| 后台整理 | page 内整理 / vacuum | compaction | checkpoint 后可回收旧日志 |
| 多版本 | 不是主模型 | 自然产生多个历史版本 | 有时有日志历史，但不是给 Get 用的 |

**5. 最容易说错的三句话（对照改正）**

- 错：`LSM 通过读 WAL 拿最新数据。`  
  对：`最新先看 MemTable；没有再看 SST/segment。WAL 主要用于恢复。`

- 错：`WAL 只属于页式存储。`  
  对：`页式和 LSM 都可以有 WAL；页式保护 page 更新，LSM 常保护未 flush 的 MemTable。`

- 错：`页式和 LSM 只是实现细节不同。`  
  对：`读路径都像缓存，但写哲学不同：原地改 vs 追加新版本再 compaction。`

**6. 图书馆比喻（三者版）**

```text
页式：
  大仓库里的书（page）可以抽出来在书架格子（frame）上改，
  改之前先在登记本（WAL）记一笔，防止停电后不知道改过什么。

LSM：
  新借还先写在柜台草稿本（MemTable），
  定期装订成不可变档案卷（SST/segment）放进档案室；
  旧卷不涂改，满了再整理合并（compaction）。
  若也有登记本（WAL），那是防止草稿本还没装订就断电。
```

**和 bustub 的关系**
- bustub 默认：页式 TableHeap + BPM + WAL（恢复课）。
- 本课概念可迁移：
- 理解“为什么有些系统选 LSM”
- 理解 WAL 与 data file 分工
- 若做扩展项目：append-only KV 或 mini-LSM 实验

- 执行器/优化器思想仍相通：谓词下推、批量读，只是物理格式不同。

---

**适用场景直觉**
- 日志结构/LSM 常见优势负载：
- 写密集
- 顺序写友好介质
- 可接受读放大和后台 compaction

- 不天然适合：
- 极低延迟点查且读放大敏感
- 大量原地更新且读最新极频繁
- 磁盘空间极紧且无 compaction 资源

- OLTP 页式 vs 写密集 KV/时序，选型不同。

---

**不变量（日志结构视角）**
- `L1`：索引中 key 指向的版本必须是当前最新有效版本（或 merge 合并规则一致）。
- `L2`：segment seal 后不可变；更新只能在新 segment append。
- `L3`：tombstone（墓碑/删除标记）在 compaction 前必须参与可见性判断。
- `L4`：compaction 不能丢最新版本，不能 resurrect（错误地复活）已删除 key（在同一 snapshot 快照语义下）。

---

**没有日志结构视角会怎样**
- 看到 RocksDB 的 level compaction 只会背名词。
- 把 WAL 当成“另一种表文件”。
- 无法解释写快读慢的根因，调参无从下手。

---

**初学者易错点**
- 以为 append-only = 不需要 compaction。
- 把 bustub 的 WAL 文件当成 LSM 的 SST。
- 忽略 tombstone：compaction 删早了会读到已删 key。
- 以为 LSM 点查永远 O(1)：实际可能多层二分 + bloom。
