**本节加重名词**
| 英文 | 意思 |
|------|------|
| full compaction | 全量合并：扫整份旧日志，重写成新文件 |
| partial compaction | 部分合并：只整理一部分文件/某一层 |
| atomic swap / rename | 原子切换：新文件就绪后一次性替换旧文件 |
| live bytes / total bytes | 有效字节 / 总占用：看空间放大 |
| supersede | 新版本盖过旧版本 |

---

**Compaction 为什么不可避免**
- append-only 只追加不回收 -> 文件单调增长。
- 同一 key 多版本、tombstone、已 supersede（被新版本取代）的 PUT 都是 logical garbage（逻辑垃圾）。
- compaction = 垃圾回收 + 读路径整理。

**不做 compaction 会怎样**
- 磁盘满。
- Get 若退化 scan，越来越慢。
- 备份和恢复成本上升。

---

**最小 compaction 算法（单文件 teaching 版）**
- 输入：old.log（只 append 过的记录流）
- 输出：new.log

```text
1. 顺序 scan old.log
2. 维护 hash: key -> (latest_record, latest_seq)
3. scan 完，遍历 hash 只写非 tombstone 的最新 PUT 到 new.log
4. 原子 rename: old.log -> old.log.bak, new.log -> active.log
5. 重建内存索引
```

- 这是 full compaction（全量合并），简单但 rewrite（重写）整个文件，写放大大。
- 工业 LSM 用分层 partial compaction（部分合并）控制写放大。

**不变量**
- compaction 后，任意 key 的可见值必须与 compaction 前一致（在同一语义下）。
- 最新 seq 规则必须全局一致。

---

**触发条件（教学系统可先用简单规则）**
- 文件大小 > 阈值（如 64MB）
- live bytes / total bytes < 0.5（空间放大过高）
- 手动 API：Compact()

- 生产系统：L0 文件数、level 大小比、后台线程负载。

**与 WAL 的协作（页式 vs LSM）**

**bustub 页式 + WAL**
- 用户事务改 TablePage。
- 先 append WAL record。
- 改内存 page（dirty），BPM eventual flush（最终刷） page 到 data file。
- WAL 是 recovery（恢复）辅助，data file 仍是 page 格式。

**mini LSM + 可选 WAL**
- Put 先进 memtable（内存表）。
- 可选：先写 WAL 再 memtable，crash 后 replay（重放）WAL 重建 memtable。
- memtable flush 成 SST（主存储）。
- SST compaction 合并主存储文件。

```text
页式:  WAL -> 改 page -> flush page
LSM:   WAL -> memtable -> flush SST -> compaction
       ^ WAL 可选但常见     ^ 主存储
```

- 关键：LSM 的 SST 是数据；WAL 是 memtable 未 flush 前的保险（若采用）。

---

**bustub 默认页式：本课如何“迁移理解”**
- bustub 不实现 LSM 主存储，但你可以：
- 把 DiskManager WritePage 想成“随机写 page”
- 把 append-only KV 想成“另一种 DiskManager 后端”
- 恢复课学 WAL 时，对比 LSM 的 WAL 角色

- 扩展实验（可选）：
- 新建 `AppendOnlyStorageEngine` 作业分支

**最小 append-only KV 模块切分**

```text
LogWriter        append 序列化 record 到文件
LogReader        按 offset 读 record
Index            key -> latest location
MemTable         写缓冲（可选第一阶段只用 Index）
Compactor        full scan + rewrite
Engine           Put/Get/Delete/Compact API
```

**阶段 0：无 compaction**
- Put append + 内存 hash 指最新 offset
- Get 读 offset
- Delete append tombstone
- 观察文件大小线性增长

**阶段 1：加 full compaction**
- Compact() 重写文件
- 统计 compaction 前后 total/live bytes

**阶段 2：加 segment seal**
- 单文件满 4MB seal，新文件；索引需 file_id

**阶段 3：加简单 L0 多层（进阶）**
- flush memtable 为 SST，点查查 mem + 所有 L0

**Engine API 与失败条件**

```cpp
bool Put(const std::string &key, const std::string &val);
bool Get(const std::string &key, std::string *out);
bool Delete(const std::string &key);
void Compact();
```

- Put 失败：磁盘满、serialize 错误。
- Get 失败：key 不存在、tombstone、offset 越界。
- Delete 失败：同 Put。
- Compact 失败：中途 crash 需保留 old file 直到 atomic swap 成功。

---

**调试与观测指标**
- `total_bytes`：文件总大小
- `live_bytes`：最新有效 KV 估算大小
- `amplification = total / live`（放大比）
- `get_steps`：一次 Get 访问了多少文件/层

- 实验：连续 Put 同一 key 1000 次不 compact -> amplification ≈ 1000。
- 再 Compact -> amplification 接近 1。

**常见 bug 现象**
- Get 读到旧值：索引未更新到最新 offset。
- Delete 仍 Get 到：tombstone 未参与索引或 compaction 丢 tombstone。
- Compact 后丢数据：merge 规则错，未保留 max seq。
- crash 后索引空：无 WAL replay（重放）。

---

**测试清单**
- Put/Get 往返
- Overwrite 同一 key，Get 最新
- Delete 后 Get not found
- Compact 前后语义不变
- Compact 后文件变小
- 故意 corrupt tail record（损坏文件尾记录），reader 应 fail graceful（优雅失败）
- （若有 WAL）crash 模拟 replay

**读路径长度实验（教学）**
- 实现 Get 时计数：scan 了多少条 record 才找到（无索引慢路径）。
- 有索引 vs 全 scan 对比，量化读放大。

---

**与 OLTP 页式的选型讨论**
- OLTP（联机事务处理）：高频小更新、强点查时，页式 + BPM + 索引常更稳。
- 写密集、可 batch、读可容忍多层：LSM。
- bustub 选页式因为教学链：page -> BPM -> index -> WAL 清晰。

---

**初学者易错点**
- compaction 期间仍接受写，未做 double-buffer（双缓冲）或版本切换。
- rename 非原子，crash 中间丢文件。
- 索引只存 offset 不存 file_id，多 segment 时读错文件。
- 把 teaching compaction 当成“可在线随意触发无成本”——大文件 rewrite 会 stall（卡住前台）。
