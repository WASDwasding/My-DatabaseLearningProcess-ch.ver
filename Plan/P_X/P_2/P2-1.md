我先按“教学模式”带你正式进入 `P2`。这一段先不急着猛背 SQL 语法，而是先把一个最容易被忽略的问题打透：`SQL 到底是什么，它为什么是数据库系统的入口语言，它和后面的内核模块是什么关系。` **P2-1 开始**

**今天这次的目标**
- 我们现在正式开始 `P2`，主题是：`现代 SQL`。
- 这一段你要先建立一个总判断框架，而不是一头扎进语法细节。
- 你学完这一段后，应该能回答 3 个问题：
- 为什么 SQL 是声明式语言，而不是命令式脚本。
- 为什么 SQL 看起来像“给用户写的语法”，但实际上会深刻影响 binder、planner、optimizer、executor。
- 为什么 SQL 里那些看起来“别扭”的地方，例如 `NULL`、`GROUP BY`、子查询，恰恰是数据库实现里的高风险点。

**先把 `P1` 和 `P2` 接起来**
- `P1` 你已经学了两件根本事情：
- 数据在逻辑上被抽象成关系。
- 查询在逻辑上被抽象成关系代数风格的运算树。

- 但如果数据库只有关系模型和关系代数，还缺一件很重要的事：
- `用户怎么把自己的查询意图表达给系统？`

- 这就是 SQL 的位置。
- 你可以先把它理解成：
- `SQL 是用户和数据库逻辑层之间的接口语言。`

- 用户不会写：

```text
投影 name
  <- 选择 age > 20
       <- Student
```

- 用户写的是：

```sql
SELECT name
FROM Student
WHERE age > 20;
```

- 所以：
- `关系代数更像数据库内部逻辑语言`
- `SQL 更像用户可读可写的声明式查询语言`

- `P2` 学的，就是这两层之间怎么对应。

---

**问题定义**
- 什么是 SQL？
- 初学者最容易给出一个很表面的答案：
- “SQL 就是查数据库用的语句。”

- 这个答案太浅了。
- 更准确一点说：
- `SQL 是一种声明式数据查询与操作语言，用户描述“要什么结果”，而不是显式描述“按什么步骤做”。`

- 这句话里最关键的是“声明式”。
- 你现在一定要把这个词真正想透。

---

**为什么需要声明式语言**
- 先从第一性原理来问：
- 用户要查数据，为什么不能像普通程序那样写一段详细步骤？

- 比如用户本来想表达的是：
- “从学生表里找出年龄大于 20 的人，再只返回名字”

- 如果数据库要求用户自己写完整步骤，可能会变成：
- 先扫描哪个文件
- 再按哪个字段比较
- 再决定是否用索引
- 再指定输出字段顺序

- 这样会有什么问题？

- 第一个问题：`把物理执行细节暴露给用户`
- 用户本来应该只关心结果。
- 不应该关心：
- 这张表是 heap table 还是别的结构
- 是否有索引
- 过滤先做还是连接先做

- 第二个问题：`数据库失去优化空间`
- 如果用户已经把执行步骤写死了，那优化器就很难再发挥。
- 数据库最有价值的一点，就是它可以在不改结果的前提下自己决定更好的执行路径。

- 第三个问题：`系统边界会塌掉`
- 逻辑语义、优化策略、物理执行混在一起，模块会变得非常难维护。

- 所以你可以记住一句话：
- `SQL 的声明式本质，是把“要什么结果”和“怎么得到结果”分离开。`

---

**SQL 和普通编程语言最大的区别**
- 这部分你必须建立起来，否则后面会一直误解优化器和执行器的角色。

- 在普通命令式语言里，你通常自己指定步骤：

```text
1. 遍历数组
2. 判断条件
3. 把满足条件的元素塞进结果
```

- 在 SQL 里，用户通常只说：

```sql
SELECT ...
FROM ...
WHERE ...
```

- 也就是说：
- 命令式语言更像在描述`过程`
- SQL 更像在描述`目标结果`

- 这意味着数据库要承担更多责任：
- Parser 要理解语法
- Binder 要绑定名字
- Planner 要构造逻辑计划
- Optimizer 要找更便宜的等价改写
- Executor 才真正跑数据

- 这也是为什么你不能把 SQL 当成“只是多几个关键字”的语法问题。

---

**SQL 到底在解决什么核心问题**
- 从数据库内核视角看，SQL 至少在解决 4 个核心问题：

- `问题 1：统一表达查询意图`
- 用户可以用同一套语言表达过滤、连接、聚合、排序、子查询。

- `问题 2：隔离逻辑语义和物理实现`
- 用户写的是“查哪些数据”，而不是“怎样扫描 page”。

- `问题 3：给优化器留下空间`
- 用户不指定具体步骤，数据库才能在内部改写、重排、选择不同执行方式。

- `问题 4：给系统定义稳定边界`
- SQL 是用户接口层。
- 关系代数风格计划是内部逻辑层。
- 物理执行器是实现层。
- 三层分开后，系统才容易演化。

---

**你要先建立的总图**
- 先把 `P2` 在整个系统中的位置看清楚：

```text
用户需求
-> SQL
-> Parser / Binder
-> 逻辑计划
-> 优化
-> 执行
-> 结果
```

- 这张图里：
- SQL 是用户视角
- 逻辑计划是系统视角
- 执行器是实现视角

- 你后面学 `P3`、`P4`、`P8` 时会更多接触物理层。
- 但现在必须先明白：
- `物理层最终都是在为 SQL 所表达的逻辑需求服务。`

---

**为什么这节课比“背语法”更重要**
- 很多初学者学 SQL 的方式是：
- 背 `SELECT`
- 背 `JOIN`
- 背 `GROUP BY`
- 背一些面试题

- 这种学习方式对数据库内核开发几乎不够。
- 因为你真正需要理解的是：
- SQL 各个子句的逻辑顺序是什么
- 每个子句如何改变输入输出关系
- 哪些地方有隐藏语义，例如 `NULL`、重复值、聚合边界
- 这些语义怎样进入 binder、planner、optimizer、executor

- 所以这节课你要把注意力放在：
- `SQL 的语义`
- 而不是只放在：
- `SQL 的写法`

---

**先告诉你这节课最危险的几个地方**
- 这一节真正容易让实现出 bug 的，不是基础 `SELECT-FROM-WHERE` 本身。
- 而是下面这些点：

- `危险点 1：书写顺序和逻辑执行顺序不同`
- 用户写 SQL 的顺序，不等于数据库逻辑上处理它的顺序。

- `危险点 2：NULL 不是普通值`
- 它会引入三值逻辑，不是简单 true/false。

- `危险点 3：GROUP BY 不只是“分组显示”`
- 它会重塑输入输出关系，改变哪些表达式合法、哪些列还能被引用。

- `危险点 4：子查询不是“把一个查询塞到另一个查询里”这么简单`
- 它可能涉及相关列绑定、半连接语义、存在性判断等。

- 你可以把这几个点看成：
- `SQL 语义最容易和程序员直觉冲突的地方`

---

**和 bustub 的联系**
- 这节如果不和 `bustub` 连起来，你会很容易觉得只是用户语言。

- 在 `bustub` 里，虽然 SQL 支持范围有限，但它完整体现了主链路：

```text
SQL
-> parse
-> bind
-> plan
-> optimize
-> execute
```

- 这里 SQL 不是外壳。
- 它会决定：
- binder 怎样解析名字
- expression 怎样组织
- planner 生成哪些逻辑节点
- executor 需要输出什么 schema

- 特别是：
- `NULL` 传播
- 类型转换
- 比较语义
- 聚合输出

- 这些都不是“用户层细节”，而是执行器代码的 bug 高频区。

---

**如果这一段没学稳，后面会怎么卡住**
- 你会把 SQL 看成字符串拼接问题，而不是逻辑语义问题。
- 你会在写表达式求值时把 `NULL` 当普通值处理，结果条件判断全错。
- 你会在写聚合、连接、投影时搞不清输出 schema，导致 tuple 构造错误。
- 你会觉得优化器像黑魔法，因为你不知道 SQL 的声明式本质给了它什么自由度。

- 能用自己的话解释“声明式”到底是什么意思。
- 能说明 SQL 和关系代数的分工：一个偏用户表达，一个偏系统内部逻辑表示。
- 能指出 SQL 最容易引发实现错误的 2 到 3 个语义点。

**学习节奏建议**
