这一段开始把 `P2` 从“语义理解”推向“工程落地”。你前面已经知道 SQL 不只是语法，还知道逻辑顺序、`NULL`、聚合、子查询这些点为什么危险；现在要继续问：`这些语义在数据库内核里到底落到哪些模块，最小实现顺序应该怎样安排，最容易在哪里写出错。` **P2-3 开始**

**今天这次的目标**
- 我们现在正式学习 `P2-3`：`现代 SQL 怎样进入数据库内核实现`。
- 这一段你要解决 3 个工程问题：
- SQL 语义分别落到 parser、binder、planner、optimizer、executor 的哪里。
- 如果你自己做一个教学型数据库，最小 SQL 支持路径应该怎么切。
- 哪些地方最容易出现“看起来语法对了，但结果语义错了”的 bug。

**先把前两段和这一段接起来**
- `P2-1` 解决的是：SQL 为什么是声明式语言，它和关系代数、内核模块是什么关系。
- `P2-2` 解决的是：SQL 的核心语义是什么，哪些地方最危险。

- 但只理解语义还不够。
- 你现在要开始建立一个工程习惯：
- `每学一个语义点，都要能指出它落在哪个模块，谁负责它，谁最容易把它做错。`

---

**先给你一张工程总图**
- 你可以先把 SQL 查询链路理解成：

```text
SQL 文本
-> Parser
-> Binder
-> Planner
-> Optimizer
-> Executor
-> Result
```

- 这条链上，`P2` 关心的不只是“有这些模块”。
- 更关键的是：
- SQL 中每一类语义，会在哪一层第一次真正变得重要。

- 例如：
- 关键字位置和语法结构，首先在 Parser 里重要。
- 表名、列名、别名、作用域，首先在 Binder 里重要。
- `WHERE`、`GROUP BY`、`HAVING` 这些子句怎样变成逻辑算子，首先在 Planner 里重要。
- 谓词下推、投影裁剪、子查询去相关化，首先在 Optimizer 里重要。
- `NULL` 求值、聚合状态维护、连接输出 tuple 构造，首先在 Executor 里重要。

---

**1. SQL 语义在 Parser 里怎么出现**
- Parser 首先做的是：
- `把字符串变成结构化语法树。`

- 对 SQL 来说，这一步要回答：
- 这是不是一条合法的 `SELECT`
- `FROM` 里有几张表
- `WHERE` 有没有表达式
- `GROUP BY`、`HAVING`、`ORDER BY` 有没有出现
- 子查询是出现在什么位置

- 这一层还不会深入处理：
- 某列到底属于哪张表
- `GROUP BY` 后某列是否还能引用
- 这个条件能不能下推

- 但 Parser 非常重要，因为它决定：
- 后面模块拿到的是不是稳定结构，而不是一坨字符串

**工程上你要记住**
- Parser 容易写成“只要能 parse 就行”。
- 但如果 AST 结构设计得不好，后面 Binder 和 Planner 会非常痛苦。

---

**2. SQL 语义在 Binder 里怎么出现**
- Binder 是 `P2` 里一个特别关键的落点。
- 因为 SQL 里很多麻烦，不是语法麻烦，而是：
- `名字和作用域麻烦。`

- Binder 典型要做的事包括：
- 把 `Student` 绑定到 catalog 中某张表
- 把 `name` 绑定到具体列
- 处理表别名、列别名
- 处理多表同名列歧义
- 处理子查询内外层作用域

- 这里最容易炸的就是：
- `相关子查询`

- 例如：

```sql
SELECT s1.name
FROM Student s1
WHERE EXISTS (
  SELECT 1
  FROM Student s2
  WHERE s2.dept_id = s1.dept_id
);
```

- 这里 `s1.dept_id` 在子查询里被引用。
- 如果 Binder 没有把作用域设计清楚，就很容易把这个列绑定错。

**为什么 Binder 对 SQL 特别重要**
- 因为 SQL 允许：
- 别名
- 多层子查询
- 同名列
- 表达式嵌套

- 这些都会让“一个名字到底指向谁”变成非常实际的工程问题。

---

**3. SQL 语义在 Planner 里怎么出现**
- Planner 是 SQL 真正进入“关系代数风格逻辑树”的地方。

- 举个最简单的例子：

```sql
SELECT name
FROM Student
WHERE age > 20;
```

- Planner 不再关心字符串长什么样。
- 它关心的是：
- 需要一个 scan
- 需要一个 filter
- 需要一个 projection

- 于是逻辑上会变成类似：

```text
Projection(name)
  <- Filter(age > 20)
       <- SeqScan(Student)
```

- 对于更复杂 SQL，Planner 还要处理：
- join 树怎么组织
- `GROUP BY` 和 aggregate node 怎么构造
- `HAVING` 放在什么位置
- 子查询是保留为子计划，还是先转换成别的逻辑结构

**这里你一定要建立一个意识**
- Planner 不是在“解释语法”。
- Planner 是在把 SQL 语义翻译成系统内部能推理、能优化、能执行的逻辑结构。

---

**4. SQL 语义在 Optimizer 里怎么出现**
- 到了 Optimizer，`P2` 里很多 SQL 细节会直接影响规则是否安全。

- 比如：
- `WHERE` 谓词能不能下推
- `SELECT` 不需要的列能不能早点裁掉
- 某些 `IN` / `EXISTS` 能不能改写成 semi-join
- 子查询能不能去相关化

- 这里最容易犯的错误是：
- 只看关系代数的理想规则，不看 SQL 的真实语义限制。

- 例如：
- 有 `NULL`
- 有重复值
- 有外连接
- 有聚合

- 这些都会让“看起来能改”的规则，必须先检查前提条件。

**所以 SQL 对 Optimizer 的训练价值很高**
- 它逼你意识到：
- 优化规则不是口号。
- 真正的规则必须同时尊重：
- 逻辑等价
- SQL 实际语义
- 输入输出 schema

---

**5. SQL 语义在 Executor 里怎么出现**
- 到 Executor，这一课的很多“抽象语义”就真正变成代码里的行为了。

- 例如：

**表达式求值**
- `age > 20`
- `name || '_' || dept`
- `salary * 1.1`

- 这些都要在执行期被真正求值。

**NULL 传播**
- 如果某个输入是 `NULL`
- 比较、算术、逻辑操作的结果该怎样传播
- 这一点很容易实现错

**聚合状态**
- `COUNT(*)`
- `SUM(score)`
- `AVG(score)`

- 这些不是“算一下就完了”。
- 执行器需要维护每组的中间状态，最后再输出结果。

**连接输出**
- 左右两边 tuple 怎么拼
- 输出 schema 怎样组织
- `NULL` 填充如何处理

- 所以你要记住：
- `P2` 的很多语义点，最后不是停在语法树里，而是落成 executor 里的状态机和 tuple 构造逻辑。`

---

**为什么 `NULL` 是 executor 里的 bug 高频区**
- 这个点我单独拉出来讲，因为它真的太常见了。

- 很多同学在实现表达式求值时会默认：
- 输入是正常值
- 比较返回 true/false
- 逻辑运算按普通布尔规则来

- 但一旦碰到 `NULL`：
- 比较可能变成 unknown
- `WHERE` 中 unknown 往往意味着不通过
- 聚合对 `NULL` 的处理又和普通表达式不完全一样

- 这就意味着：
- 你不能只把 `Value` 当普通 C++ primitive 包一下。
- 你必须把“是否为 null”作为值语义的一部分。

---

**为什么聚合是另一个高风险区**
- 聚合的问题不只是“算和、算平均数”。
- 真正麻烦的是：
- 分组键怎么编码
- 每组中间状态怎么保存
- 空输入怎么处理
- `COUNT(*)` 和 `COUNT(col)` 的语义不同
- `SUM(NULL)`、`AVG(NULL)`、全空组要不要输出 `NULL`

- 也就是说：
- 聚合执行器其实是在维护一个“小型状态机”。
- 不是简单地看到一行就输出一行。

- 这就是为什么 `GROUP BY` 和 aggregate executor 往往比单纯 filter/projection 复杂得多。

---

**为什么子查询会同时牵动 Binder / Planner / Optimizer**
- 子查询最适合拿来训练“一个语义点跨多个模块传播”的感觉。

- 子查询先在 Parser 里出现为嵌套结构。
- 然后 Binder 要处理作用域和名字绑定。
- Planner 要决定把它表示成什么逻辑结构。
- Optimizer 可能还要尝试把它改写成 join 或 semi-join。
- Executor 最后还要真正执行它。

- 所以你一旦会实现一个最小子查询支持，实际上是在同时练：
- AST 结构设计
- 作用域管理
- 逻辑计划构造
- 执行策略选择

- 这就是为什么子查询虽然看起来只是 SQL 语法扩展，实际上工程含量非常高。

---

**和 bustub 的联系**
- 这部分你必须建立起来，否则这一段会显得空。

- 在 `bustub` 里，你可以先这样对照：
- SQL parser 负责拿到初始结构
- binder 负责把名字对到 schema/catalog
- planner 把 SQL 变成 plan nodes
- optimizer 对 plan nodes 做规则改写
- executors 逐步产出 tuple

- 如果你只看类名，会觉得：
- “这里一个 executor，那里一个 executor”

- 但如果你把 `P2` 的 SQL 语义装进去，就会意识到：
- `ProjectionExecutor` 不只是“选几列”
- 它要正确处理表达式和输出 schema
- `FilterExecutor` 不只是“if 一下”
- 它要按 SQL 的真假语义工作
- `AggregationExecutor` 不只是“做统计”
- 它要严格服从分组和聚合语义

---

**如果你自己做教学型数据库，最小实现顺序怎么安排**
- 我建议你按下面顺序来，而不是一上来做完整 SQL：

**第一步**
- 只支持：

```sql
SELECT col_list
FROM table
WHERE predicate;
```

- 先练：
- parser/binder 最短路径
- scan -> filter -> projection
- 表达式求值

**第二步**
- 加入简单内连接：

```sql
SELECT ...
FROM A, B
WHERE A.id = B.id;
```

- 先练：
- 多表绑定
- 输出 schema 组合
- join executor

**第三步**
- 加入最小聚合：

```sql
SELECT key, COUNT(*)
FROM T
GROUP BY key;
```

- 先练：
- 分组键
- 聚合状态
- 输出 tuple 构造

**第四步**
- 再考虑简单子查询或 `IN/EXISTS`

- 这样做的好处是：
- 每一步都有清楚验收
- 每一步都能对上一个真实语义点
- 每一步都不会把复杂度一次性炸开

---

**你写代码时最该盯住什么**
- 输入 schema 和输出 schema 是否始终明确。
- 每个 expression 节点的求值规则是否考虑了 `NULL`。
- 聚合状态是否和分组边界严格对应。
- 名字绑定是否真正区分了作用域，而不是靠字符串碰运气。
- 逻辑语义和物理执行是否被清楚分开。

---

**调试时优先收集什么证据**
- 对表达式 bug：
- 先打印输入 tuple、输入 schema、表达式树、求值结果、是否为 null。

- 对聚合 bug：
- 先打印分组键、每步状态更新、最终输出结果。

- 对绑定 bug：
- 先打印每个列引用最终绑定到哪张表哪一列。

- 对子查询 bug：
- 先打印作用域层次、外层引用、改写前后逻辑结构。

- 数据库里很多“SQL 结果不对”的问题，最后都能追到：
- 绑定错了
- `NULL` 处理错了
- schema 传播错了
- 聚合状态错了

---

**推荐最小实验**
- 实验 1：手工把 5 条 SQL 翻译成逻辑执行顺序，再翻译成逻辑计划树。
- 实验 2：列出 5 个 `NULL` 相关的反直觉判断，写出你期望的 SQL 结果。
- 实验 3：用伪代码设计一个最小表达式求值接口：输入 tuple 和 schema，输出 value 与 is_null。
- 实验 4：用伪代码设计一个最小聚合状态结构，支持 `GROUP BY key, COUNT(*)`。

---

**最小测试集合**
- 单表 `SELECT-FROM-WHERE` 的正确性测试。
- `NULL` 输入下比较、逻辑运算、过滤的测试。
- `GROUP BY + COUNT(*)` 的正常路径和空输入测试。
- 多表同名列、别名、歧义引用的绑定测试。
- 一个最小 `IN` 或 `EXISTS` 的子查询测试。

---

**这一段真正的工程目标**
- 让你不再把 SQL 当成“用户写法”，而是看见它在内核里的真实落点。
- 让你能把 SQL 语义映射到具体模块职责。
- 让你能为自己的教学型数据库设计一个可执行、可验收的最小 SQL 支持路线。
