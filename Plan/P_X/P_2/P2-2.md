这一段正式进入 `P2` 的核心内容。现在我们不再只讲“SQL 为什么存在”，而是要把 SQL 里最核心、也最容易写错实现的语义拆开来看。重点不是背子句，而是回答：`这些子句在逻辑上分别做了什么、它们怎样改变输入输出关系、哪些地方最容易和程序员直觉冲突。` **P2-2 开始**

**今天这次的目标**
- 我们现在正式学习 `P2-2`：`现代 SQL 的核心语义`。
- 这一段你要重点吃透 4 组内容：
- SQL 的书写顺序和逻辑执行顺序为什么不同。
- `NULL` 和三值逻辑为什么危险。
- `GROUP BY`、聚合、`HAVING` 分别在做什么。
- 子查询、`EXISTS`、`IN` 这些结构为什么会让 binder 和 planner 变复杂。

**先提醒一个学习方法**
- 不要把这一段当成“语法记忆课”。
- 你遇到每个 SQL 子句时，都要追问 4 个问题：
- 它的输入是什么。
- 它的输出是什么。
- 它会不会改变行数、列结构、分组边界或者真假判断方式。
- 如果实现错了，最容易在哪类查询里暴露出来。

- 如果你看完之后还是只能背：
- `SELECT ... FROM ... WHERE ...`

- 但说不清这些子句的逻辑顺序和相互约束，那这一段就还没真正吃透。

---

**第一件大事：书写顺序不等于逻辑执行顺序**
- 这是 SQL 最重要、也最反直觉的地方之一。

- 用户通常这样写：

```sql
SELECT name
FROM Student
WHERE age > 20
GROUP BY name
HAVING COUNT(*) > 1
ORDER BY name
LIMIT 10;
```

- 但逻辑上，数据库不是按这个顺序理解的。
- 更接近的逻辑顺序通常是：

```text
FROM
-> WHERE
-> GROUP BY
-> HAVING
-> SELECT
-> ORDER BY
-> LIMIT
```

- 你一定要问：
- 为什么 `SELECT` 明明写在最前面，逻辑上却不是最先做？

- 因为 `SELECT` 子句里要引用的列、表达式，必须先有输入关系。
- 输入关系从哪里来？
- 来自 `FROM`。

- `WHERE` 为什么在 `SELECT` 前面？
- 因为你必须先筛掉不满足条件的行，才能决定哪些数据会进入后续阶段。

- `GROUP BY` 为什么在 `SELECT` 前面？
- 因为分组会重塑输入。
- 一旦分组之后，后面允许直接引用的列范围就变了。

- `HAVING` 为什么在 `GROUP BY` 后面？
- 因为它是在过滤“分组后的组”，不是在过滤原始行。

**你要建立的核心观念**
- SQL 的书写顺序更像“用户表达顺序”。
- SQL 的逻辑顺序更像“数据库语义顺序”。

- 如果你把这两者混在一起，后面在写 planner、binder、aggregation executor 时会不断犯错。

---

**第二件大事：WHERE 和 HAVING 根本不是一回事**
- 这两个词初学者非常容易混。

**WHERE**
- 作用对象是：`原始行`
- 它发生在分组之前。
- 它决定哪些元组能继续进入后面的阶段。

**HAVING**
- 作用对象是：`分组后的组`
- 它发生在分组和聚合之后。
- 它决定哪些组能出现在最终结果里。

- 举个例子：

```sql
SELECT dept_id, COUNT(*)
FROM Student
WHERE age > 20
GROUP BY dept_id
HAVING COUNT(*) >= 2;
```

- 这里的逻辑不是：
- 先统计每个部门全部学生数，再看年龄。

- 真正逻辑是：
- 先从 `Student` 里保留 `age > 20` 的行
- 再按 `dept_id` 分组
- 再算每组 `COUNT(*)`
- 再筛掉 `COUNT(*) < 2` 的组

**为什么必须分清**
- 因为 `WHERE` 和 `HAVING` 作用的阶段不同，能引用的对象也不同。
- 你不能在 `WHERE` 里直接用聚合结果。
- 因为那时分组还没发生。

---

**第三件大事：NULL 不是普通值**
- 这是 SQL 语义里最容易造成直觉错误的地方。

- 很多程序员第一次看 SQL 时，会不自觉把 `NULL` 当成：
- 空字符串
- 0
- 某种特殊常量

- 这些理解都不对。
- 更准确地说：
- `NULL 表示值缺失或未知。`

- 这意味着：
- 它不是一个普通可比较值。
- 它会影响谓词求值规则。

- 最典型的例子：

```sql
NULL = NULL
```

- 这不是 `true`。
- 通常结果是 `unknown`。

- 为什么？
- 因为 SQL 语义不是在问：
- “两个空是不是一样”

- 而是在问：
- “两个未知值能否确认相等”

- 既然都未知，就不能断言一定相等。

---

**第四件大事：三值逻辑**
- 正因为有 `NULL`，SQL 的布尔逻辑不再只是：
- `true`
- `false`

- 而变成：
- `true`
- `false`
- `unknown`

- 这叫三值逻辑。

- 这件事的后果是什么？
- 在 `WHERE` 里，通常只有结果为 `true` 的行会被保留。
- `false` 和 `unknown` 往往都不会通过。

- 所以：

```sql
WHERE age > 20
```

- 如果某一行的 `age` 是 `NULL`，那么 `age > 20` 的结果不是 `false`，而往往是 `unknown`。
- 但对筛选效果来说，这行同样不会保留。

**为什么这会成为 bug 高频区**
- 因为很多表达式求值实现会偷懒，写成普通二值逻辑。
- 一旦这么做，`NULL` 相关查询就会产生错误结果。

- 你后面写 expression evaluator 时，一定要把这个点牢牢记住。

---

**第五件大事：GROUP BY 和聚合不是同一个概念**
- 这又是一个极容易混的点。

**GROUP BY**
- 它的作用是：`定义分组键`
- 也就是决定“哪些行应该被看成同一组”

**聚合函数**
- 它的作用是：`把一组多行压缩成某种汇总结果`
- 例如：
- `COUNT`
- `SUM`
- `AVG`
- `MIN`
- `MAX`

- 举个例子：

```sql
SELECT dept_id, COUNT(*)
FROM Student
GROUP BY dept_id;
```

- 这里不是简单地“按部门显示”。
- 逻辑上发生了两件事：
- 先按 `dept_id` 把行切成若干组
- 再对每组执行 `COUNT(*)`

**为什么这点重要**
- 因为一旦 `GROUP BY` 发生，输入关系的语义已经变了。
- 后续 `SELECT` 里能直接引用的列，不再是原表任意列，而通常必须满足：
- 要么是分组键
- 要么是聚合结果

- 否则语义会不清楚。

**这也是为什么很多 SQL 会报错**
- 比如你 `GROUP BY dept_id`
- 却还想直接 `SELECT name`
- 如果 `name` 既不是分组键，也不是聚合结果，那么系统就会问：
- “这一组里有很多名字，你到底想要哪个？”

---

**第六件大事：ORDER BY 和 LIMIT 是结果层语义**
- 很多人会把排序看成“随手加个修饰”。
- 但从系统角度看，它其实很贵。

**ORDER BY**
- 决定输出结果顺序。
- 它不会改变“有哪些行”，但会改变结果呈现顺序。

**LIMIT**
- 决定最终只返回前多少行。

- 这两个子句很像结果层操作。
- 它们往往位于逻辑链后面，因为通常要等结果集形态基本确定之后，才能排序和截断。

**为什么这在工程上重要**
- 因为排序常常是昂贵操作。
- 如果优化器能先过滤、先投影、先缩小中间结果，再排序，通常更有利。

---

**第七件大事：子查询为什么麻烦**
- 子查询表面上看只是“在一个查询里再写一个查询”。
- 但实际它会立刻引入更多语义复杂度。

- 例如：

```sql
SELECT name
FROM Student
WHERE dept_id IN (
  SELECT dept_id
  FROM Dept
  WHERE building = 'A'
);
```

- 这里系统要回答：
- 子查询返回的是单值、单列集合，还是多列关系。
- 外层谓词怎样和子查询结果互动。
- 这个结构能否改写成 join 或 semi-join。

**更复杂的是相关子查询**
- 如果子查询内部引用了外层查询的列，那就不是独立执行一次那么简单了。
- Binder 要能分清作用域。
- Planner 要能识别相关引用。
- Optimizer 可能要尝试去相关化。

- 所以子查询不是“再包一层 SELECT”这么简单。
- 它直接牵扯名字绑定、作用域、逻辑改写和执行策略。

---

**关键不变量**
- 对 `P2-2` 来说，最重要的不变量有这些：

- `不变量 1：逻辑顺序必须和 SQL 语义一致`
- 不能因为书写顺序把阶段搞错。

- `不变量 2：NULL 必须按三值逻辑参与表达式求值`
- 不能偷懒按二值逻辑处理。

- `不变量 3：分组后可引用的列范围必须受约束`
- 不然聚合查询语义会模糊。

- `不变量 4：子查询作用域和外层查询作用域必须清楚`
- 否则 binder 和 planner 很容易绑定错列。

---

**常见错误理解**
- `误区 1：SELECT 写在前面，所以最先执行`
- 不对。
- 写法顺序和逻辑顺序不是一回事。

- `误区 2：NULL 就是一个特殊值`
- 不对。
- 它代表未知或缺失，会改变布尔求值方式。

- `误区 3：GROUP BY 就是把结果按列分一下`
- 不对。
- 它会改变查询输入的逻辑组织方式和后续表达式合法性。

- `误区 4：子查询只是语法嵌套`
- 不对。
- 它往往直接牵涉绑定、重写、执行策略。

---

**把这一段落到最小实现时要警惕什么**
- 你不要一上来就想支持完整 SQL。
- 更合理的顺序是：
- 先支持单表 `SELECT-FROM-WHERE`
- 再支持简单投影和表达式
- 再支持 `GROUP BY + COUNT`
- 最后再考虑子查询

- 否则你会非常容易在：
- schema 传播
- NULL 求值
- 聚合输出
- 列绑定

- 这些地方同时炸开。
