**今天这次的目标**
- 我们现在正式开始 `P10`，主题是：`数据结构中的锁存机制`。
- 这一段你要建立 latch 的语义边界，而不是先背 crabbing 算法步骤。
- 你学完 `P10-1` 后，应该能回答 3 个问题：
- latch 和 lock 有什么区别，为什么不能混用概念。
- 共享/独占 latch 分别保护什么访问模式。
- 为什么单线程正确的 B+Tree 一到多线程就会 corrupt。

**先把 `P8`、`P9` 和 `P10` 接起来**
- `P8` 你实现了（或读懂了）单线程 B+Tree：split、merge、leaf chain。
- 真实数据库多个线程同时：
  - 两个 session 同时 Insert 相邻 key
  - 一个线程 range scan，一个线程 Delete
  - buffer pool 同一 page 被多个 executor 访问

- 如果没有 latch：
- 两个 Insert 同时 split 同一叶 -> 丢 key、链表断。
- 读线程看到写线程 half-updated 内节点 -> 走错 child。

- `P10` 就是教：
- `在保持 P8 结构不变量的前提下，用 latch 协调对 page 的并发访问。`

---

**先给你一张总图**

```text
                事务层                    数据结构层
                  |                            |
            Lock Manager                  Latch Manager
            (2PL, MVCC...)               (RW latch on page)
                  |                            |
           逻辑隔离性                     物理结构一致性
         "读到的语义对不对"              "页内字节会不会被写坏"
                  |                            |
                  +-------- B+Tree page -------+
```

- 同一次 B+Tree Insert 可能同时涉及：
- 事务 lock（若课程/project 要求）——谁可以读写字段
- page latch——谁可以读/写这个 page 的字节

---

**问题定义**
- 什么是 latch？
- 简单说：
- `保护内存中共享数据结构（尤其 buffer pool page）短期互斥的轻量同步原语。`

- 什么是 lock（事务锁）？
- `由锁管理器维护、与事务生命周期绑定的逻辑并发控制，保证隔离级别。`

- 两者不是同一层东西。

---

**latch vs lock 对比**

```text
维度           Latch                    Lock
------------------------------------------------------
保护对象       物理 page/结构            逻辑数据项/tuple
持有时间       极短（一次操作）          可能跨多条语句
是否死锁检测   通常避免；靠顺序          锁管理器检测/等待
是否参与 2PL   否                        是
用户是否感知   否                        是（阻塞/超时）
释放时机       操作完成即放              commit/rollback
```

- 如果没有这层区分：
- 你会用 mutex 包整棵 B+Tree（正确但极慢）。
- 或以为 MVCC 就不需要 latch（错，结构仍会 corrupt）。

---

**为什么单线程正确的结构多线程会错**
- 经典例子：两个线程同时 Insert 到同一满叶。

```text
Thread A: 读 leaf size=max, 准备 split
Thread B: 读 leaf size=max, 也准备 split
Thread A: split, 插入 key1
Thread B: split again on stale view -> 结构灾难
```

- 读改写竞态：

```text
Thread R: 读 internal keys[2]=100, 走 child 3
Thread W: split 把 keys 数组改写一半
Thread R: 用旧 child 3 -> miss 或 segfault
```

- 你要记住：
- `逻辑算法正确 ≠ 并发正确；并发正确需要互斥或乐观验证。`

---

**共享 latch vs 独占 latch**
- 是什么：
- **Shared (S) latch**：多读并发，用于 Lookup、Iterator 读叶。
- **Exclusive (X) latch**：独占读写，用于 Insert/Delete/split/merge 改 page。

- 为什么 Lookup 可以共享：
- 只要 page 不被写，多个读线程同时读 keys 数组安全。

- 为什么 Insert 必须独占：
- 修改 size、keys、children、next 指针，读线程看到中间态会 corrupt。

- 小例子：

```cpp
// 读路径
ReadPageGuard g = bpm->FetchPageRead(page_id);
const auto *leaf = g.As<BPlusTreeLeafPage>(...);
// 只读 KeyAt(i)

// 写路径
WritePageGuard g = bpm->FetchPageWrite(page_id);
auto *leaf = g.AsMut<BPlusTreeLeafPage>(...);
leaf->Insert(key, rid);
```

- bustub 的 `ReadPageGuard` / `WritePageGuard` 就是 latch 的 RAII 封装。

---

**Latch 粒度的选择**
- 粗粒度：整棵树一把锁——简单，零并发。
- 细粒度：每个 page 一把 latch——高并发，但要防死锁。

- B+Tree 标准选择：
- **page 级 latch** + **latch crabbing**（P10-2 详讲）。

- 如果没有 page 级：
- 锁整树吞吐崩溃。

- 如果 latch 粒度过细（槽位级）：
- 实现复杂度爆炸，split 仍要锁多页。

---

**和 buffer pool 的关系**
- page 在 buffer pool 的 frame 上。
- FetchPageRead/Write 通常：
  - pin page（防止 evict）
  - acquire latch（防止并发 corrupt）

- 顺序直觉：
- 先 pin 再 latch；unlatch 再 unpin（Guard 析构处理）。

- 如果没有 pin 就写：
- 写一半 page 被 evict 写盘，内存帧给别的 page -> 灾难。

---

**B+Tree 并发为何不能全程锁整棵树**
- 是什么问题：
- Insert 路径从 root 到 leaf，若全程 X latch root：
- 所有其他操作阻塞，并发度 = 1。

- 为什么 crabbing 必要：
- 在向下走的过程中，若子节点“安全”（split/merge 暂不需要），可释放祖先 latch。
- 让其他线程走其他分支。

- P10-2 会详讲 safe/unsafe 节点。

---

**死锁与加锁顺序（预告）**
- 两线程：
  - A：latch page 1 -> 等待 page 2
  - B：latch page 2 -> 等待 page 1
- -> 死锁。

- 避免规则之一：
- **全局固定加锁顺序**（如 page_id 递增）。
- B+Tree crabbing 通过“从上到下、必要时再锁兄弟”减少交叉。

---

**和 bustub 的联系**
- 并发 B+Tree project：
- `BPlusTree` Insert/Remove/GetValue 用 latch
- `Context` 记录 `write_set_` / `read_set_`，管理 guard 生命周期
- `TracedLatch` 调试死锁（部分版本）

- PageGuard 来自 buffer pool：
- 析构自动 Drop，避免忘记 Unpin/Unlatch。

- 若把 latch 当 lock 用：
- 事务结束才释放 page latch -> 性能极差 + 仍不保证隔离级别。

---

**常见错误理解**
- `误区 1：MVCC 就不需要 latch`
  - MVCC 解决读写版本可见性；page 字节仍要 latch。

- `误区 2：latch 就是 mutex 包整表`
  - 粒度应在 page，且读写分离。

- `误区 3：读路径永远不需要 latch`
  - 无 latch 读可能读到 torn write。

- `误区 4：P10 可以跳过先写并发 B+Tree`
  - 没有 P8 单线程正确，加 latch 只会更难 debug。

---

**今天你必须真正吃透的 4 句话**
- `Lock 管事务逻辑隔离；Latch 管物理 page 结构一致。`
- `读用 S latch，写用 X latch，持有时间要极短。`
- `单线程 B+Tree 多线程 corrupt 是常态，必须 page 级同步。`
- `bustub PageGuard = pin + latch 的 RAII。`

**Latch 持有时间的工程直觉**
- 理想情况：单次 B+Tree Lookup 持 latch 时间 = 几次 page 比较 + 无磁盘等待（页已在 buffer pool）。
- 危险情况：在 **持有 X latch 的 leaf page** 上调用可能阻塞的操作（日志 fsync、网络 RPC）——会阻塞所有访问该页的其他线程。
- 规则：`Latch 临界区只做内存中的 page 结构修改，尽快 Release。`

**和 OS mutex 的关系**
- bustub 的 ReadPageGuard/WritePageGuard 底层通常是 `std::shared_mutex` 或课程提供的 `ReaderWriterLatch`。
- 你不需要自己实现内核级 latch，但要理解：**每个 page 一个 RW lock** 是常见实现。
- 切忌在持有 page X latch 时再 Fetch 另一 page 并可能阻塞——死锁风险上升；crabbing 的设计就是为了缩短这种重叠窗口。
