**今天这次的目标**
- 我们现在正式开始 `P8`，主题是：`B+树`。
- 这一段你要建立的是索引选型的判断框架，而不是先背分裂合并步骤。
- 你学完 `P8-1` 后，应该能回答 3 个问题：
- 为什么数据库主索引通常不是二叉树或哈希表。
- B+Tree 的节点为什么要对齐 page，而不是按指针随意生长。
- 内节点和叶节点各自负责什么，为什么叶子链表对范围扫描至关重要。

**先把 `P7` 和 `P8` 接起来**
- `P7` 你学了 hash index：等值查找快，范围查询做不了。
- 真实 workload 里还有很多查询是：

```sql
SELECT * FROM orders WHERE amount BETWEEN 100 AND 500;
SELECT * FROM users ORDER BY created_at LIMIT 10;
SELECT * FROM logs WHERE ts >= '2026-01-01' AND ts < '2026-02-01';
```

- 这些都需要 key 的**全序**和**顺序扫描**能力。
- B+Tree 就是数据库在“磁盘 + 有序 + 高扇出”约束下的标准答案。

- 你可以这样记两者分工：
- `P7 hash index：点查加速器`
- `P8 B+Tree：有序索引主角，范围扫描和排序都靠它`

---

**先给你一张总图**
- B+Tree 在查询链路中的位置：

```text
SQL: SELECT * FROM T WHERE k BETWEEN 10 AND 20
        |
        v
   Index Scan (B+Tree)
        |
        v
   从根向下找 start key 所在叶节点
        |
        v
   沿叶子链表顺序读 [10, 20] 范围内 entry
        |
        v
   每条 entry 的 rid -> heap 取 tuple
```

- 和 hash 对比：
- hash：一次定位桶，无顺序。
- B+Tree：一次定位起始叶，然后链表向右扫。

---

**问题定义**
- 什么是 B+Tree？
- 简单说：
- `一种多路平衡搜索树，所有真实 key-value 都在叶子层，内节点只做导航，叶子之间用链表连接以支持范围扫描。`

- 4 个关键词：
- `多路`：一个节点有很多 key，扇出高。
- `平衡`：所有叶子深度相同。
- `key-value 在叶子`：内节点不存 record pointer（B+ 特性）。
- `叶子链表`：支持 range scan。

- 如果没有 B+Tree 这类结构：
- 要么 range 查询回退成 heap scan。
- 要么用 hash 只能做点查，ORDER BY 全表排序。

---

**为什么不是二叉搜索树 BST**
- 是什么问题：
- BST 每个节点最多两个孩子，树高 O(log2 N)。

- 在内存里 BST 或红黑树很好。
- 在磁盘上，代价模型完全不同：
- 一次随机 I/O 读一个 page，代价远大于比较几个 key。

- 小例子：
- 100 万 key，BST 高度约 20。
- 最坏查找要 20 次 page read。
- B+Tree 若每节点 200 key，高度约 3–4。

- 为什么扇出高这么重要：
- `磁盘数据库优化的是 I/O 次数，不是指针跳转次数。`
- 一个 page 里塞满 key 和 child pointer，一次 I/O 覆盖大量 key。

- 不变量直觉：
- 树高 h 满足 `N <= fanout^h`。
- fanout 越大，h 越小，I/O 越少。

---

**为什么不是哈希表（复习 P7）**
- hash 在等值上期望 O(1) page access，很快。
- 但：
- range 查询无法按 hash 顺序扫。
- 排序必须额外 sort。
- 前缀匹配、最左前缀联合索引也依赖有序。

- 所以生产系统常见组合：
- 主键 / 范围查询：B+Tree（InnoDB 聚簇索引就是 B+Tree）。
- 等值-only 辅助索引：有时 hash（较少），或仍用 B+Tree 求通用性。

---

**BTree vs B+Tree**
- 这是很多考试的坑，现在就要分清。

**BTree（B-Tree）**
- 内节点和叶节点都可以存 key + record pointer。
- 找到 key 可能在内部节点就结束。

**B+Tree**
- 内节点只有 key + child page id，不存 record。
- 所有 record pointer（或 rid）只在叶子。
- 叶子有链表。

- 为什么数据库几乎总是 B+Tree：

```text
1. 内节点更小 -> 扇出更高 -> 树更矮
2. 范围扫描只需扫叶子链表，不用中序遍历整棵树
3. 叶子顺序与 key 顺序一致，顺序 I/O 友好
4. 内节点结构统一，实现更简单
```

- 易错点：
- “BTree”在口语里有时泛指 B+Tree，读论文/代码要看清是哪种。

---

**节点对齐 page：为什么这是硬约束**
- 是什么：
- `每个 B+Tree 节点 = 一个 disk page（或若干固定 page），大小与 buffer pool page 一致。`

- 为什么：
- I/O 单位是 page，节点跨 page 会破坏“读一次拿一个节点”的模型。
- 节点大小固定，才能计算 max keys、max children。

- 如果没有 page 对齐：
- 节点可能半在一个 page 半在另一个，读一次 I/O 拿不到完整节点。
- fanout 不可预测，高度分析失效。

- 典型 page 布局（叶子）：

```text
Leaf Page:
  page_type
  size / num_keys
  next_page_id     // 链表
  keys[]
  rids[] 或 values[]
```

- 内节点：

```text
Internal Page:
  page_type
  size
  keys[]           // 分隔键
  children[]       // page_id，比 keys 多 1 个
```

- 不变量：
- `sizeof(node) <= PAGE_SIZE`（含 header）。
- 内节点：`children.size() == keys.size() + 1`。

---

**内节点：导航**
- 是什么：
- `只存 key 和子 page id，不存 tuple 数据。`

- 为什么：
- 同样 page 空间能放更多 key -> 更高扇出。
- 查找路径：从根开始，在每个内节点二分/线性找第一个 `key >= search_key` 的 child。

- 小例子：

```text
Internal node keys:    [10, 20, 30]
Internal children:  [p0, p1, p2, p3]

search 15 -> 10 <= 15 < 20 -> go p1
search 30 -> go p3
search 5  -> go p0
```

- 如果没有内节点分层：
- 扁平数组在磁盘上插入删除 O(N)，不可接受。

---

**叶节点：数据 + 链表**
- 是什么：
- `存 (key, rid) 或 (key, value)，并通过 next_page_id 链接。`

- 为什么链表：
- range scan 找到起始叶后，沿 next 指针顺序读，不必回溯父节点。
- 顺序读预读友好，减少随机 I/O。

- 小例子：

```text
Leaf L1: keys [1,3,5]  next -> L2
Leaf L2: keys [7,9,11] next -> L3
Range [4,10]: 从 L1 找到 5，然后 L1->L2 扫到 9
```

- 如果没有叶子链表：
- 每次找 successor 要回溯树顶，range 代价高。

- 易错点：
- 链表是**叶子之间**的，不是内节点之间。
- next 指针要在 split 时正确维护。

---

**B+Tree 的不变量（入门版）**
- 所有叶子在同一深度。
- 内节点 key 将子树 key 范围分区，左子树 key < 分隔 key（具体规则看实现，bustub 有精确定义）。
- 叶子 key 有序。
- 每个 key 在树中可唯一定位（唯一索引下）。
- 叶子链表按 key 升序连接。

- 违反任何一条：
- 查找可能 miss，range 漏行或多行，树“看起来能跑”但 silently wrong。

---

**和 bustub 的联系（地图）**
- bustub B+Tree 项目核心类：
- `BPlusTree`：对外 GetValue / Insert / Delete / Iterator
- `BPlusTreeInternalPage`：内节点
- `BPlusTreeLeafPage`：叶节点
- `IndexIterator`：叶子链表迭代
- `Context`：记录查找/插入路径上的 page，为 P10 latch 准备

- 你要建立的心智模型：
- `P7 的 page 化哈希 -> P8 的 page 化平衡树 -> P10 的 page 化并发保护`

**常见错误理解**
- `误区 1：B+Tree 节点就是 C++ 里的 new 出来的 struct`
  - 不对，节点是 disk page 上的 layout。

- `误区 2：找到内节点的 key 就等于找到数据`
  - B+Tree 必须落到叶子。

- `误区 3：B+Tree 只适合主键`
  - 任何需要有序访问的 secondary index 也是 B+Tree。

- `误区 4：hash 全面优于 B+Tree`
  - 只对纯等值且无需排序时 hash 可能更简。

---

**今天你必须真正吃透的 4 句话**
- `磁盘索引优化 I/O 次数，B+Tree 用高扇出压低树高。`
- `B+Tree 所有数据在叶子，内节点只导航；叶子链表服务范围扫描。`
- `节点必须对齐 page，这是和内存 BST 的根本差别。`
- `hash 做点查，B+Tree 做有序与范围——P7 和 P8 互补。`
