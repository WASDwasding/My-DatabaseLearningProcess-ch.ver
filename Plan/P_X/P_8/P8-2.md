这一段我们进入 `P8` 的核心机制：B+Tree 怎样查找、插入、分裂、删除、合并与再分配，以及这些操作如何维护“所有叶子同深、key 有序、链表正确”的不变量。**P8-2 开始**

**今天这次的目标**
- 我们现在正式学习 `P8-2`：`B+Tree 核心机制深讲`。
- 这一段你要真正搞懂的，不是背“节点满了就分裂”，而是：
- 查找从根到叶的路径规则，以及为何必须落到叶子。
- 插入分裂怎样向上传播，根分裂如何增加树高。
- 删除不足时 merge 和 redistribute 如何选型，链表如何修复。

**先把上一段和这一段接起来**
- `P8-1` 你已建立：高扇出、page 对齐、内节点导航、叶子存数据+链表。
- 现在要问：`Insert(key, rid)` 逐步修改了哪些 page？`

- 如果你只会静态画树，不会走 split 传播，bustub B+Tree 项目一定在 Delete 或 Iterator 处卡住。

---

**查找 Lookup 路径**
- 是什么：
- `从 root page 开始，在内节点选 child，直到 leaf，再在 leaf 内找 key。`

- 步骤：

```text
1. current = root_page_id
2. while current 是 internal page:
     在 keys 中找 child i（规则：第一个 keys[i] > key 的 i，或实现等价变体）
     current = children[i]
3. 在 leaf 中线性/二分找 key
4. 找到则返回 rid；否则 not found
```

- 小例子：

```text
        [20|40]           <- internal root
       /  |   \
   [5|10] [25|30] [50|60]  <- leaves (简化)
```

- 查 25：root -> 中间 child -> leaf [25|30] -> 命中。

- 为什么必须到叶子：
- B+Tree 规定 record 只在叶子；内节点 hit 不算数。

- 复杂度：
- O(h * log fanout) 比较 + h 次 page read。
- h 通常 2–4，所以极快。

- 不变量：
- 沿路径下走，子树 key 范围不断收窄，不会走岔。

---

**插入 Insert 主路径**
- 是什么：
- `在叶子插入 (key, rid)；若 leaf 满则 split，分裂可能向上传播。`

- 步骤：

```text
1. Lookup 找到目标 leaf L（不提前创建）
2. 若 L 未满 -> 插入有序位置，结束
3. 若 L 满 -> Split L 为 L 和 L_new
   - 一半 key 留 L，一半去 L_new（或 median 上推，看实现）
   - 维护 leaf 链表：L.next 原来是 X，现在 L_new.next = X，L.next = L_new
   - 把新分隔 key 插入父节点
4. 若父满 -> 递归 split internal node
5. 若 root split -> 新 root，树高 +1
```

- bustub 风格叶分裂（典型）：
- 叶节点 `[k0,k1,...,k_{n-1}]` 满（n == max）。
- 新叶存后半，旧叶保前半。
- 父节点插入一个分隔 key（常是新叶的第一个 key 或中间 key，以实现为准）。

- 小例子（max=3，0-based）：
- 叶 [10,20,30] 满，Insert 25：

```text
Split:
  L  = [10, 20]
  L' = [25, 30]
父插入 key 25（若规则是插入新叶最小 key）
```

- 如果没有向上插入父：
- 树无法从 L' 定位，25 和 30 成为孤儿。

---

**叶分裂与链表维护**
- 是什么：
- `split 后必须更新 next_page_id，保证叶子仍按 key 有序链接。`

- 为什么最容易错：
- 大家记得 copy key，忘记 `L.next -> L_new -> old_next`。

- 正确顺序（概念上）：

```text
L_new.next = L.next
L.next = L_new.page_id
```

- 如果没有：
- Iterator 和 range scan 跳过 L' 或形成环。

- 不变量：
- 中序遍历叶子链表 == 中序遍历树 == key 升序。

---

**内节点分裂**
- 是什么：
- `internal page 的 keys/children 也满时，分裂成两个 internal node，中间 key 上推到父。`

- 与叶分裂差别：
- 内节点 split 会**上推**一个 key 到父（不是复制两份）。
- children 数组比 keys 多 1，split 时要仔细划分 child 归属。

- 小例子（简化）：
- 内节点 keys [10,20,30]，children [p0,p1,p2,p3] 满。
- split 后：
  - 左：keys [10,20]，children [p0,p1,p2]
  - 右：keys [30,...]，children [...]
  - 上推 key 30 到父（具体上推哪个看实现）

- 易错点：
- children 划分少一个或多一个，子树覆盖范围出现空洞或重叠。

---

**根分裂与树高增长**
- 是什么：
- `当 root 也满并 split 时，创建新 root，高度 +1。`

- 为什么特殊：
- root 没有父节点，上推的 key 和两个 child 组成新 root。

```text
旧 root R split -> R_left, R_right
新 root: keys [K_up], children [R_left, R_right]
tree height += 1
```

- 如果没有新 root：
- 两个子树失去统一入口，Lookup 失败。

- 这是 B+Tree 唯一增加高度的方式（标准 insert-only 视角）。

---

**删除 Delete 主路径**
- 是什么：
- `从 leaf 删 (key, rid)；若 key 数量低于最小占用，则 merge 或 redistribute。`

- 步骤：

```text
1. Lookup leaf L，删 key
2. 若 L 仍 >= min_keys -> 结束（可能更新父分隔 key）
3. 若 L 过少 -> 试 redistribute（向兄弟借键）
4. 若借不了 -> merge 与兄弟
5. merge 后父少一个 key 一个 child，父也可能 underflow -> 递归
6. 若 root 只剩一个 child -> 降级 root，树高 -1
```

- min_keys 通常：
- `ceil(max_keys / 2) - 1` 或实现定义，bustub 有常量 `LEAF_PAGE_SIZE` 等。

- 为什么 delete 比 insert 难：
- merge 要改链表、合并两叶 key、更新父、可能递归。
- 测试覆盖不足时，delete 路径 bug 远多于 insert。

---

**Redistribute 再分配（借键）**
- 是什么：
- `underflow 的节点从左或右兄弟借一个 key，避免 merge。`

- 叶节点借键（从左兄弟）：

```text
兄弟 L_left: [a,b,c]  (多一个)
当前 L: [x]           (过少)
父分隔 key = k

借后：
  L_left: [a,b]
  L: [c,x] 或 [k,x] 取决于实现是否拉下父 key
  父分隔 key 更新为兄弟与 L 之间的新边界
```

- 为什么先尝试 redistribute 再 merge：
- merge 代价更高，会删父项并可能递归 underflow。
- 借键只局部调整。

- 不变量：
- 借键后兄弟和自己 key 数都在 [min, max] 内。
- 父分隔 key 仍正确划分范围。

---

**Merge 合并**
- 是什么：
- `underflow 节点与兄弟合成一个节点，父删除分隔 key 和 child 指针。`

- 叶 merge 还要注意：
- 链表：`L_prev.next` 应跳过被 merge 的节点，指向合并后的节点。
- 合并 key 数组，释放(empty)被删 page（若项目要求）。

- 小例子：
- L0: [1,2] underflow，L1: [4,5,6] 兄弟
- merge -> [1,2,4,5,6]，删 L1，父少一项

- 如果没有更新链表：
- range scan 断链。

---

**父分隔 key 的更新**
- 是什么：
- `子树最小 key 变化时，父节点中指向该子树的分隔 key 可能要改。`

- 何时发生：
- 删除 leaf 的最小 key。
- redistribute 后边界变化。

- 为什么重要：
- 父分隔 key 错 -> Lookup 走错 child -> 假 not found。

- bustub 里有时在 Insert/Delete 后调用 `UpdateParentKey` 或沿 Context 回溯更新。

---

**Context：路径记录**
- 是什么：
- `Insert/Delete 时保存 root->leaf 路径上的 page id 和 guard。`

- 为什么：
- split/merge 需要知道父是谁。
- P10 latch crabbing 需要在 Context 里记录已 latch 的 page。

```cpp
struct Context {
  page_id_t root_page_id_;
  std::vector<page_id_t> write_set_;  // 或 read_set_
  // page guards...
};
```

- 如果没有 Context：
- split 完找不到父，或重复 Fetch 同一 page。

---

**Iterator 与范围扫描**
- 是什么：
- `从某 key 开始，沿 leaf 链表 ++ 遍历。`

- 实现要点：

```cpp
IndexIterator Begin();           // 最小 key
IndexIterator Begin(key);        // >= key 第一个
IndexIterator End();

// operator++ 若 leaf 内还有下一 key -> ++index
// 否则 leaf = leaf.next，index=0
```

- 为什么依赖 P8-2 的分裂/merge：
- 链表错，Iterator 全错，range index scan  silently wrong。

---

**B+Tree vs 哈希：执行计划视角**
- 优化器选择 Index Scan 时：

```text
Hash Index Scan: 仅 equality
B+Tree Index Scan: equality + range + order by prefix
```

- 例如联合索引 (a,b)：
- `WHERE a=1 AND b>10` 可用 B+Tree 先定 a=1 再扫 b。
- hash 对 composite key 通常只能全键等值。

---

**关键不变量汇总**
- 所有 leaf 深度相同。
- Internal: `children.size() == keys.size() + 1`。
- Leaf keys 严格递增（唯一索引）。
- Leaf 链表顺序 == key 全局顺序。
- 每个 internal key 正确分隔 child 子树范围。
- Root 至少 2 children（非空树），或 0/1 特殊空树。

**Insert/Delete 手推例题**
- 空树，max leaf=2，依次 Insert 10, 20, 5, 6。

```text
Insert 10: leaf [10]
Insert 20: leaf [10,20]
Insert 5:  leaf [5,10,20] 满 -> split
  -> [5,10] | [20], 可能 root 分裂
Insert 6:  落在 [5,10] 叶 -> [5,6,10] 满 -> 再 split...
```

- 建议你纸上画到树高 2，标 next 指针。
- 再 Delete 5,6，观察是否 merge 或借键。

---

**常见错误实现**
- `错误 1`：split 没更新父
- 症状：部分 key 永远 not found。

- `错误 2`：叶 split 没修 next
- 症状：range/iterator 缺数据。

- `错误 3`：内 split children  off-by-one
- 症状：随机 key 走错子树。

- `错误 4`：delete 只删 key 不处理 underflow
- 症状：树仍“能查”，但 key 密度违反不变量，最终 insert fail。

- `错误 5`：root 变空没降级
- 症状：height 不对，或 root 是空叶。

---

**今天你必须真正吃透的 5 句话**
- `Lookup 必到 leaf；Insert 满则叶 split，分隔 key 上推，父满则递归。`
- `叶 split 必须修 next 链表；merge 也必须修链表。`
- `Delete underflow 先 redistribute 再 merge，可能递归到 root 降级。`
- `Context 记录路径，split/merge 和 P10 latch 都依赖它。`
- `B+Tree 正确性 = 结构不变量 + 叶子有序链表。`
