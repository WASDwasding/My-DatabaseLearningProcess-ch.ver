**边界条件清单**
- 下面每条都应该是你的测试用例，不是读后即忘的列表。

**1. 空表首次 Insert**
- 是什么：directory 刚初始化，只有一个桶，global_depth=0 或 1。
- 为什么危险：很多人默认 global_depth>=1，初始化漏写 directory[0]。
- 没有正确处理：第一次 Insert 就 segfault 或写到非法 page。
- 测试：

```cpp
ExtendibleHashTable<int, int> ht(/*header_page_id, bucket_size*/);
ht.Insert(1, 100);
auto result = ht.GetValue(1);
// 必须找到 100
```

**2. 桶满触发 split**
- 是什么：capacity 很小的桶，连续 Insert 直到 split。
- 为什么危险：split 是最复杂路径，off-by-one 就会丢 key。
- 测试：Insert N 个 key，N 等于 capacity、capacity+1、2*capacity。

**3. local_depth == global_depth 时 split**
- 是什么：必须目录翻倍的那次 split。
- 为什么危险：初学者常忘记翻倍，directory 不够长。
- 测试：故意设 bucket_size=1，强制每一步都 split。

**4. 重复 Insert 同一 key**
- 是什么：唯一索引下应 Update 或拒绝；看项目要求。
- bustub 通常：已存在则 Update value。
- 没有处理：size_ 虚高，bitmap 重复占用，Lookup 不确定。

**5. Remove 不存在 key**
- 应返回 false，不能修改结构。

**6. Remove 后再 Insert**
- 槽位应复用，不应无故触发 split。

**7. 删除到空桶**
- 桶 size_=0 但 directory 仍指向它——合法，不要 dereference 空指针。

**8. hash 冲突：不同 key 同桶**
- 必须都能 Lookup 到。

**9. 大 key 或小 bucket_size**
- 测 split 链深度增长，directory 指数变大时的边界。

**10. 并发读写在 P10 前可先单线程全覆盖**
- 先把单线程所有 split 路径测透，再加 latch。

**陷阱 1：global_depth 与 directory 大小不同步**
- 是什么：
- `directory 数组长度 != 2^global_depth`。

- 为什么发生：
- 手动 memcpy 目录时算错大小。
- 从磁盘读回 header 后没校验 global_depth。

- 会怎样：
- idx 越界，写坏别的 page。
- 或者 Lookup 永远 miss。

- 调试：
- 每次修改 global_depth 后 assert：

```cpp
assert(directory.size() == (1 << global_depth));
```

---

**陷阱 2：local_depth 与 directory 指向关系错乱**
- 不变量回顾：
- 若 bucket.local_depth = d，则应有 `2^(global_depth - d)` 个目录项指向它。

- 违反时会怎样：
- 某些 hash 前缀找不到 key。
- split 后旧 key 漂移到错误桶。

- 调试方法：
- 写 `VerifyIntegrity()`：

```cpp
for each bucket B:
  count = number of directory entries pointing to B
  assert(count == 1 << (global_depth - B.local_depth));
```

- 每次 Insert/Remove 后在 debug 模式调用。

---

**陷阱 3：split 后没有重新 Insert**
- 是什么：
- split 完成后，触发 split 的那条 key 还没写入任何桶。

- 为什么易忘：
- 代码结构上 split 在 helper 函数里，主流程直接 return success。

- 正确模式：

```cpp
if (bucket->Insert(key, value)) return true;
Split(bucket);
return Insert(key, value);  // 递归或循环重试
```

- 测试：
- 记录每次 split 前后的 key 集合，assert 全集仍可 GetValue。

---

**陷阱 4：bitmap 与 keys 数组不一致**
- 是什么：
- SetOccupied 写了，keys_ 没写；或 Remove 清 key 没 ClearOccupied。

- 会怎样：
- Lookup 扫到 garbage key。
- IsFull 误判，频繁 split。

- 最小修复纪律：
- 所有修改槽位必须走 `InsertSlot` / `RemoveSlot` 两个封装函数，禁止散落裸写。

---

**陷阱 5：把内存哈希思维带进 page 版**
- 错误写法：

```cpp
std::unordered_map<int, page_id_t> dir;  // 进程内 map 当目录
```

- 为什么不行：
- 重启后 map 清空，索引全丢。
- 无法和 buffer pool 集成。

- 正确写法：
- directory 存在 HashTableDirectoryPage 里，通过 page_id 访问。

**bustub 映射：从理论到类名**
- 你读 bustub 代码时，建议按这张表对照：

```text
概念              bustub 典型位置
------------------------------------------
目录页            container/hash/hash_table_directory_page.h
桶页              container/hash/hash_table_bucket_page.h
对外接口          container/hash/extendible_hash_table.h
header page       存 directory page id
bucket page       存 key/value + bitmap + local_depth
Hash 函数         Hasher 模板参数
```

**ExtendibleHashTable 对外 API**
- `Insert(key, value)`
- `GetValue(key, &result)`
- `Remove(key)`

- 内部典型 helper：
- `GetBucketIndex(key)`
- `FetchDirectoryPage()` / `FetchBucketPage(page_id)`
- `Split(bucket_page_id)`
- `UpdateDirectoryMapping(bucket_idx, old_id, new_id, new_local_depth)`

**HashTableDirectoryPage**
- 存：
- `global_depth_`
- `bucket_page_ids_[]` 数组

- 你要关心的方法：
- `GetGlobalDepth()` / `IncrGlobalDepth()`
- `GetBucketPageId(idx)` / `SetBucketPageId(idx, page_id)`

**HashTableBucketPage**
- 存：
- `local_depth_`
- `size_`, `capacity_`
- `bitmap_`, `keys_[]`, `values_[]`

- 你要关心的方法：
- `Insert(key, value)` -> bool
- `Remove(key)` -> bool
- `IsFull()` / `IsEmpty()`
- `GetLocalDepth()` / `SetLocalDepth(d)`

**最小实现路线**

**对应 Code 目录**
- 这一段如果要动手实现，代码统一放在 `Code/p7_hash_index/`。
- 这一课在 `Code/` 里的主题是：`extendible hashing 与桶/目录页实验`。
- 建议起手顺序：先做单线程 extendible hash，再补目录扩容和分裂。

- 不要一上来就写 page 版。按 3 步走，每一步可验收。

**阶段 1：纯内存 extendible hash**
- 目标：只实现 key->int value，directory 用 `vector<int*>` 指到 bucket 结构。
- 只验证 split 逻辑和 global/local depth。
- 伪结构：

```cpp
struct MemBucket {
  int local_depth;
  vector<pair<int,int>> entries;
  int capacity;
};

class MemExtendibleHash {
  int global_depth;
  vector<MemBucket*> directory;
  bool Insert(int key, int val);
};
```

- 验收：
- bucket_size=2，Insert 1..100 都能 Get。
- VerifyIntegrity 通过。

**阶段 2：桶改成 page layout，目录仍可在内存**
- 目标：把 MemBucket 换成 HashTableBucketPage 序列化格式。
- 用单块 char buffer 模拟 page：

```cpp
char page_data[PAGE_SIZE];
auto *bucket = reinterpret_cast<HashTableBucketPage<Key,Value,KeyComparator>*>(page_data);
```

- 验收：
- Insert/Remove 后 page 内 bitmap 正确。
- 手动 corrupt bitmap 时测试能 fail。

**阶段 3：目录也 page 化 + buffer pool**
- 目标：完整 bustub 项目形态。
- header page -> directory page -> bucket pages。
- 验收：
- 重启后（若项目要求持久化）或至少 buffer pool 驱逐后再 Fetch 仍正确。

**调试策略**
- 当测试 fail 时，按这个顺序查，不要瞎改。

**Step 1：打印三元组**
- 每次 Insert/Remove 后打印：

```text
global_depth=?
directory=[page_ids...]
each bucket: (page_id, local_depth, size, keys...)
```

- 人眼先看 invariant 3 和 5 是否成立。

**Step 2：缩小 bucket_size**
- capacity=1 时，每次 Insert 几乎都 split，能快速暴露 split bug。

**Step 3：固定 hash 便于手推**
- 测试里用 consecutive int key，配合 mock hash：

```cpp
// 仅测试用
Hash(key) = key;  // 低几位就是 key 本身
```

- 这样 directory 变化可手算。

**Step 4：split 前后 key 集合 diff**
- 维护 `std::set<Key> all_keys`。
- split 后 foreach k in all_keys: assert GetValue(k) ok。

**Step 5：AddressSanitizer / 越界**
- directory idx 越界、bucket slot 越界是常见 crash 源。

**推荐测试用例设计**
- 测试 1：`InsertLookupSequential`
- Insert 0..999，逐个 GetValue。

- 测试 2：`SplitStressSmallBucket`
- bucket_size=1，Insert 0..20。

- 测试 3：`RemoveAndReinsert`
- Insert 1,2,3；Remove 2；Insert 4；检查 1,3,4 都在。

- 测试 4：`UpdateExistingKey`
- Insert (k,v1), Insert (k,v2)，Get 必须 v2，size 不增。

- 测试 5：`DirectoryDoubling`
- 监控 global_depth 增长，在 depth 从 1->2 时 snapshot directory。

- 测试 6：`Randomized`
- 随机 Insert/Remove/Get，和小型 std::map 对拍。

```cpp
std::map<Key, Value> ref;
// 每个操作同时更新 ht 和 ref，最后比较
```

- 对拍是抓 bug 核武器，尤其 split 边界。

**与 aggregation / hash join 的实现对照**
- 在 bustub 执行器里，HashJoin 和 Aggregation 也用到哈希表。
- 你可以对照理解，但别混用代码：

```text
ExtendibleHashTable     -> storage/index extendible_hash_table.cpp
HashJoinExecutor        -> execution/hash_join_executor.cpp
AggregationExecutor     -> execution/aggregation_executor.cpp
```

- HashJoin 的 HT：

```cpp
// 典型：unordered_map<JoinKey, vector<RID>> 或 custom hash table
join_hash_table_.Insert(key, rid);
```

- 区别总结：
- Join/Agg：build phase 建表，probe phase 查表，query 结束释放。
- Index：每次 DML 都可能改目录和桶，生命周期跟表一样长。

- 对你写 extendible hash 的启发：
- Join 的 hash 表可以 rehash 整个 table。
- Index 必须 split 单个桶，保留其他桶不动。

---

**并发预告（为 P10 铺垫）**
- 单线程正确是前提。并发时额外陷阱：

- 读线程 Lookup 时，写线程正在 split：
  - 可能看到旧 directory 或新 directory，都必须能查到 key。
  - 通常需要 latch 目录页，或乐观读 + 验证。

- 两个线程同时 Insert 导致同一桶 double split：
  - 必须互斥 split 操作。

- 这里不展开 crabbing，但你要在 `P7` 就记住：
- `split 是多页原子性难题，没有 latch 不要开多线程测。`

---

**崩溃一致性（了解即可）**
- bustub 基础项目可能不强制 WAL 保护 hash index。
- 但工业数据库会要求：
- 分裂前先 WAL 记录新桶分配和 directory 变更。
- 或使用 careful ordering：先写新桶，再原子更新 directory。

- 如果没有 crash safety：
- 重启后 index 可能指向不存在 page。
- 这超出 bustub 基础范围，但面试常问“若 crash 会怎样”。

**关键不变量（调试版）**
- 写代码时把这些 assert 加成 debug helper：

```cpp
void AssertHashTableOk() {
  auto d = GetDirectory();
  assert(d->Size() == (1 << d->GetGlobalDepth()));
  for (int i = 0; i < d->Size(); i++) {
    assert(d->GetBucketPageId(i) != INVALID_PAGE_ID);
  }
  // 统计每个 bucket 被指向次数
  std::unordered_map<page_id_t, int> ref_count;
  for (int i = 0; i < d->Size(); i++) {
    ref_count[d->GetBucketPageId(i)]++;
  }
  for (auto [pid, cnt] : ref_count) {
    auto b = FetchBucket(pid);
    int expect = 1 << (d->GetGlobalDepth() - b->GetLocalDepth());
    assert(cnt == expect);
  }
}
```

**常见卡点**
- `卡点 1`：能 Insert 少量 key，上千就 miss
  - 多半 split 搬 entry 或 directory 更新错。

- `卡点 2`：Remove 后 Insert 失败
  - bitmap 没释放或 IsFull 实现错。

- `卡点 3`：Gradescope 超时
  - 递归 Insert 无界、split 死循环——检查 local_depth 是否严格递增。

- `卡点 4`：本地过、提交挂
  - 没测 bucket_size=1 和小 global_depth 边界。
