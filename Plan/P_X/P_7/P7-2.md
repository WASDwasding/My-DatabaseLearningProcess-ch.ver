这一段我们正式进入 `P7` 的核心机制：extendible hashing 怎样在磁盘页上完成 Insert、Lookup、Remove，以及目录翻倍和桶分裂到底怎么维护 global_depth 与 local_depth。**P7-2 开始**

**今天这次的目标**
- 我们现在正式学习 `P7-2`：`extendible hashing 的核心机制深讲`。
- 这一段你要真正搞懂的，不是背“桶满就分裂”五个字，而是：
- Insert 和 Lookup 各自走哪条路径，在哪一步可能触发目录翻倍。
- 分裂后旧 entry 怎样按 hash 位重新分配，为什么不会丢 key。
- 桶页里的槽位、bitmap、local_depth 怎样一起维护不变量。

**先把上一段和这一段接起来**
- `P7-1` 你已经建立了：
- 目录是 `hash 前缀 -> bucket page` 的数组。
- global_depth 决定目录大小，local_depth 描述桶的分裂阶段。
- hash index 擅长等值，不擅长范围。
- 若英文词不熟，先回 `P7-1` 的「本课英文名词速查」。

**本节新增 / 加重名词**
| 英文 | 意思 |
|------|------|
| Insert / Lookup / Remove | 插入 / 查找 / 删除 |
| Split | 桶分裂：满桶拆成两桶并重分 entry |
| Directory doubling | 目录翻倍：`global_depth++`，目录长度 ×2 |
| low bits / hash prefix | 取 hash 低位（或约定位）当目录下标 |
| bitmap / occupied slot | 槽位占用标记 |
| local_depth++ | 该桶区分粒度 +1，常与 split 一起发生 |
| retry Insert | 分裂后重新尝试插入（可能落入新桶） |

**先给你一张 Insert 总流程图**
- 一次 Insert `(key, rid)` 的主路径可以概括成：

```text
1. hash(key) -> 得到完整 hash 值 H
2. 取 H 的后 global_depth 位 -> 目录索引 idx
3. directory[idx] -> 找到 bucket page B
4. 若 B 还有空槽 -> 写入 (key, rid)，结束
5. 若 B 已满 -> 触发 split：
   5a. 若 B.local_depth == global_depth -> 目录翻倍
   5b. B.local_depth += 1
   5c. 创建新桶 B'
   5d. 重新分配 B 和 B' 中的 entry（按新的 hash 位）
   5e. 更新目录项指向
6. 重新尝试插入 key（可能落入 B 或 B'）
```

- 你要抓住：
- `Lookup 只读前 3 步；Insert 在第 4 步之后才可能进入分裂子流程。`

---

**Lookup 路径深讲**
- 是什么：
- `给定 key，找到对应 rid 或判定不存在。`

- 为什么必须先讲 Lookup：
- Lookup 是只读路径，没有分裂副作用，最容易用来验证你的结构理解是否正确。

- 步骤：

```text
H = Hash(key)
idx = low_bits(H, global_depth)
bucket_page_id = directory[idx]
在 bucket_page 内扫描/探测，比较 key
```

- 小例子：

```text
global_depth = 2
Hash(42) = ...011010
取低 2 位 -> 10 -> idx = 2
directory[2] -> bucket page 5
在 page 5 里找 key=42
```

- 如果没有目录，直接 `% num_buckets`：
- 静态哈希可以工作，但扩容时必须 rehash 全部 entry。
- extendible hashing 用目录保留“只局部分裂”的能力。

- 不变量：
- 对任意 key，它一定位于 `directory[low_bits(H, global_depth)]` 指向的桶里。
- 桶内若存在该 key，则 rid 必须正确。

- 易错点：
- 取 hash 位时必须和实现约定一致：低位还是高位、是否包含符号扩展。
- bustub 里通常取低位，且位数随 global_depth 增长而增加。

---

**桶页内部布局**
- 是什么：
- `一个 page 上的定长槽位数组 + 元数据 + 可选 bitmap。`

- 为什么用定长槽位：
- page 大小固定，必须能精确计算最多几个 entry。
- 定长槽位让 rid 定位、bitmap 管理都更简单。

- 典型 bustub 风格布局：

```text
Bucket Page:
  page_id
  local_depth
  size (当前 entry 数)
  capacity (最大槽位数)
  bitmap[]        // 哪些槽位占用
  keys[]
  values[]        // 通常是 rid 或 value
```

- 如果没有 bitmap：
- 删除后你不知道哪些槽位可复用，Insert 可能误判“桶满”。
- 或者把空槽位当成有效 entry，Lookup 返回脏数据。

- 小例子 C++ 伪代码：

```cpp
bool BucketPage::Insert(key_t key, value_t value) {
  if (IsFull()) return false;
  size_t slot = FindEmptySlot();
  keys_[slot] = key;
  values_[slot] = value;
  SetOccupied(slot);
  size_++;
  return true;
}
```

- 为什么 Insert 返回 false 而不是直接 split：
- 分层设计：桶页只负责“我能不能塞下”，split 策略由上层 ExtendibleHashTable 决定。

---

**桶满：什么时候 split**
- 是什么：
- `当前桶所有槽位都占用，还要插入新 entry。`

- 为什么不能链到 overflow page 就完事：
- 教学项目里 extendible hashing 的重点就是 split 协议。
- 工业系统有时用 overflow，但分裂思想仍是理解动态哈希的关键。

- 触发条件：

```text
bucket.IsFull() == true
且上层决定不丢弃/不扩容到其他结构
=> 进入 SplitBucket(bucket)
```

- 如果没有 split：
- 桶内冲突链无限增长，查找退化。
- 或者 Insert 直接失败，索引无法继续增长。

---

**Split 的核心：按多出来的那一位 hash 分桶**
- 这是整节课最核心的一段。

- 假设桶 B 的 local_depth = d。
- split 后：
- B.local_depth 变成 d+1
- 新桶 B'.local_depth 也是 d+1
- 原来在 B 里的每个 entry，根据 hash 的第 d 位（从低位数）决定留在 B 还是去 B'

- 小例子：

```text
split 前：
  B.local_depth = 1
  B 里有 keys: k1(hash ...0), k2(hash ...0), k3(hash ...1)

split 后：
  B.local_depth = 2
  B' 新桶 local_depth = 2
  k1, k2 -> 第 1 位是 0 -> 留 B
  k3     -> 第 1 位是 1 -> 去 B'
```

- 为什么用“第 d 位”：
- local_depth = d 表示这个桶之前只区分了 hash 的低 d-1 位。
- 再分裂一次，就要多区分一位，也就是第 d 位（0-based 从低位算）。

- 不变量：
- split 后，B 和 B' 中 entry 总数 = split 前 B 中 entry 数。
- 任意 key 仍能通过更新后的 directory 被找到。

- 易错点：
- 分裂后只移动“该走”的 entry，不能把整个桶复制两份。
- 如果 B.local_depth 已经等于 global_depth，分裂前先目录翻倍——否则 directory 没有足够位来区分 B 和 B'。

---

**目录翻倍 Directory Doubling**
- 是什么：
- `global_depth += 1，目录大小变为原来的 2 倍，每个旧目录项复制成两个。`

- 为什么需要：
- 当桶 B 的 local_depth == global_depth 时，目录已经用尽全部 hash 位来索引。
- 此时 B 还要 split，就必须再多一位 hash 来区分 B 和 B'。
- 所以目录容量先翻倍。

- 步骤：

```text
old_global = g
new_global = g + 1
new_directory_size = 2^(g+1)

for i in 0 .. 2^g - 1:
  new_directory[2*i]   = old_directory[i]
  new_directory[2*i+1] = old_directory[i]

global_depth = new_global
```

- 小例子：

```text
split 前 global_depth=1, directory=[B0, B1]
B0 满且 local_depth=1，需要 split
=> 目录翻倍
global_depth=2, directory=[B0, B0, B1, B1]  // 先复制
再执行 B0 split，按新位更新部分目录项指向新桶
```

- 如果没有目录翻倍：
- B 和 B' 无法被不同 hash 前缀区分，Lookup 会找错桶。

- 性能直觉：
- 目录翻倍是 O(目录大小) 操作，但发生频率远低于普通 Insert。
- 均摊后仍然可接受。

---

**Split 完成后如何更新目录项**
- 是什么：
- `所有仍指向旧桶 B、且其 hash 前缀对应新位的目录项，要改指向 B 或 B'。`

- 规则（典型实现）：
- 对 directory 中每个指向 B 的索引 idx：
  - 看 idx 的第 (local_depth-1) 位（刚增加的那位）
  - 0 -> 仍指向 B
  - 1 -> 改指向 B'

- 为什么只更新“指向 B 的项”：
- 其他桶的目录项不受这次 split 影响。

- 完成后：
- 重新计算要插入 key 的 directory idx
- 插入对应桶

---

**Remove 与 Delete 后再 Insert**
- 是什么：
- `删除 entry 后，桶可能变空，但 extendible hashing 通常不会立即 merge。`

- 为什么很多实现不做 merge：
- merge 比 split 更复杂，要判断兄弟桶能否合并、目录能否缩小。
- bustub 项目往往只要求 Remove 正确，不要求 merge。

- 没有 tombstone 处理会怎样：
- 删除后槽位状态不明，Insert 可能失败或重复。
- 正确做法：bitmap 标记空槽，size_--。

- 删除后再插入同一个 key：
- 必须走完整 Lookup + Insert 路径。
- 如果桶在删除后仍满，Insert 新 key 仍可能触发 split——测试时要覆盖这种序列。

---

**Insert 全路径手推例题**
- 假设一开始：
- global_depth = 1
- directory = [B0, B0]（只有一个桶，local_depth=1）
- B0 capacity = 2，已有 (k1, r1), (k2, r2)

- 现在 Insert (k3, r3)：

```text
1. idx = low_bits(H(k3), 1) -> 0 或 1 都行，都指向 B0
2. B0 已满 -> split
3. B0.local_depth(1) == global_depth(1) -> 目录翻倍
   global_depth=2, directory=[B0,B0,B0,B0]
4. split B0 -> B0', 按 hash 第 1 位分配 k1,k2,k3
5. 更新 directory 中指向 B0 的项
6. 插入 k3 到正确桶
```

- 这道题建议你纸上画 3 次：
- 初始态
- 目录翻倍后、split 前
- split 并插入完成后

- 如果你能手推无误，bustub 的 split 测试就不容易 panic。

**碰撞处理与线性探测**
- 在单个桶页内，常见策略：

**1. 线性探测**
- 槽位 i 被占，就试 i+1, i+2...
- 优点：cache 友好，实现简单
- 缺点：聚集现象，删除要 tombstone

**2. 只存一组 array + bitmap**
- Insert 找第一个空槽
- Lookup 扫描全部 occupied 槽位比较 key
- bustub bucket page 常见这种

- 为什么桶内还要处理碰撞：
- 即使两个 key hash 到同一桶，它们也不能占同一槽位。
- split 只能减少“桶级”冲突，不能消灭“槽位级”同 key 重复。

- 不变量：
- 同一桶内 key 唯一（唯一索引）。
- occupied 槽位数 == size_。

---

**Hash 函数在数据库里的要求**
- 是什么：
- `把变长或定长 key 映射成定长 hash 值。`

- 为什么重要：
- 分布不均会导致某些桶频繁 split，成为热点。
- 函数太慢会让每次 Insert/Lookup 都吃亏。

- 常见选择：
- 整型 key：可直接用或混合位
- 字符串 key：类似 std::hash 或 Murmur/CityHash 简化版

- 易错点：
- 不要用 `key % prime` 直接当目录索引而不保留完整 hash——split 需要更多位。
- 正确模式：`H = Hash(key)`，再 `low_bits(H, global_depth)`。

---

**页布局与 buffer pool 的交互**
- 是什么：
- `每次访问 directory 或 bucket 都要通过 buffer pool 拿 page。`

- 为什么这影响设计：
- 目录页是全局热点，频繁读写。
- 分裂时可能同时修改 directory page 和两个 bucket page。

- 典型访问顺序（Insert）：

```cpp
auto dir_guard = buffer_pool.FetchPageWrite(directory_page_id_);
auto bucket_guard = buffer_pool.FetchPageWrite(bucket_page_id);
// ... split 时还要 Fetch 新桶页、可能写回目录
```

- 如果没有 page guard：
- 分裂到一半另一个线程读到半更新目录，结构损坏。

- `P10` 会专门讲 latch；这里你要知道：
- `split 是多页写操作，必须有清晰的加锁/latch 顺序。`

---

**和 aggregation / hash join 的内存哈希对比**
- 相同点：
- 都是 `hash(key) -> bucket -> entry`
- 都要处理碰撞

- 不同点：

```text
                Hash Index          Hash Join / Agg
生命周期         持久化               查询结束即销毁
存储单位         page                 内存 hash table
扩容             split + 目录翻倍      rehash 或新分区
正确性要求       跨 crash 仍正确      仅本次查询正确
value 类型       rid                  聚合状态 / join buffer
```

- 为什么 hash join 可以 rehash 整张表：
- 内存里 rehash 代价相对可控，且数据是临时的。
- 磁盘索引要尽量避免“全体重建”。

---

**关键不变量汇总**
- `不变量 1`：目录长度 = `2^global_depth`。
- `不变量 2`：每个 directory[i] 指向合法 bucket page。
- `不变量 3`：对 key，设 `idx = low_bits(H(key), global_depth)`，则 key 必在 directory[idx] 所指桶中。
- `不变量 4`：bucket.local_depth <= global_depth。
- `不变量 5`：若 directory 中有 k 个项指向桶 B，则 `k = 2^(global_depth - B.local_depth)`。
- `不变量 6`：bucket 内 occupied 槽位数 = size_，且 key 不重复。

- 调试时任何异常现象，都先问：上面哪条被破坏了。

---

**常见错误实现**
- `错误 1`：split 时忘记目录翻倍
- 症状：local_depth == global_depth 时仍 split，directory 无法区分两桶。

- `错误 2`：只增加 local_depth 不搬 entry
- 症状：key 丢失或 Lookup 失败。

- `错误 3`：Insert 失败后没重试
- 症状：split 完成后新 key 没写进去，测试偶发 missing。

- `错误 4`：Remove 不更新 bitmap
- 症状：桶永远“满”，无意义 split 或 Insert 失败。

- `错误 5`：hash 位取错（高位/低位混淆）
- 症状：小数据量通过，大数据量 random fail。

---

**今天你必须真正吃透的 5 句话**
- `Lookup = hash -> 目录索引 -> 桶内扫描；Insert 在桶满时走 split。`
- `split 按 hash 的新一位把 entry 分到旧桶和新桶，entry 总数不变。`
- `local_depth == global_depth 时 split 前先目录翻倍。`
- `桶页用 bitmap 管槽位，Remove 必须释放槽位。`
- `hash index 的分裂是局部磁盘操作，不是全体 rehash。`
