**本课英文名词速查（先看这一段再往下读）**
- P7 英文词很多。下面按“中文意思 → 它在系统里干什么”解释；后文再出现时你可随时回查。

| 英文 | 中文意思 | 一句话 |
|------|----------|--------|
| hash index | 哈希索引 | 用哈希把 key 映射到桶，加速等值查找 |
| hash table | 哈希表 | 更泛的结构名；数据库里常指磁盘友好的索引实现 |
| hash function | 哈希函数 | 把 key 打成整数/位串，用来选桶 |
| hash value / digest | 哈希值 | 哈希函数的输出 |
| index entry | 索引项 | 通常是 `(key, RID)`，不是整行数据 |
| RID | 记录标识 | `(page_id, slot_num)`，指向堆表里的一行 |
| heap file | 堆文件 / 堆表 | 表数据本体；索引通过 RID 找回整行 |
| Directory | 目录 | 数组：用 hash 的若干位当下标，指向桶页 |
| Bucket / Bucket Page | 桶 / 桶页 | 真正存放 index entry 的 page |
| Global Depth | 全局深度 | 目录当前用 hash 的多少位做索引；目录长度=`2^global_depth` |
| Local Depth | 局部深度 | 某个桶分裂到什么粒度；可小于 global_depth |
| Static Hashing | 静态哈希 | 桶数固定，常用 `hash % N` |
| Dynamic Hashing | 动态哈希 | 桶数可增长，热点桶可分裂 |
| Extendible Hashing | 可扩展哈希 | 动态哈希的一种：目录 + 局部分裂，必要时目录翻倍 |
| Linear Hashing | 线性哈希 | 另一种动态哈希（本课次要，知道名字即可） |
| Split | 分裂 | 桶满了拆成两个桶，并按新的 hash 位重分 entry |
| Directory doubling | 目录翻倍 | global_depth+1，目录长度翻倍 |
| Rehash | 再哈希 | 用新规则重算落点；全体 rehash 很贵，extendible 尽量避免 |
| Collision | 冲突 | 不同 key 落到同一桶（或争同一槽） |
| Overflow | 溢出 | 桶装不下；静态哈希常靠 overflow page/链，extendible 更倾向 split |
| Overflow page / chain | 溢出页 / 溢出链 | 桶满后挂出去的额外页（实现相关） |
| Load factor | 装载因子 | 已用槽位 / 总容量；太高则冲突变多 |
| Probe | 探测 | 在桶内找空槽或找 key（线性探测等） |
| Bitmap (occupied) | 占用位图 | 标记桶内哪些槽有有效 entry |
| Slot / capacity | 槽位 / 容量 | 桶页里能放多少个 entry |
| Latch | 闩锁 | page/结构级短锁，保护并发访问（细节在 P10） |
| PageGuard | 页守卫 | RAII 管 pin/unpin，防忘 unpin |
| Hash Join | 哈希连接 | 执行器里用内存哈希做 join；生命周期通常短于持久索引 |
| Aggregation hash table | 聚合哈希表 | 执行器为 GROUP BY 等建的内存表 |
| Point / Equality lookup | 点查 / 等值查找 | `WHERE key = ?`，hash index 主场 |
| Range scan | 范围扫描 | `BETWEEN` / `<` / `>`，hash 不保序，通常不适合 |
| Seq Scan | 顺序扫描 | 全表扫，没有合适索引时的兜底 |
| StressTest | 压力测试 | 大量随机 Insert/Get/Remove 抓 split bug |

- 最容易混的几组：
  - **global_depth vs local_depth**：前者管目录大小；后者管单个桶有多“细”。
  - **hash index vs `std::unordered_map`**：前者要 page/持久化/扩容协议；后者是进程内内存容器。
  - **hash index vs hash join 表**：前者持久、服务点查；后者常是查询执行期间的临时内存结构。
  - **split vs 全体 rehash**：extendible hashing 尽量只分裂一个桶，必要时才目录翻倍。

**先给你一张总图**
- 数据库哈希索引在系统里大致长这样：

```text
SQL: SELECT * FROM T WHERE id = 42
        |
        v
   Index Scan (Hash)
        |
        v
   Hash Index: key -> rid
        |
        v
   Buffer Pool -> Bucket Page(s)
        |
        v
   Heap File: 按 rid 取 tuple
```

- 这条链里每一层职责不同：
- 查询层：决定走 hash index 还是 seq scan。
- 索引层：把 key 映射到 rid。
- 存储层：rid 再定位到具体 page + slot。

- `P7` 的核心就在中间这层：
- `key 怎样通过哈希函数落到某个桶页，桶页里又怎样存 index entry。`

**问题定义**
- 什么是“数据库哈希表”？
- 初学者容易把它理解成“C++ 里的哈希 map”。
- 更准确地说：
- `数据库哈希表是一种按 key 组织 index entry 的磁盘友好数据结构，通常由目录、桶页、哈希函数和扩容协议共同组成。`

- 注意这里有 4 个关键词：
- `index entry`：存的是 `(key, rid)` 或 `(key, value_ptr)`，不是整行数据本身。
- `磁盘友好`：基本分配单位是 page，不是 malloc 出来的节点。
- `目录`：负责把 hash 前缀映射到具体桶。
- `扩容协议`：数据变多时要能分裂，而不是一次性重建整张表。

- 如果没有这层抽象，会发生什么？
- 等值查找只能 seq scan，大表上 `WHERE id = ?` 代价极高。
- 即使用内存哈希做 hash join / aggregation，也和持久化索引完全是两回事。

**为什么数据库不能直接用标准容器**
- 先从第一性原理来问：
- 既然 C++ 已经有 `unordered_map`，为什么还要自己写？

- 第一个原因：`持久化`
- 标准容器活在进程内存里，进程退出就没了。
- 数据库索引必须能在重启后仍然有效。
- 这意味着目录、桶、槽位状态都要能写进 page，并能从磁盘读回。

- 第二个原因：`page 粒度`
- 数据库 I/O 的基本单位是 page，通常是 4KB 或 8KB。
- 哈希桶不是“一个链表节点”，而是“一页或若干页上的槽位数组 + 元数据”。
- 你要考虑：
  - 一页能放多少个 entry
  - 槽位满了怎么办
  - 删除后槽位如何标记为空、如何复用

- 第三个原因：`并发`
- 多个线程可能同时查、插、删同一个桶。
- 标准容器在单进程内可用，但数据库还要和 buffer pool latch、事务语义、后续 `P10` 的 latch crabbing 配合。

- 第四个原因：`崩溃一致性`
- 分裂目录、分裂桶时如果中途 crash，重启后索引不能坏。
- 这通常要配合 WAL 或 careful write ordering——虽然 bustub 项目里有时简化了，但设计思想不能丢。

- 所以你要记住：
- `数据库哈希表首先是索引结构，其次才是哈希表；它的约束来自 page、并发和持久化，而不是 STL 接口。`

**静态哈希 vs 动态哈希**
- 这是 `P7` 的第一组核心对比。

**1. 静态哈希 Static Hashing**
- 是什么：
- `桶数量固定，hash(key) % num_buckets 决定落桶。`

- 为什么曾经有用：
- 实现简单，目录结构甚至可以省略。
- 适合数据量可预估、很少扩容的场景。

- 没有动态机制会怎样：
- 数据量超过设计值后，冲突链变长，性能从 O(1) 退化成 O(n)。
- 或者你预留太多空桶，空间浪费严重。

- 小例子：

```text
num_buckets = 4
h(key) % 4 -> bucket 0/1/2/3
```

- 如果 bucket 2 里塞了 10000 个 entry，而 bucket 0 几乎是空的，这就是静态哈希的典型痛点：
- `冲突分布不均，且无法通过分裂单个热点桶缓解。`

**2. 动态哈希 Dynamic Hashing**
- 是什么：
- `桶数可以增长，冲突严重时就分裂桶，而不是整张表重建。`

- 为什么数据库更偏爱它：
- 数据量随时间增长，索引不能一次性定死容量。
- 分裂是局部操作，比“全体 rehash”更适合磁盘环境。

- extendible hashing 是动态哈希里 bustub 项目的重点：
- 用目录数组把 hash 前缀映射到桶。
- 某个桶满了，只分裂这个桶，必要时再扩大目录。

- 你要建立的第一判断：
- `静态哈希适合教学入门；extendible hashing 适合理解数据库索引扩容。`

---

**extendible hashing 术语入门**
- 下面 4 个词后面会一直出现，现在就要分清。

**1. 目录 Directory**
- 是什么：
- `一个数组，目录项 i 保存“指向某个桶页的指针/页号”。`

- 为什么需要它：
- hash 值可能很长，但目录大小有限。
- 我们只取 hash 的前 `global_depth` 位来索引目录。

- 小例子：

```text
global_depth = 2
directory size = 2^2 = 4

hash(key) = ...b1 b0   (取最后 2 位)
directory[b1 b0] -> bucket page id
```

- 不变量：
- 目录长度始终是 `2^global_depth`。
- 每个目录项必须指向一个合法桶页。

**2. 桶 Bucket**
- 是什么：
- `真正存放 index entry 的页（或页组）。`

- 为什么单独强调“桶”：
- 分裂发生在桶级别，不是整个 hash table 级别。
- 一个桶满了，就分裂成两个桶，并把 entry 按新的 hash 位重新分配。

- 小例子：

```text
Bucket Page:
  local_depth = 2
  [ (k1, rid1), (k2, rid2), ... ]
```

**3. 全局深度 Global Depth**
- 是什么：
- `目录当前用 hash 值的多少位来做索引。`

- 为什么重要：
- global_depth 决定目录大小。
- 当目录项都指向同一个桶、而这个桶又要分裂时，可能需要把目录翻倍。

- 如果没有 global_depth 概念：
- 你无法判断目录何时扩容，也无法解释“为什么两个目录项可以指向同一个桶”。

**4. 局部深度 Local Depth**
- 是什么：
- `某个桶当前区分自己的 entry 时用到了 hash 的后多少位。`

- 为什么和 global_depth 并存：
- 不同桶可以处于不同“分裂阶段”。
- 一个桶 local_depth 小于 global_depth，说明它还没分裂到最细粒度，于是多个目录项会指向它。

- 经典例子：

```text
global_depth = 2
directory = [B0, B0, B1, B1]
```

- 这里 B0 的 local_depth 可能是 1，B1 的 local_depth 也是 1。
- 目录有 4 项，但只有两个物理桶。
- 这就是 extendible hashing 节省空间的诀窍。

- 易错点：
- 不要把 global_depth 理解成“树的深度”。
- 它是“目录索引用了 hash 的几位”，不是 B+Tree 那种节点层级。

**哈希索引适合什么、不适合什么**
- 这部分后面选索引结构时会反复用到。

**适合：等值查找**
- 例如：

```sql
SELECT * FROM users WHERE email = 'alice@example.com';
```

- hash 函数直接定位桶，再在桶内比较 key。
- 期望代价：O(1) 次 page access + 桶内线性扫描。

**不适合：范围查询**
- 例如：

```sql
SELECT * FROM orders WHERE amount BETWEEN 100 AND 200;
```

- 哈希值对 range 没有保序性。
- `100` 和 `200` 的 hash 可能落到完全不相邻的桶。
- 所以 hash index 无法像 B+Tree 那样做 `[low, high]` 顺序扫描。

**不适合：排序输出**
- 例如：

```sql
SELECT * FROM users ORDER BY created_at;
```

- hash index 不提供 key 的全序遍历能力。
- 这类查询要靠 B+Tree 或额外排序。

- 你要记住：
- `hash index 是等值查找加速器，不是通用有序索引。`

---

**碰撞 Collision 在这里指什么**
- 是什么：
- `不同 key 映射到同一个桶，或者桶内槽位冲突。`

- 为什么不可避免：
- hash 是把大 key 空间压到小桶空间，鸽巢原理保证会有碰撞。

- 数据库里怎么处理：
- 桶内用线性探测、链式槽位或 overflow page。
- 桶满则触发 split，而不是无限堆在一个桶里。

- 没有碰撞处理会怎样：
- 两个 key 写进同一槽位，后写覆盖先写，索引 silently corrupt。
- 查找返回错误 rid，读到别人的 tuple。

- 不变量：
- 每个 key 在索引中最多出现一次（唯一索引场景）。
- 每个 `(key, rid)` entry 必须落在正确的桶里，且能被 hash + local_depth 规则找到。

**和 bustub 的联系（先建立地图）**
- bustub 的 extendible hash table 项目，就是把这节课的理论落到代码里。
- 你后面会看到这些组件：
- `HashTableDirectoryPage`：目录页，存 global_depth 和 bucket page array。
- `HashTableBucketPage`：桶页，存 key、value(rid)、槽位 bitmap。
- `ExtendibleHashTable`：对外 Insert / GetValue / Remove 接口。

- 和 aggregation / hash join 的区别：
- aggregation、hash join 里的哈希表通常是内存里的临时结构，查询结束就销毁。
- extendible hash index 是持久化索引，entry 布局、分裂、目录翻倍都要考虑 page。
- 思路相似：都是 `hash -> bucket -> entry`。
- 约束不同：索引要跨查询存活，还要和 buffer pool 协作。

**页布局与并发的直觉（先预告）**
- `P7-2` 会深讲分裂协议；这里先建立边界意识。

- 页布局要回答：
- 目录页多大、能放多少 bucket pointer。
- 桶页多大、能放多少 `(key, rid)`。
- 槽位删除后是 tombstone 还是真正 compaction。

- 并发要回答：
- 查的时候能不能只读 latch 目录页。
- 分裂时其他线程查旧桶还是新桶。
- 目录翻倍是不是原子操作——通常不是，要靠 latch 保护。

- 如果没有这些意识：
- 你写出的 hash index 在单线程测试里能通过，多线程或 crash 后立即坏掉。

**常见错误理解**
- `误区 1：哈希索引可以替代 B+Tree`
- 不对。它只擅长等值，不擅长 range/order。

- `误区 2：global_depth 就是桶的数量`
- 不对。桶数量可以少于目录项数量，多个目录项可以共享一个桶。

- `误区 3：extendible hashing 每次插入都可能翻倍目录`
- 不对。只有“桶满且需要更细粒度区分”时才分裂；目录翻倍是更少见的事件。

- `误区 4：hash join 的哈希表和 hash index 是一回事`
- 不对。前者是查询执行临时结构，后者是存储索引。

---

**今天你必须真正吃透的 4 句话**
- `数据库哈希表是 page 化的 key->rid 索引，不是内存容器。`
- `静态哈希简单但有热点桶问题；extendible hashing 用目录+局部分裂解决动态扩容。`
- `global_depth 管目录索引位数，local_depth 管桶的分裂阶段。`
- `hash index 服务等值查找，不服务范围扫描和排序。`
