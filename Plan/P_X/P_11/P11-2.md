**先给你一张外部排序总图**
- 经典 external sort = `Phase 1: 生成有序 run` + `Phase 2: 多路归并`

```text
输入（无序，可能来自 Scan 或子算子）
        │
        ▼
┌───────────────────┐
│ 读满一个内存块 B   │  ← sort buffer，大小受 work_mem 类参数限制
│ 块内排序           │
│ 写出 run_1 到磁盘  │
└───────────────────┘
        │ 重复直到输入读完
        ▼
磁盘上: run_1, run_2, ..., run_k   （每个 run 内部已有序）
        │
        ▼
┌───────────────────┐
│ k 路归并（merge）  │  ← 内存里维护 k 个 run 的“当前头指针”
│ 输出全局有序流     │
└───────────────────┘
```

- 两个阶段的代价特征不同：
- Phase 1：读一遍输入 + 写一遍 run（约 2 倍数据量 I/O，若只写一次 run）。
- Phase 2：读 run + 写最终输出（归并可能多轮，若 k 太大）。

---

**内存排序：不是“整个表排序”，而是“run 内排序”**
- 什么是内存排序？
- 在数据库语境下，它通常指：`在固定大小的 sort buffer 内，对当前批次 tuple 做完整排序。`

- 实现上，run 内排序常用：
- `std::sort`、quicksort、introsort 等比较排序，O(m log m)，m 为 buffer 内行数。
- 若排序键是整数且范围可控，有时可用计数排序/radix sort——工业系统更常见的是比较排序 + 键编码。

- 排序比较的是什么？
- 不是整行 tuple 的字节memcmp（除非所有键定长且已编码好）。
- 通常是`排序键（sort key）`的多列字典序比较，并携带`原始 tuple 的引用或副本`。

```cpp
// 教学伪代码：sort key 比较
bool Less(const SortEntry &a, const SortEntry &b) {
  for (each key column k in order_by_list) {
    int cmp = Compare(a.key[k], b.key[k], nulls_first_or_last);
    if (cmp != 0) return cmp < 0;  // ASC 为例
  }
  return false;  // 相等时稳定性策略见下
}
```

- 稳定性（stability）：
- SQL 标准对 “相等键的行顺序” 往往不保证；但实现里常保留输入顺序以便可重复测试。
- 若需要稳定，比较相等时要 tie-break（例如保留 input ordinal）。

---

**Phase 1：怎样生成 run**
- 算法步骤（单线程版）：

```text
1. 分配大小为 B 的内存 buffer
2. while (从子算子 Next 出 tuple) {
     若 buffer 满：
       对 buffer 内 tuple 按 key 排序
       顺序写出到临时文件，形成一个 run
       清空 buffer
   }
3. 若 buffer 非空，同样排序并写出最后一个 run
```

- 例子：
- 输入 1000 万行，buffer 一次装 50 万行。
- 大约产生 20 个 run，每个 run 内部 50 万行有序。

- 不变量 `R1`：
- 每个 run 文件内部，按排序键严格有序（含 NULL 规则）。

- 易错点：
- 写出 run 时忘记清空 buffer，导致重复或漏数据。
- sort key 提取与最终输出 schema 不一致（例如只按 dept 排，却丢了 tie 行）。

---

**Phase 2：k 路归并**
- 目标：把 k 个有序 run 合并成一个全局有序流，且不必把 k 个 run 全部读入内存。

- 经典做法：内存里维护一个`大小为 k 的小顶堆（priority queue）`：
- 每个 run 有一个当前读指针。
- 堆顶是 k 个 run “当前头元素”里最小的那个。
- 弹出堆顶输出，从对应 run 再读一条进堆，重复。

```text
初始化：从每个 run 读第一条入堆
while 堆非空:
  pop min -> 输出
  从该 run 再读一条（若有）-> push 入堆
```

- 例子：
- run_1 头：`(dept=1, name='Alice')`
- run_2 头：`(dept=1, name='Bob')`
- run_3 头：`(dept=2, name='Cindy')`
- 堆顶 dept=1, Alice 先出；然后从 run_1 取下一条。

- 不变量 `R2`：
- 任何时候堆顶元素是“所有 run 剩余元素中的全局最小”。

---

**当 run 数量 k 太大：归并也要分层**
- 问题：若 Phase 1 产生 10 000 个 run，你不能同时开 10 000 个文件句柄，也不能在内存里放 10 000 个 buffer。

- 解法：`多轮归并（multi-pass merge）`
- 第一轮：每 M 个 run 归并成一个更大的 run（M 受 `merge width` 限制）。
- 重复直到只剩 1 个 run 或可直接流式输出。

```text
10000 runs --(100-way merge)--> 100 runs --(100-way merge)--> 1 run
```

- 代价：
- 每一轮归并都要读+写临时文件，I/O 次数增加。
- 所以 Phase 1 的 buffer 越大 → run 越少 → 归并轮数越少 → 总 I/O 越低。

- 核心工程权衡：
- `work_mem` 大：少 run、少归并轮数，但占内存、影响并发查询。
- `work_mem` 小：多 run、多轮 merge，磁盘临时文件暴涨。

---

**I/O 代价直觉（不用背公式，但要会估）**
- 外部排序常被概括为 `sort(N)` 的 I/O 与 `2 * passes * N` 量级相关（简化模型）。
- passes 取决于 run 数量和 merge fan-in。

- 你要能口头回答：
- “为什么 ORDER BY 大表时临时磁盘空间暴涨？”
  - 因为 run 文件 + 中间 merge 文件都要写盘。
- “为什么加内存有时比加 CPU 更管用？”
  - 更大 buffer → 更少 run → 更少 merge pass → 更少随机/顺序 I/O。

- CPU 热点在哪：
- run 内排序的比较次数。
- merge 堆操作：每条输出 O(log k)。

**Sort 为什么是阻塞算子**
- 从 Volcano 接口看：

```text
SortExecutor::Init() {
  // Phase 1: 可能要把子算子 ALL 或大部分读入并写 run
  // Phase 2: 建立 merge 堆
}

SortExecutor::Next(&tuple) {
  // 第一次 Next 之前，Init 可能已经完成全部 Phase 1
  // 或至少完成到可开始 merge 的状态
}
```

- 对 latency 的影响：
- 用户/上层算子第一次要结果时，可能要等整个 sort 的 Phase 1 完成。
- 这不是实现“偷懒”，而是`全序`语义要求：在未看到全部元素前，你无法保证某条 tuple 不是全局最小（除非做 top-N 特例）。

- 对 pipeline 的影响：

```text
Filter -> Sort -> Limit 10
```

- Sort 把 pipeline 切成两段：
- Sort 以下（Filter）可以先跑完灌入 Sort。
- Sort 以上（Limit）必须等 Sort 至少能产出第一条（全排序时要等 Phase 1+merge 就绪）。

- 对比流式：

```text
Filter -> Projection -> 客户端
```

- 每 Next 一条，整条链路透传，内存占用小。

---

**部分排序 vs 全排序：top-N 的入口**
- 全排序：输出与输入等 cardinality（除非 DISTINCT key），必须保证任意两条的相对顺序正确。

- top-N（`ORDER BY x LIMIT k`）：
- 若 k 很小，可维护大小为 k 的 heap，扫描一遍输入即可，不必 external sort 全表。
- 内存：O(k)；时间：O(n log k)。
- 这在 `P11-3` 与优化器规则里会细讲；这里先建立联系：
- `top-N 是 Sort 语义在 k << n 时的特化，不必阻塞到全表排序完成。`

- 例子：
- 找 salary 最高的 10 人，1000 万行，k=10。
- 一个 10 元小顶堆（或最大堆视实现而定）即可，不必写出 200 个 run。

- 易错点：
- top-N heap 的 comparator 必须与 ORDER BY 全序一致（含 NULL、DESC）。
- 多列排序时 tie-break 错会导致 “第 10 名”边界行错误。

---

**DISTINCT 与 Sort 的关系**
- `SELECT DISTINCT col FROM T` 的一种经典实现：
- 先按 col 排序，再扫描有序流，只输出 key 变化时的第一行。

- 另一种实现：
- hash table 记录见过的 key（内存够时）。

- 交集：
- 若优化器已经要为 `ORDER BY col` 做 sort，distinct 可能“顺便”在有序流上去重，避免第二个 hash table。
- 若没有 ORDER BY，distinct 更常走 hash。

- 这体现了 `P11-1` 说的：top-N、distinct、group by、order by 在实现上常共享 sort 或 hash 基础设施。

---

**NULL 与排序键编码**
- SQL 里 NULL 比较特殊：`NULL = NULL` 是 unknown，但排序必须给出确定性位置。

- 实现技巧：
- 比较时把 NULL 映射为“负无穷”或“正无穷”，取决于 `NULLS FIRST` 还是 `NULLS LAST`。
- 或在 sort key 里带 `(is_null, value)` 二元组。

- 例子（ASC NULLS LAST）：
- 键值：`5, NULL, 3` → 排序后 `3, 5, NULL`

- 聚合与排序交叉：
- `ORDER BY AVG(salary)` 需要先聚合再排序——执行树里 Aggregate 在 Sort 下面。

**关键不变量（本段）**
- `S1`：每个 run 内 tuple 按排序键有序。
- `S2`：k 路归并输出顺序等价于“把所有 run 拼接后做一次全局 sort”。
- `S3`：merge 过程中每个 run 的头指针单调前进，不会回退或跳过。
- `S4`：临时文件在查询结束或 abort 时必须可回收（资源管理）。
- `S5`：Sort 输出 cardinality = 输入 cardinality（无 DISTINCT 时）。

---

**常见错误理解与 bug 形态**
- “Init 里读子算子，Next 里只读 merge 堆”——结构对，但若 Init 没处理子算子 EOF，会 hang 或丢数据。
- “run 文件可以无序，merge 会修”——错，merge 前提是每个 run 已有序。
- “merge width 越大越好”——过大则内存和文件句柄压力；过小则 pass 数爆炸。
- “Sort 可以和 Limit 任意交换顺序”——错，除非优化器证明 top-N 等价变换安全。
