**先把前面的课和 `P11` 接起来**
- `P1/P2` 告诉你：逻辑上查询是关系代数风格的运算树；`GROUP BY`、`ORDER BY`、`DISTINCT` 都是这层语义。
- 更前面的执行器课（或你读 bustub 代码时）已经见过：`SeqScan`、`Filter`、`NestedLoopJoin` 这类算子，大多是“来一条处理一条”的流式风格。
- 但一碰到排序和聚合，节奏就变了：
- 排序常常必须“先看全（或看够多）再吐第一条”。
- 聚合必须“按组维护状态，组没收齐前不能乱输出”。

- 你可以先记这条分界线：
- `流式算子回答：下一条输入来了，我能不能立刻产出下一条输出？`
- `阻塞算子回答：我还缺多少输入/状态，才能开始或继续产出？`

- 如果 `P11` 没学稳，你后面写 `AggregationExecutor`、做 top-N、调 “GROUP BY 结果少一行” 这类 bug，都会缺少代价和语义上的抓手。

**先给你一张总图**
- 一次典型分析查询，执行树里排序和聚合常出现在这些位置：

```text
SELECT dept, COUNT(*)
FROM Employee
WHERE salary > 50000
GROUP BY dept
ORDER BY COUNT(*) DESC
LIMIT 10;
```

- 逻辑上大致对应：

```text
Limit
  <- Sort (ORDER BY count desc)     ← 可能阻塞
       <- Aggregate (GROUP BY dept) ← 通常阻塞
            <- Filter (salary > 50000)
                 <- SeqScan(Employee)
```

- 三个高层算子，实现上高度相关：
- `GROUP BY`：按 key 分组，维护每组聚合状态。
- `DISTINCT`：可以看成 `GROUP BY key` 但不算聚合函数，或 `GROUP BY` 后只输出 key。
- `ORDER BY`：按排序键全序或部分序排列。
- `LIMIT k` / top-N：有时不必全排序，但依赖对“前 k 名”结构的理解。

- 这一课的核心，不是背 6 个算法名字，而是建立：
- `语义是什么`
- `状态要存什么`
- `内存不够时怎样 spill 到磁盘`
- `优化器为什么有时选 hash agg、有时选 sort agg`

**问题定义：排序算子到底在算什么**
- 什么是排序（Sort）？
- 简单说：`Sort 把一个输入关系（或流）按一个或多个排序键，重排成全序（或所需偏序）的输出。`

- 注意几个细节：
- 输入可能是已无序的 heap scan，也可能是另一算子吐出的流。
- 排序键可以来自列，也可以来自表达式，例如 `ORDER BY salary * 1.1`。
- SQL 的 `ORDER BY` 还涉及 NULL 排序规则（`NULLS FIRST/LAST`），实现里必须显式编码。

- 如果没有 Sort 算子会怎样？
- 很多 SQL 语义无法高效实现：`ORDER BY`、sort-merge join、某些 distinct 实现、窗口函数的分区排序。
- 你只能假设输入“碰巧已有序”，这在真实系统里极少成立。

---

**问题定义：聚合算子到底在算什么**
- 什么是聚合（Aggregation）？
- 简单说：`Aggregation 把多行输入，按分组键压缩成更少的输出行，并在每组上应用聚合函数。`

- 例子：

```sql
SELECT dept, AVG(salary), COUNT(*)
FROM Employee
GROUP BY dept;
```

- 输入可能是 10 万行员工记录。
- 输出可能只有 20 行（20 个部门）。
- 每组维护的状态至少包括：`sum(salary)`、`count(*)`，用于算 AVG。

- 如果没有 Aggregation 算子会怎样？
- `GROUP BY`、`COUNT`、`SUM`、`MAX`、`HAVING` 全部无法在执行层落地。
- 你只能在应用层拉全表自己算——这正是数据库要替你做的事。

---

**为什么排序和聚合是“核心算子”而不是语法糖**
- 从第一性原理看，数据库卖的不只是“存数据”，还有“对大量数据做结构化约”。

- 排序解决的是`顺序`问题：
- 用户要“最大的 10 个”“按时间线浏览”“合并两个已序流”。
- 顺序在磁盘上不是天然存在的；heap 表里的行顺序通常与逻辑顺序无关。

- 聚合解决的是`压缩`问题：
- 用户要“每个部门多少人”“总额是多少”，而不是每一行明细。
- 压缩意味着执行器必须维护`组状态（group state）`，不能来一行吐一行（除非恰好每组只有一行且已分组有序——那是特例）。

- 所以这两类算子的共同点是：
- `都依赖对“尚未见过的全部或足够多输入”的假设。`
- 这正是它们常常阻塞 pipeline 的根源。

---

**阻塞算子 vs 流式算子：必须先建立直觉**
- 什么是 pipeline（流水线）？
- 子算子每产出一条 tuple，父算子就可以立刻处理，内存里通常只驻留少量中间结果。

- 什么是 blocking operator（阻塞算子）？
- 算子在 `Init/Open` 后，第一次 `Next` 可能要等子算子`全部或部分`输入读完，才开始输出。
- 或者算子内部需要先把数据写到临时文件，再第二阶段读回。

- 典型阻塞算子：
- `Sort`（全排序几乎总是阻塞）。
- `Hash Aggregation`（build 阶段读完输入或 spill 完成前，不能输出最终组）。
- `Hash Join` 的 build 侧（下一课详讲，这里先建立联系）。

- 典型流式或近流式算子：
- `SeqScan`、`Filter`、`Projection`：来一条，处理一条。
- `Limit`：在已序输入上可以是流式的；在无序输入上若配合 top-N heap，也可能边读边维护小结构。

- 如果没有“阻塞/流式”这个视角会怎样？
- 你会奇怪：“为什么 Sort 的 Next 第一次调用很慢？”
- 你会在 pipeline 里错误地假设“上游一 Init，下游立刻能 Next 出结果”。
- 调性能时分不清是 CPU 热点还是 I/O 等临时文件。

---

**内存边界：为什么不能总假设“一次性放进内存”**
- 教学环境和生产环境的第一个落差就在这里。

- 假设你要对 1 亿行、每行 200 字节的数据排序：
- 粗算数据量约 20GB。
- 若 sort buffer 只有 256MB，你不可能 `std::sort` 一把梭。

- 数据库的标准答案是`外部排序（external sort）`：
- 分块读入，块内排序，写出`有序 run（顺串）`到磁盘。
- 再多路归并（multi-way merge），得到全局有序输出。

- 聚合同理：
- hash table 若装不下所有 group，必须` spill 分区`到磁盘，再递归或分阶段聚合。
- 这就是为什么 hash agg 和 external sort 在工程上经常一起出现。

- 核心结论：
- `排序/聚合的实现，首先是内存管理问题，其次才是算法细节问题。`

---

**为什么聚合既可以用 hash，也可以用 sort**
- 这是优化器选型里非常经典的一道题。

- Hash Aggregation 思路：
- 扫描输入，对 group key 做 hash，在 hash table 里更新每组的 agg state。
- 适合：group 数量相对可控、内存够或 spill 可接受、不需要输出有序。

- Sort Aggregation 思路：
- 先按 group key 排序，再线性扫描有序流，相同 key 的行归为一组做聚合。
- 适合：group 很多但 sort 已有序输入可复用、或优化器本来就要 sort（例如 ORDER BY 同一 key）、或 hash 内存压力极大。

- 两者语义必须等价，代价不同：
- hash：O(n) 期望时间，内存敏感，对 skew 敏感。
- sort：O(n log n)，但可 external sort，且排序结果可被下游复用。

- 初学者最容易犯的错：
- 以为“hash 一定比 sort 快”——错，要看 group  cardinality、内存、是否已有序、是否要输出顺序。

**和 SQL 语义的几个高危边界（先预告）**
- 这些在 `P11-2`、`P11-3` 会展开，这里先让你有雷达。

- `NULL` 与聚合：
- `COUNT(*)` 计行，`COUNT(col)` 通常不数 NULL。
- `SUM/AVG` 忽略 NULL；全 NULL 组 AVG 结果是 NULL 不是 0。

- 空输入：
- `SELECT COUNT(*) FROM empty_table` 应返回 1 行 `0`，不是 0 行。

- `DISTINCT` vs `GROUP BY`：
- `SELECT DISTINCT dept FROM T` 与 `SELECT dept FROM T GROUP BY dept` 结果常相同，实现路径可共享，但和 `COUNT(*)` 组合时不同。

- `ORDER BY` 与 `LIMIT`：
- top-N 优化可能避免全排序；但语义上仍要保证“真正的前 N 名”。

**关键不变量（P11 整课都要守住）**
- `I1`：同一逻辑查询，hash agg 与 sort agg 的结果必须逻辑等价（在 SQL 语义下）。
- `I2`：Sort 的输出必须满足排序键的全序定义（含 NULL 规则、ASC/DESC）。
- `I3`：Aggregation 的输出每组恰好一行（除非 HAVING 过滤掉），且 agg 函数语义与 SQL 标准一致。
- `I4`：阻塞算子对外接口仍应是 Volcano 风格的 `Init/Next`；阻塞发生在内部，不应破坏执行器组合性。
- `I5`：spill 到磁盘后的中间文件，必须可恢复正确结果；不能因为分区边界错误而漏组或重复组。

**常见错误理解**
- “ORDER BY 只是显示顺序，不影响结果集”——对结果集成员通常对，但对执行路径和 LIMIT 语义影响巨大。
- “GROUP BY 就是 DISTINCT”——不完全对；带聚合函数时语义不同。
- “排序一定用快排”——数据库用 external sort + merge，快排只是内存 run 内的小步骤。
- “聚合可以边 scan 边输出每组一行”——只有输入已按 group key 有序时才成立；一般情况不行。

- `同一 SQL 语义可有多种物理实现；优化器在 hash 与 sort 之间选的是代价，不是语义。`
