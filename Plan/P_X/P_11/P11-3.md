**先把 `P11-2` 和这一段接起来**
- 排序给你全局顺序；聚合利用`顺序`或`哈希`把多行压成组。
- 一个常见完整查询：

```sql
SELECT dept, COUNT(*), AVG(salary)
FROM Employee
GROUP BY dept
HAVING COUNT(*) > 10
ORDER BY AVG(salary) DESC;
```

- 物理上可能是：
- Hash Agg（按 dept 分组）→ Filter(HAVING) → Sort(ORDER BY avg) 
- 或 Sort Agg（若 planner 已选 sort 路径）→ Filter → 可能省略第二次 sort

- 本段重点：前半段聚合；Sort 与 top-N 的衔接在末尾收束。

---

**Hash Aggregation：核心思路**
- 一句话：`扫描输入，对 group key 哈希，在 hash table 里为每个 distinct key 维护聚合状态。`

```text
输入 tuple 流
    │
    ▼
提取 group key (dept)
    │
    ▼
hash(dept) -> bucket
    │
    ├─ key 首次出现：插入新 entry，初始化 agg state
    └─ key 已存在：更新 agg state（count++, sum+=salary, ...）
    │
    ▼
输入 EOF 后，遍历 hash table 输出每组一行
```

- group state 里有什么（典型）：

```text
GroupKey: dept = 'Sales'
State:
  count_star = 42
  sum_salary = 3150000
  max_salary = 120000
  // avg 不必存，输出时 sum/count 即可
```

- 不变量 `H1`：
- 每个 distinct group key 在 table 里恰好一个 entry。
- 同一 key 的所有输入行都必须反映到同一 entry 的 state 上。

---

**Hash Agg 的代价模型（直觉）**
- 时间：O(n) 期望，每次 insert/update O(1) 均摊。
- 空间：O(g)，g = distinct group 数量。
- 对 CPU：hash 计算 + 比较 group key（处理 hash 冲突）。
- 对内存：每个 group 一条 entry，skew 时某个 bucket 极长链表。

- 适用场景：
- 等值分组，group 数远小于行数但内存可承受。
- 不需要按 group key 有序输出。
- 下游不要 sort on same key（否则 sort agg 可能更合算）。

- 不适用或需谨慎：
- group 数接近行数（例如 `GROUP BY id` on 大表）→ hash table 接近 n 条，内存爆炸。
- 高 skew：某个 key 占 50% 行 → 冲突链长、缓存差、并行难。

---

**Hash Agg 内存不够：spill 与两阶段聚合（思想）**
- 工业系统：partition by hash key，把 hash table 切成多个分区，装不下的分区 spill 到磁盘；再对每个 spilled 分区递归 hash agg。
- bustub 教学版常简化成“假设内存够”；但你必须理解思想，否则读生产代码会懵。

```text
Phase 1 (local):
  分区 0..P-1，每区一个内存 hash table
  某区满 -> spill 该区 entry 到磁盘文件 f_i

Phase 2:
  对每个 spill 文件重新读入，做 local hash agg

Global merge:
  若同一 key 可能出现在多个分区（不应，若分区函数一致）
  或 map-reduce 式 combiner 后再 reduce
```

- 并行聚合（`P14` 预告）：
- 各 worker 做 local partial agg → exchange/repartition → global merge agg。
- 本课先记住：`COUNT/SUM/MIN/MAX` 等可分解聚合适合两阶段；`AVG` 通常传 (sum, count) 再合并。

---

**Sort Aggregation：核心思路**
- 一句话：`先按 group key 排序，再扫描有序流，相邻同 key 的行归为一组做聚合。`

```text
输入 -> Sort(group keys) -> 有序流
                │
                ▼
        线性扫描，维护“当前组”状态
        key 变化时，输出上一组，重置 state
                │
                ▼
        最后一组 flush
```

- 例子（已按 dept 排序）：

```text
(dept=HR, sal=5000)
(dept=HR, sal=6000)   <- 同组，更新 state
(dept=IT, sal=8000)   <- key 变，输出 HR 组，开 IT 组
...
```

- 不变量 `A1`：
- 只有当排序键严格按 GROUP BY 列有序时，线性扫描才正确。
- 若只按 dept 排但 GROUP BY dept, year，则必须按 (dept, year) 联合排序。

---

**Hash Agg vs Sort Agg：优化器怎么选**
- 这不是语义问题，是`代价问题`。

| 因素 | 倾向 Hash Agg | 倾向 Sort Agg |
|------|---------------|---------------|
| group 数 g 相对 n | g 较小 | g 很大或接近 n |
| 是否已有序输入 | 否 | 是（例如 index scan 按 group key） |
| 下游是否需要 ORDER BY group key | 否 | 是，可复用 sort |
| 内存/work_mem | 充足 | hash 放不下，sort+spill 更成熟 |
| DISTINCT on key | hash 自然 | 若已有 sort 可扫描去重 |

- 例子 1：
- `GROUP BY user_id` on 10 亿行日志，distinct user 5 亿 → hash 很可能 spill 惨烈；sort agg 也不便宜，但优化器可能选其他路径（预聚合、采样、列存等——超出本课，但要有“没有银弹”的意识）。

- 例子 2：
- `GROUP BY dept`（20 组）on 1000 万行 → hash agg 极合适。

**聚合函数的实现细节**
- `COUNT(*)`：每组计数器 +1，不 care 其他列 NULL。
- `COUNT(expr)`：expr 为 NULL 时不计数。
- `SUM(expr)`：忽略 NULL；全 NULL 组 → SUM 为 NULL。
- `AVG(expr)`：通常维护 (sum, count_non_null)，输出时除法；除零 → NULL。
- `MIN/MAX`：按类型比较，NULL 传播规则依 SQL。

- `HAVING`：
- 逻辑上在聚合之后过滤组；物理上常在 Agg 输出后接 Filter，或融合进 agg 输出前（实现细节因系统而异）。
- 语义：`WHERE` 过滤行；`HAVING` 过滤组。

```sql
-- HAVING 可引用聚合结果
HAVING COUNT(*) > 10
```

---

**DISTINCT：与 GROUP BY 的分叉与合并**
- `SELECT DISTINCT dept FROM T`
  - 语义：每个 dept 值最多输出一行。
  - 实现 A：hash set of dept。
  - 实现 B：sort by dept，扫描时 last_dept != current_dept 则输出。

- `SELECT dept, COUNT(*) FROM T GROUP BY dept`
  - 不能只去重 dept，还要算 COUNT。

- `SELECT COUNT(DISTINCT dept) FROM T`
  - 语义：distinct dept 的个数，一行输出。
  - 实现：hash set 计数，或 sort+scan 计数 group 数。

- 易错点：
- 把 `COUNT(DISTINCT x)` 实现成 `COUNT(*)` after distinct x —— 在空表、全 NULL 时语义不同。

---

**top-N 与聚合排序的衔接**
- 查询：`ORDER BY agg_expr DESC LIMIT k` after GROUP BY
- 执行树：Agg → Sort(agg_expr) → Limit
- 优化：
- 若 k 小，可在 Sort 节点用 heap 做 top-N（`P11-2`），不必全序所有 group。
- group 数 g=1000，k=10 → 对 1000 个组做 top-10 heap 很便宜。

- 查询：`ORDER BY non-agg column` 与 GROUP BY 不一致 —— SQL 非法（标准下 SELECT 列表约束）；binder 应报错。这是语义层防线，executor 不应默默猜。

---

**阻塞性：Aggregation 也是阻塞算子**
- Hash Agg：
- `Init` 或第一次 `Next` 前，通常要读完整个输入 build hash table（除非流式分组已有序且可边读边输出——特例）。
- 输出阶段：遍历 hash table，顺序可能 arbitrary。

- Sort Agg：
- 必须先完成 Sort（阻塞）或消费有序子计划，再扫描；整体阻塞程度 ≥ Sort。

- 与 pipeline 对比：
- `Scan -> Filter -> Agg -> Client`：Client 第一次 Next 可能要等 Agg build 完成。
- `Scan -> Filter -> Project -> Client`：可边 scan 边出结果。

**bustub：AggregationExecutor 怎样读**
- bustub 典型结构（名称因版本略有差异，思想一致）：

```cpp
class AggregationExecutor : public AbstractExecutor {
  void Init() override;
  bool Next(Tuple *tuple) override;
 private:
  const AggregationPlanNode *plan_;
  AbstractExecutor *child_;
  SimpleHashTable<GroupKey, AggregateValue> ht_;
  // 或 iterator over ht_ for output phase
};
```

- `Init` 常见逻辑：
- `child_->Init()`
- loop `child_->Next` until false:
  - 从 tuple 提取 group by 列 → GroupKey
  - 对每条 agg 表达式更新 AggregateValue
- 准备输出迭代器（或直接 first output ready）

- `Next` 常见逻辑：
- 若 hash table 还有未输出组 → 组装输出 tuple（group cols + agg results）
- 否则 return false

- schema 传播：
- 输出列 = group by 列 + agg 结果列，类型来自 plan node 的 agg types。
- child schema 用于求 agg 表达式输入；输出 schema 与 SELECT 列表对齐由 planner 保证。

---

**bustub 调试清单**
- 空表：`COUNT(*)` 应 0 行还是 1 行？—— GROUP BY 无行时 0 行；`SELECT COUNT(*)` 无 GROUP BY 时 1 行 0。
- 全 NULL group key：是否单独成组？—— 通常 NULL 是一个合法 group key 值。
- 重复输入行：COUNT 是否正确累加？
- 多 agg：`SUM(a), AVG(a)` 是否共用 state 而不重复扫描？
- HAVING 若在独立 Filter：Agg 输出 schema 是否含 HAVING 需要的列？

---

**关键不变量（本段）**
- `G1`：每个 logical group 恰好输出一行（HAVING 前或后依计划而定）。
- `G2`：可分解 agg 的 partial + merge 与一次聚合结果一致。
- `G3`：hash 与 sort 两路径对同一 SQL 结果集等价。
- `G4`：GROUP BY 列集合必须与 sort agg 的排序键前缀一致。
- `G5`：输出 tuple 的 group 列值等于该组内行的 group key（代表值；非 agg 列在标准 SQL 中不在 SELECT 除非 functionally dependent）。

---

**常见错误理解与 bug 形态**
- hash 冲突处理错：不同 key 映射到同一 entry → 结果 silently wrong。
- 输出阶段修改 hash table 同时迭代 → iterator 失效。
- `AVG` 用 sum/count 但 count 用了 COUNT(*) 而非 COUNT(col)。
- Sort Agg 只按第一列 GROUP BY 列排序，GROUP BY 多列时错组。
- Init 里未 `child_->Init()`，或 Next 后未重置状态导致第二次 Init 脏读。
