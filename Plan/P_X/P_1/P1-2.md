这一段正式进入 `P1` 的核心内容：`关系代数`。这一次我们不再停留在“关系、元组、属性是什么”，而是开始回答另一个更关键的问题：`查询到底由哪些基本运算组成`。**P1-2 开始**

**今天这次的目标**
- 我们现在正式学习 `P1-2`：`关系代数的基本算子`。
- 这一段你要真正搞懂的，不是几个符号怎么写，而是：
- 为什么数据库要把查询拆成一组基本运算。
- 为什么 `选择`、`投影`、`连接` 这些算子是后面优化器和执行器的基础。
- 为什么“一个复杂查询 = 一棵由基本算子组成的树”这件事，会直接决定 `bustub` 里 planner 和 executor 的设计。

**先把上一段和这一段接起来**
- `P1-1` 解决的是：数据库到底在操作什么对象。
- 你已经知道：
- 数据被抽象成关系。
- 一行是元组，一列是属性。
- 模式定义关系的结构，实例代表某时刻的真实数据。

- 但现在还差一个问题：
- `如果用户写了一个查询，数据库到底在“做什么运算”？`

- 比如用户写：

```sql
SELECT name
FROM Student
WHERE age > 20;
```

- 这个查询不是一句“魔法命令”。
- 从逻辑上看，它是在做两件事：
- 先从 `Student` 里挑出 `age > 20` 的行。
- 再从这些行里只保留 `name` 这一列。

- 这就是关系代数的切入点：
- `把复杂查询拆成一组定义清晰、可以组合、可以推理的基本运算。`

---

**问题定义**
- 什么是关系代数？
- 简单说：
- `关系代数是一套以关系为输入、以关系为输出的基本运算体系。`

- 注意这句话有两个关键点：
- `输入是关系`
- `输出还是关系`

- 这两个点非常重要。
- 因为只要一个算子的输出仍然是关系，那么这个输出就还能继续作为另一个算子的输入。
- 这意味着查询可以层层组合，最后组成一棵运算树。

- 这就是为什么关系代数不是“几个零散操作”。
- 它本质上是一种：
- `可组合`
- `可推理`
- `可优化`
- `可执行映射`

的逻辑查询表示。

---

**为什么数据库需要这套运算**
- 先从第一性原理来问：
- 如果没有关系代数，会发生什么？

- 第一类问题：`查询没有统一内部表示`
- 用户写 SQL 是字符串。
- 数据库不能直接靠字符串去优化、执行、比较两个查询是否等价。
- 它必须先把 SQL 翻译成一种结构化表示。

- 第二类问题：`优化器无从下手`
- 优化器的工作不是“猜一个快方法”。
- 它的工作是：
- 在`不改变结果语义`的前提下，改写运算顺序、改写树结构、选择更便宜的执行方式。

- 如果没有一组定义清楚的逻辑算子，优化器根本无法判断：
- 哪些操作可以交换顺序
- 哪些过滤可以提前做
- 哪些列可以提前裁掉
- 哪些连接顺序代价更低

- 第三类问题：`执行器没有清晰职责边界`
- 执行器不是“执行 SQL 字符串”。
- 执行器是在执行逻辑算子的物理版本。
- 例如：
- `SeqScanExecutor` 对应扫描输入关系
- `Filter` 对应选择
- `Projection` 对应投影
- `NestedLoopJoinExecutor` 对应连接的一种物理实现

- 所以你要记住：
- `关系代数不是数学装饰品，它是数据库内部理解和处理查询的工作语言。`

---

**先给你一张总图**
- 你可以把一个查询的内部生命周期先理解成这样：

```text
SQL 字符串
-> 语法树
-> 关系代数风格的逻辑树
-> 物理计划
-> 执行器
-> 结果
```

- 这条链路里：
- SQL 是用户语言
- 关系代数是逻辑语义层
- 物理计划是执行策略层
- 执行器是真正跑数据的实现层

- `P1-2` 学的就是第二层：
- `查询在逻辑上由哪些基本运算组成`

---

**关系代数里最重要的概念**
- 这一段最重要的不是一口气背完所有算子。
- 你第一次必须先吃透 3 个：
- `选择`
- `投影`
- `连接`

- 这三个为什么优先？
- 因为绝大多数 OLTP/OLAP 查询，最后都离不开：
- 从某些表里读数据
- 过滤掉不要的行
- 裁掉不要的列
- 把多个关系按某种条件拼起来

- 也就是说：
- `选择解决“要哪些行”`
- `投影解决“要哪些列”`
- `连接解决“怎样把多个关系组合起来”`

- 你可以先把这三个看成查询系统的主骨架。

---

**1. 选择 Selection**
- 选择，通常记成 `σ`，你现在先不用背符号。
- 你先记它的本质：
- `选择是在一张关系里保留满足某个条件的元组。`

- 举个例子：

```text
Student(id, name, age)

(1, 'Alice', 20)
(2, 'Bob', 21)
(3, 'Cindy', 19)
```

- 如果做“年龄大于 20”的选择，那么结果就是：

```text
(2, 'Bob', 21)
```

- 你要注意：
- 选择改变的是`行数`
- 它通常`不改变列结构`

- 也就是说，输入 schema 是：

```text
Student(id, name, age)
```

- 输出 schema 还是：

```text
Student(id, name, age)
```

- 只是满足条件的元组变少了。

**为什么需要选择**
- 因为用户几乎不会总是要整张表。
- 用户想要的是“符合条件的那部分数据”。

- 如果没有选择这个逻辑算子，数据库就无法统一表达：
- `WHERE age > 20`
- `WHERE id = 5`
- `WHERE salary > 10000 AND dept = 'DB'`

- 所以 `WHERE` 子句在逻辑上，最核心的对应物就是选择。

**选择的关键不变量**
- 输入和输出必须是同一模式的关系。
- 只有满足谓词条件的元组才能保留下来。
- 谓词求值规则必须清楚，尤其后面你学 SQL 时会遇到 `NULL` 和三值逻辑。

**初学者最容易错的点**
- 误以为选择会改变列结构。
- 不对。
- 选择主要是筛`行`，不是裁`列`。

- 误以为选择只是“程序里 if 一下”。
- 这也不对。
- 在数据库里，选择是一个可组合、可下推、可重排、可由多种物理算法实现的逻辑算子。

---

**2. 投影 Projection**
- 投影，通常记成 `π`。
- 它的本质是：
- `从关系中保留指定属性，丢弃其他属性。`

- 还是看 `Student(id, name, age)`：
- 如果我们只想要 `name`，结果就是：

```text
('Alice')
('Bob')
('Cindy')
```

- 这次你要注意：
- 投影主要改变的是`列结构`
- 它通常会减少属性个数

- 输入 schema 是：

```text
Student(id, name, age)
```

- 输出 schema 则可能变成：

```text
Result(name)
```

**为什么需要投影**
- 因为用户通常不需要整行所有属性。
- 例如：
- 登录时可能只要用户 id
- 展示列表时可能只要 name 和 title
- 聚合前可能只需要 group key 和被聚合列

- 从工程角度看，投影非常重要，因为它不只是语义操作，还会影响性能：
- 不需要的列可以尽早丢掉
- tuple 更小
- 内存更省
- 连接和排序代价可能更低

- 这就是为什么优化器喜欢做：
- `投影裁剪`

- 本质上就是：
- `越早丢掉不需要的列，后续算子就越轻。`

**投影的关键不变量**
- 输出属性集合必须清楚定义。
- 输出 schema 必须正确传播到下游算子。
- 如果语义是集合语义，投影可能涉及去重；如果是 SQL 的包语义，行为会更复杂。

**初学者最容易错的点**
- 把投影理解成“显示时少打印几列”。
- 不对。
- 投影不是 UI 层行为，而是逻辑层算子。
- 它会影响中间结果的 schema，进而影响后续计划节点和执行器逻辑。

---

**3. 连接 Join**
- 连接是这段里最重要、也最容易一开始觉得抽象的算子。
- 你先抓住一句话：
- `连接是在两个关系之间按某种条件，把相关联的元组合并起来。`

- 举个例子，有两张表：

```text
Student(sid, name, dept_id)
Dept(dept_id, dept_name)
```

- 数据可能是：

```text
Student:
(1, 'Alice', 10)
(2, 'Bob', 20)

Dept:
(10, 'DB')
(20, 'AI')
```

- 如果按 `Student.dept_id = Dept.dept_id` 连接，结果就是：

```text
(1, 'Alice', 10, 10, 'DB')
(2, 'Bob', 20, 20, 'AI')
```

- 逻辑上看，连接做的是：
- 从左边关系拿一条元组
- 从右边关系拿一条元组
- 检查是否满足连接条件
- 满足就把两者拼成更宽的一条结果元组

**为什么需要连接**
- 因为现实数据通常被拆在多个关系里。
- 如果没有连接，你就很难表达：
- 学生属于哪个院系
- 订单对应哪个用户
- 评论对应哪篇文章

- 也就是说：
- `连接是把被分散存储的逻辑实体重新拼回查询结果的核心机制。`

**连接为什么比选择、投影更关键**
- 因为连接往往是查询里代价最高的部分。
- 你后面学优化器，最重要的很多优化都围绕连接：
- 连接顺序怎么选
- 先过滤再连接还是先连接再过滤
- 用 nested loop、hash join 还是 sort-merge join

- 所以从数据库内核角度看：
- `连接既是语义核心，也是性能核心。`

**连接的关键不变量**
- 左右输入 schema 必须清楚。
- 连接条件必须明确定义。
- 输出 schema 是左右两边属性的组合。
- 逻辑语义不能因为物理算法不同而改变。

**初学者最容易错的点**
- 误以为连接只是“把两张表并排放”。
- 不对。
- 没有连接条件时，那更接近笛卡尔积。
- 真正的连接通常是在某个匹配条件上做筛选和组合。

---

**4. 笛卡尔积 Cartesian Product**
- 这也是关系代数里的基本算子。
- 它的本质是：
- `左边每一条元组和右边每一条元组都组合一次。`

- 如果左边有 `m` 条，右边有 `n` 条，结果通常有 `m * n` 条。

- 你现在先不要把它当成常用查询目标。
- 它更像一个理论基础：
- 很多连接都可以理解成：
- `先做笛卡尔积，再做选择`

- 当然，真实系统一般不会傻到真的完整做出一个巨大笛卡尔积再筛。
- 但逻辑上，这个理解很重要。

---

**5. 并、差、重命名**
- 这些你这次先知道作用就够。

**并 Union**
- 把两个同模式关系合并起来。
- 前提通常是两边 schema 兼容。

**差 Difference**
- 从左关系中保留那些“不在右关系里”的元组。

**重命名 Rename**
- 给关系或属性换个名字。
- 这很重要，因为复杂查询里属性名可能冲突，或者子查询结果需要一个新别名。

- 第一次学习时，你不用把这三个当主战场。
- 但你要知道：
- 它们让关系代数更完整，也让复杂查询的表达更严谨。

---

**查询为什么是一棵树**
- 现在你已经看到：
- 选择的输入输出都是关系
- 投影的输入输出都是关系
- 连接的输入输出也是关系

- 所以一个复杂查询可以这样理解：

```text
投影
  <- 选择
       <- 连接
            <- Student
            <- Dept
```

- 你看到没有：
- 每个节点都是一个算子
- 每条边传递的都是关系

- 这就是逻辑查询树。

- 这件事极其关键，因为：
- planner 要构造它
- optimizer 要改写它
- executor 要执行它

- 没有这棵树，数据库就很难做结构化推理。

---

**为什么这些算子是优化器的基础**
- 优化器的核心工作不是“发明新查询”。
- 而是：
- `在结果不变的前提下，改写算子组织方式，让代价更低。`

- 举几个最经典的直觉：

**直觉 1：选择下推**
- 如果一个过滤条件只依赖某一张表，那通常越早做越好。
- 因为这样可以减少后面连接时参与的数据量。

**直觉 2：投影裁剪**
- 如果后面根本不需要某些列，那最好早点丢掉。
- 这样中间结果更小。

**直觉 3：连接顺序影响巨大**
- 三张表连接时，先连哪两张，代价可能差很多。

- 所以你现在必须真正建立一个观念：
- `优化器不是在优化 SQL 字符串，而是在优化关系代数树。`

---

**为什么这些算子是执行器的基础**
- 从逻辑层下到执行层，每个算子都会有一个物理实现版本。

- 例如：
- 选择 -> filter executor
- 投影 -> projection executor
- 连接 -> nested loop join / hash join / sort-merge join executor

- 你要注意：
- 一个逻辑算子可以对应多种物理实现。
- 例如连接的逻辑语义只有一种“按条件组合两个关系”。
- 但物理上可以有多种执行方法。

- 所以：
- `逻辑算子定义“做什么”`
- `物理算子定义“怎么做”`

- 这是数据库内核里非常核心的分层。

---

**和 bustub 的联系**
- 这部分你必须建立起来，否则这一段会像纯理论。

- 在 `bustub` 里，你后面会看到：
- planner 生成计划节点
- executor 按节点类型逐步拉取 tuple

- 你可以先粗略这样对照：
- `SeqScan`：从某个关系读元组
- `Filter`：做选择
- `Projection`：做投影
- `NestedLoopJoin`：做连接的一种物理实现
- `Aggregation`：后面会连到更复杂的代数和分组语义

- 也就是说，`bustub` 的很多 executor，不是在“发明查询语义”。
- 它们是在执行已经被关系代数化之后的逻辑结构。

- 如果你现在不理解：
- 选择的输入输出是什么
- 投影怎样改变 schema
- 连接怎样组合两个关系

- 那你后面看 executor 时就会很痛苦。

---

**最小实现视角**
- 如果你自己写一个最小数据库，这一段最直接的落点其实是：
- `定义逻辑算子节点`

- 比如你可以先想一个极简结构：

```cpp
enum class LogicalOpType {
  SeqScan,
  Filter,
  Projection,
  Join
};

struct LogicalPlanNode {
  LogicalOpType type;
  std::vector<LogicalPlanNode *> children;
};
```

- 这里最关键的不是 C++ 语法。
- 而是这个思想：
- 查询先被表示成逻辑树
- 再由后续模块决定如何执行

- 这一步就是从 `P1` 走向 `planner / optimizer / executor` 的桥。

- `选择决定保留哪些行，投影决定保留哪些列，连接决定怎样组合多个关系。`
