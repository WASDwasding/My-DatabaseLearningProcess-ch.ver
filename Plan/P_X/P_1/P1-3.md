这一段开始进入 `P1` 里最容易被忽略、但对优化器最关键的部分：`查询为什么能改写`。你在 `P1-2` 已经知道查询可以表示成一棵由选择、投影、连接组成的逻辑树；现在要继续追问：`为什么数据库敢动这棵树，而且改完结果还不变`。**P1-3 开始**

**今天这次的目标**
- 我们现在正式学习 `P1-3`：`关系代数里的等价变换直觉`。
- 这一段你要真正搞懂的，不是背几个优化规则名字，而是：
- 为什么有些查询改写前后结果一样。
- 为什么优化器不是“瞎调顺序”，而是在依赖一组逻辑等价关系工作。
- 为什么有些改写在理论上成立，但在真实 SQL 里却可能因为 `NULL`、重复值、外连接、聚合而出问题。

**先把上一段和这一段接起来**
- `P1-2` 解决的是：查询可以拆成基本算子，并组织成一棵逻辑树。
- 但如果数据库只是机械执行这棵树，它其实还不算“聪明”。
- 真正让数据库和普通脚本区别拉开的，是它会进一步问：
- `这棵树能不能换一种形状，结果不变，但代价更低？`

- 例如一个简单查询：

```sql
SELECT name
FROM Student
WHERE age > 20;
```

- 逻辑上是：

```text
投影 name
  <- 选择 age > 20
       <- Student
```

- 现在假设另一个写法变成：

```text
选择 age > 20
  <- 投影 name, age
       <- Student
```

- 这两个写法在某些条件下结果是一样的。
- 这就说明：
- `查询不是只有一种逻辑树形态。`

- 也正因为存在多种等价形态，优化器才有工作空间。

---

**问题定义**
- 什么叫查询等价改写？
- 简单说：
- `如果两棵逻辑树对任意合法输入都产生相同结果，我们就说它们在逻辑上等价。`

- 你一定要注意这里有两个关键词：
- `任意合法输入`
- `相同结果`

- 这不是“我今天试了几条数据看起来差不多”。
- 也不是“多数情况下差不多”。
- 而是：
- `在语义上必须稳定相同。`

- 只要你改变了结果含义，那就不是优化，而是把查询改坏了。

---

**为什么数据库一定要有这一步**
- 先从第一性原理来问：
- 如果数据库不能做等价改写，会怎样？

- 第一类问题：`代价优化空间极小`
- 同一个查询，不同执行顺序、不同连接顺序、不同过滤位置，代价可能差很多。
- 如果数据库只能照着用户字面写法执行，那很多性能机会都丢了。

- 第二类问题：`优化器没有理论基础`
- 优化器不是拍脑袋换顺序。
- 它必须先证明：
- 改写后结果不变
- 然后才去比较代价

- 第三类问题：`逻辑层和物理层无法分离`
- 如果没有“逻辑等价”这层，系统就很容易直接从 SQL 跳到某个具体执行方案。
- 这样 planner、optimizer、executor 的边界就会糊掉。

- 所以你要抓住一个核心结论：
- `优化器能存在，不是因为数据库会算代价，而是因为关系代数提供了可证明的逻辑等价基础。`

---

**先建立一个最重要的判断标准**
- 当你判断一个改写是否安全时，脑子里要先问 3 个问题：
- 改写前后的输入关系集合是不是一样。
- 改写前后的输出 schema 和输出值语义是不是一样。
- 改写有没有悄悄改变重复值、NULL 语义、分组边界或者外连接保留行。

- 前两个是理论层面。
- 第三个是工程层面。

- 很多初学者一看到“交换顺序”就觉得都可以换。
- 这是错的。
- `关系代数里的等价规则，是带前提条件的。`

---

**最经典的等价直觉 1：选择下推**
- 这是你后面最常见的优化直觉。
- 它的本质是：
- `如果某个过滤条件只依赖一部分输入，那么通常可以尽量早做。`

- 举个例子：

```text
选择 Student.age > 20
  <- 连接 Student.dept_id = Dept.dept_id
       <- Student
       <- Dept
```

- 如果过滤条件只用到了 `Student.age`，那很多时候可以改写成：

```text
连接 Student.dept_id = Dept.dept_id
  <- 选择 Student.age > 20
       <- Student
  <- Dept
```

- 为什么这通常是对的？
- 因为无论你先连再筛，还是先把 Student 里不满足条件的元组删掉再连，最终能参与连接的 Student 行其实是同一批。

- 为什么这通常更快？
- 因为连接前输入更小了。
- 后面参与匹配的元组数减少了。

**你要真正理解的不是“下推更快”**
- 而是：
- `它之所以能更快，是因为它先利用逻辑等价，证明可以提前过滤；然后才利用更小输入降低代价。`

**但注意前提**
- 如果过滤条件同时依赖左右两边属性，那它就不能简单地下推到某一边。
- 例如：

```text
Student.score > Dept.threshold
```

- 这种条件必须等两边都在了，才有办法求值。

---

**最经典的等价直觉 2：选择的合并与交换**
- 如果你有两个连续选择：

```text
选择 c1
  <- 选择 c2
       <- R
```

- 往往可以看成：

```text
选择 c1 AND c2
  <- R
```

- 或者把 `c1` 和 `c2` 的顺序交换。

- 这背后的原因很简单：
- 选择只是不断缩小行集合。
- 连续筛两次和一次筛掉两类不满足条件的行，本质上是一样的。

**为什么这个直觉重要**
- 因为很多复杂谓词都会先被拆开，再分别看哪些部分能下推到哪里。
- 这其实就是优化器在做谓词拆分和谓词下推。

---

**最经典的等价直觉 3：投影裁剪**
- 在 `P1-2` 你已经知道投影会减少列。
- 现在你要进一步知道：
- `投影也常常可以提前。`

- 举个直觉例子：
- 如果后面连接和输出只需要：
- `Student.name`
- `Student.dept_id`
- `Dept.dept_name`

- 那么 `Student` 里的 `age`、`salary` 等无关列，其实可以在更早阶段丢掉。

- 为什么这通常安全？
- 因为那些列本来就不会被后续算子使用，也不会出现在最终结果里。

- 为什么这通常更快？
- 因为中间 tuple 更窄，内存、拷贝、排序、hash 构建成本都可能下降。

**但这里也有前提**
- 你不能把后面谓词、连接条件、聚合、排序要用的列提前丢掉。
- 所以投影裁剪本质上依赖一个能力：
- `列使用分析`

- 也就是优化器必须知道：
- 哪些列还会被谁使用。

---

**最经典的等价直觉 4：连接顺序的调整**
- 这是数据库优化里最有名，也最重要的一类问题。

- 假设你有三张表：

```text
A JOIN B JOIN C
```

- 逻辑上可能有多种树形：

```text
(A JOIN B) JOIN C
```

或者

```text
A JOIN (B JOIN C)
```

- 在某些前提下，它们逻辑结果一样。
- 但物理代价可能天差地别。

- 例如：
- 如果 `A` 很小，`B` 很大，`C` 也很大
- 而且 `A JOIN B` 之后结果非常小
- 那先做 `A JOIN B` 可能就很划算

**为什么这个问题如此重要**
- 因为连接往往是查询里代价最高的部分。
- 连接顺序一变，中间结果大小就会变。
- 中间结果一变，后面所有算子的代价都可能被放大或缩小。

- 所以你可以先记一句工程上非常重要的话：
- `很多优化，本质上都在想办法让中间结果尽量早变小。`

---

**为什么“中间结果大小”这么关键**
- 你学数据库内核时，要尽快建立一个性能直觉：
- 数据库真正贵的，很多时候不是“做了一次操作”，而是：
- 做这次操作时喂进去的数据量太大
- 中间结果太宽
- 中间结果太多
- 需要落盘、排序、建 hash、拷贝、比较

- 所以：
- 选择下推在减少行数
- 投影裁剪在减少列宽
- 连接顺序优化在减少中间爆炸

- 这三件事其实都在围绕同一个目标：
- `让后续算子处理更小的输入。`

---

**为什么有些改写会出问题**
- 到这里你必须建立一个重要警惕：
- `不是所有看起来“差不多”的改写都安全。`

- 下面是最常见的几个陷阱。

**陷阱 1：集合语义和包语义不同**
- 纯关系代数更接近集合语义，天然不强调重复值。
- 但 SQL 实际上很多时候是包语义，也就是允许重复值。

- 这意味着：
- 某些在集合语义下看起来等价的改写，在 SQL 里可能影响重复次数。
- 一旦重复次数变了，聚合结果、计数结果都可能变。

**陷阱 2：NULL 和三值逻辑**
- SQL 不是简单的 true/false。
- 遇到 `NULL` 时，很多表达式会进入 unknown。

- 所以某些“按数学直觉看起来能换”的过滤顺序，在包含 `NULL` 的真实 SQL 语义下，要更小心验证。

**陷阱 3：外连接 Outer Join**
- 内连接更像“只保留匹配成功的行”。
- 外连接则还承担“保留某一边未匹配行”的语义责任。

- 所以外连接不是你想怎么换顺序就怎么换。
- 很多对内连接成立的交换律、结合律，到外连接就不成立了。

**陷阱 4：聚合和分组**
- 一旦开始 `GROUP BY` 或聚合，很多改写都必须考虑：
- 这个条件是在聚合前过滤，还是聚合后过滤
- 这个投影会不会丢掉分组键
- 这个重排会不会改变聚合输入多重性

- 所以你要记住：
- `优化规则不是口号，而是带严格前提条件的。`

---

**关键不变量**
- 对 `P1-3` 来说，最重要的不变量有这些：

- `不变量 1：改写前后的逻辑结果必须一致`
- 这是底线。
- 只要结果语义变了，再快也没意义。

- `不变量 2：改写前后的输出 schema 必须一致`
- 不只是值要对，输出列的含义、顺序、名称边界也要一致。

- `不变量 3：改写规则必须满足前提条件`
- 例如一个选择条件能否下推，取决于它引用了哪些属性。

- `不变量 4：逻辑等价先于代价比较`
- 先证明“能这么改”，再比较“这么改值不值得”。

---

**为什么这直接连接到优化器**
- 现在你就可以把优化器的工作，先抽象成两步：

```text
第一步：找等价改写候选
第二步：在候选中选代价更低的
```

- 你要注意：
- 如果没有第一步，第二步根本没有合法搜索空间。
- 这也是为什么优化器课程会同时讲：
- 关系代数
- 逻辑等价规则
- 代价估计
- 计划枚举

- 它们不是并列零件，而是一条链。

---

**和 bustub 的联系**
- 在 `bustub` 里，你后面会看到 optimizer 不是直接看 SQL 文本，而是在看计划节点结构。
- 它做的很多事，本质上都是在改写逻辑树。

- 例如你可以先这样理解：
- planner 先把查询变成一个比较“直译”的逻辑结构
- optimizer 再尝试做一些安全改写
- executor 最终执行改写后的计划

- 如果你不理解：
- 为什么某个 filter 能提前
- 为什么某个 projection 能裁掉列
- 为什么某个 join 顺序可能更优

- 那你看到 optimizer 规则时就会觉得像黑魔法。

- 其实不是黑魔法。
- 它只是在利用关系代数提供的等价性。

---

**最小实现视角**
- 如果你自己做一个最小数据库，这一段最适合做的不是一上来写“完整优化器”。
- 而是先做一个极简版的规则重写器。

- 例如你可以只支持一条规则：
- `Filter` 如果只依赖左孩子属性，就把它往左孩子方向下推。

- 这样一个最小实验，就已经能让你练到：
- 表达式依赖分析
- 计划树改写
- 改写前后结果一致性验证

- 这个练习比背一堆优化规则更有价值，因为它会逼你真正思考：
- 什么叫“能改”
- 什么叫“不能改”

---
