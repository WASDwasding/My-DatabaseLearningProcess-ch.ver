**先给你一张总图**
- 你可以先把数据库想成 3 层：
- 最上层：用户写 SQL，说“我要什么结果”
- 中间层：数据库把 SQL 转成逻辑运算，也就是关系代数风格的查询树
- 最底层：数据库把数据存在 page、tuple、index、buffer pool 里

- 这三层分别回答三个不同问题：
- 用户层：`我要查什么`
- 逻辑层：`这个查询在语义上到底是什么意思`
- 存储层：`这些数据在磁盘和内存里怎么放、怎么读`

- `P1` 学的就是中间这层。
- 也就是说，`P1` 不是讲“怎么存”，而是讲“我们到底在算什么”。

**问题定义**
- 什么是关系模型？
- 简单说：`关系模型是一种用表来抽象数据、用一组严格定义的运算来抽象查询的方法。`

- 注意，这句话有两个部分：
- `数据抽象成表`
- `查询抽象成运算`

- 这两个部分缺一不可。
- 只有表，没有运算，你只能“看数据”，不能系统地表达查询。
- 只有运算，没有统一的数据抽象，你没法定义运算的输入输出是什么。

---

**为什么需要它**
- 先从第一性原理来问：
- 数据库系统最核心的任务是什么？

- 一个很朴素的答案是：
- `保存数据`
- `查数据`
- `改数据`

- 但这还不够，因为如果只是保存和读取，普通文件系统也能做。
- 数据库和普通文件系统最大的区别之一是：
- `数据库提供了一套统一的、可推理的、可组合的数据抽象和查询抽象。`

- 如果没有关系模型，会出现什么问题？

- 第一类问题：`用户直接面对底层存储细节`
- 例如用户得知道：
  - 文件怎么分块
  - 某条记录在第几个 page
  - 哪个字段在偏移量多少的位置
- 这会让查询语言完全和存储实现绑死。
- 一旦你换了 page layout、换了索引结构、换了压缩方式，用户查询全坏。

- 第二类问题：`查询无法系统优化`
- 如果查询只是“一段程序逻辑”，数据库很难判断：
  - 哪些操作可以交换顺序
  - 哪些过滤可以提前做
  - 哪些列根本不用读
- 没有统一逻辑表示，就没有优化器。

- 第三类问题：`系统模块边界混乱`
- 你后面会学到：
  - parser
  - binder
  - planner
  - optimizer
  - executor
- 这些模块之所以能分层，是因为关系模型提供了统一语义边界。

- 所以你要抓住一个核心结论：
- `关系模型的价值，不是“把数据画成表格好看”，而是给数据库系统提供了稳定的数据语义和查询语义。`

---

**核心术语**
- 下面这几个词你必须分清，不然后面会一直混。

**1. 关系**
- “关系”通常可以先粗略理解成“表”。
- 但更准确一点说：
- `关系是一个满足某个固定模式的元组集合。`

- 这里有两个关键词：
- `固定模式`
- `元组集合`

- 举个例子，假设有一张学生表：

```sql
Student(id, name, age)
```

- 这不是具体数据本身，它更像一个“形状定义”。
- 真正的数据可能是：

```text
(1, 'Alice', 20)
(2, 'Bob', 21)
(3, 'Cindy', 19)
```

- 那么：
- `Student` 是一个关系
- 每一行是一个元组
- `id`、`name`、`age` 是属性

**2. 属性**
- 属性就是列。
- 例如：
- `id`
- `name`
- `age`

- 但数据库语义里，属性不只是“列名”，它还代表这个位置的意义和类型约束。

**3. 元组**
- 元组就是一行记录。
- 例如：

```text
(1, 'Alice', 20)
```

- 你可以把它理解成“一个对象的一个状态实例”。
- 但注意，关系模型本身不关心“对象方法”之类的面向对象语义，它只关心值。

**4. 模式**
- 模式，也就是 schema，定义的是这张关系“长什么样”。
- 例如：

```text
Student(id: int, name: string, age: int)
```

- 模式回答的是：
- 这张表有哪些属性
- 每个属性是什么类型
- 它们的逻辑含义是什么

- 模式是“定义”。
- 它不是具体数据。

**5. 实例**
- 实例，也就是 instance，指某个时间点上这张关系里实际存的那些数据。
- 例如今天 Student 表里有 100 行数据，这 100 行就是当前实例。
- 明天插入两条数据，实例就变了。
- 模式通常不常变，实例经常变。

**6. 域**
- 域可以理解为某个属性允许取值的范围。
- 比如：
- `age` 的域可能是整数
- `name` 的域可能是字符串
- `grade` 的域可能是 `A/B/C/D/F`

- 域的意义在于：
- 它决定一个属性能接受什么类型和值范围。
- 这对比较、排序、聚合、表达式求值都很关键。

---

**一个最容易混淆的点**
- 很多初学者会把“表”当成纯 UI 概念。
- 这是错误的。

- 在关系模型里，“表”不是 Excel 那种视觉表格。
- 它本质上是：
- `带有严格模式定义的一组元组`

- 这意味着数据库真正关心的不是“画出来像几行几列”。
- 它关心的是：
- 这些值是否符合模式
- 这些元组之间能否做合法运算
- 查询结果是否满足语义

---

**为什么不是直接用文件模型**
- 这个问题你一定要想透。

- 假设没有关系模型，你的数据可能只是一个二进制文件：
- 第 0 到 3 字节是 id
- 第 4 到 35 字节是 name
- 第 36 到 39 字节是 age

- 这样会有什么问题？

- 第一个问题：`用户必须理解物理布局`
- 这是灾难。
- 因为用户本来只想问：
  - “年龄大于 20 的学生有哪些”
- 结果却必须知道：
  - age 在第 36 字节开始

- 第二个问题：`逻辑语义和物理实现耦合`
- 只要你改了存储格式，所有访问逻辑都得改。

- 第三个问题：`没有统一查询代数`
- 数据库没法说：
  - 先过滤 age > 20
  - 再投影 name
- 因为它没有“过滤”和“投影”这样的逻辑抽象。

- 所以你可以记住一句话：
- `关系模型的作用，就是把“用户关心的数据逻辑”从“系统内部的物理存储”中隔离出来。`

---

**关系模型的核心收益**
- 这部分很重要，你要把它当成考试题来记。

- 关系模型至少带来 4 个核心收益：

- `收益 1：数据独立性`
- 用户写查询时，不需要知道底层文件、page、offset、索引布局。
- 后面你学 buffer pool 和 slotted page 时，会更深刻感受到这一点。

- `收益 2：统一语义`
- 所有数据都按关系和属性来理解。
- 所有查询都能转成一套统一逻辑。

- `收益 3：可组合性`
- 查询不是一坨黑盒代码，而是一棵可以继续拼接的运算树。
- 一个查询的输出仍然是关系，因此还能作为另一个查询的输入。

- `收益 4：可优化性`
- 因为查询被表示成结构化运算，数据库才能做谓词下推、投影裁剪、连接重排等优化。

---

**关键不变量**
- 你以后学数据库内核，不能只背概念，必须养成“这个模块的不变量是什么”的习惯。

- 对 `P1` 来说，最重要的不变量有这些：

- `不变量 1：关系的每个元组都符合相同模式`
- 也就是每一行都得有同样的列结构和可解释的属性含义。

- `不变量 2：属性具有明确域和语义`
- 否则你无法比较、排序、过滤、聚合。

- `不变量 3：查询运算必须有清晰输入输出`
- 你不能发明一个“随便改数据”的黑盒操作，否则优化器无法推理。

- `不变量 4：逻辑语义独立于物理存储`
- 查询结果不应该依赖记录在磁盘上怎么排布。

- 这第四条尤其关键。
- 因为后面你会学：
  - heap table
  - B+Tree index
  - buffer pool
  - WAL
- 这些都属于物理层。
- 关系模型属于逻辑层。
- 逻辑层不能被物理层细节污染。

---

**常见错误理解**
- 这里我直接指出几个典型误区。

- `误区 1：关系模型就是“表格形式存数据”`
- 不对。
- 表格只是表象。
- 真正核心是：
  - 统一数据抽象
  - 统一查询语义
  - 支持代数推理

- `误区 2：关系模型只和 SQL 有关，和内核实现无关`
- 不对。
- parser、planner、optimizer、executor 全都直接依赖关系模型。
- 没有关系模型，你连执行器要处理什么输入输出都说不清。

- `误区 3：关系模型和物理存储完全无关，所以没必要学`
- 也不对。
- 它不负责“怎么存”，但它决定“物理层要为谁服务”。
- 存储引擎再复杂，最终都要支持关系层的语义访问。

- `误区 4：学数据库内核先学 page 和 B+Tree 就行，P1 太理论`
- 这是很多初学者的坑。
- 如果你一上来只学 page 和树，你会做出“能跑的结构”，但不知道系统整体为什么这样设计。
- 到 executor、optimizer、SQL 语义时就会断层。

**和 bustub 的联系**
- 这部分你一定要建立起来，否则这节会显得抽象。

- 在 `bustub` 里，大致有这样一条链路：

```text
SQL
-> Parser
-> Binder
-> Planner
-> Optimizer
-> Executor
```

- 这条链路里：
- parser 负责把字符串 SQL 解析成语法结构
- binder 负责把表名、列名和真实 schema 对上
- planner 负责把查询变成逻辑计划
- optimizer 负责做等价改写
- executor 负责真正执行

- 你现在要理解的是：
- `planner 和 optimizer 之所以存在，是因为查询不是一段随便写的命令式程序，而是可以被表示成关系运算树。`

- 举个例子，用户写：

```sql
SELECT name
FROM Student
WHERE age > 20;
```

- 数据库不会简单理解成“先扫文件再打印”。
- 它更可能在逻辑上理解成：

```text
投影 name
  <- 选择 age > 20
       <- Student
```

- 这已经是关系代数风格的表达了。
- 你先不用急着背“选择、投影”的正式符号。
- 你先抓住本质：
- `一个查询可以表示为一系列有输入输出的逻辑运算。`

- 这就是为什么 `P1` 和 `bustub` 有直接关系。

**最小实现视角**
- 虽然 `P1` 偏理论，但我还是要把它拉回工程。

- 如果你自己写一个最小数据库，你迟早要定义一个“逻辑计划节点”结构。
- 哪怕不完整，也大概会长成这样：

```cpp
enum class PlanType {
  SeqScan,
  Filter,
  Projection
};

struct PlanNode {
  PlanType type;
  std::vector<PlanNode *> children;
};
```

- 你看，这里最关键的不是 C++ 语法。
- 而是背后的思想：
- 一个查询不是一坨不可分解逻辑
- 它是一棵由若干关系运算组成的树

- 这正是 `P1` 在为你铺路。
