**bustub 组件地图**

```text
DiskManager          读写 page 字节到文件
BufferPoolManager    frame 池 + page table + pin/dirty + 调 replacer
Replacer (LRUK等)    选 evict 哪个 frame
Page / FrameHeader   内存页对象与元数据
PageGuard            RAII 管理 pin/unpin
TableHeap / B+Tree   FetchPage 的消费者
```

- 数据流：

```text
上层要 page_id
  -> BPM::FetchPage (pin++)
  -> 返回 PageGuard 或 Page*
  -> 读写 page bytes
  -> guard 析构或 Unpin (pin--)
```

- 不要让 TableHeap 直接调 DiskManager 读 page，除非你在做极简原型且明确绕过 BPM。

---

**DiskManager：BPM 的下游**
- 负责：
- ReadPage(page_id, char *dest)
- WritePage(page_id, const char *src)
- 新页分配（AllocatePage）等

- page_id 到文件偏移通常是：

```text
offset = page_id * PAGE_SIZE
```

- BPM 不关心 TablePage 语义，只搬运 PAGE_SIZE 字节。
- 这保证了 BPM 可被索引、表、系统 catalog 共用。

**如果没有 DiskManager 抽象**
- BPM 和文件格式绑死，测试无法 mock 磁盘。

**BufferPoolManager 核心 API（概念集）**
- FetchPage(page_id)
- NewPage(page_id *)
- UnpinPage(page_id, is_dirty)
- FlushPage(page_id)
- FlushAllPages()
- DeletePage(page_id)

- 你要为每个 API 写清：
- 前置条件（例如 page 必须已在 pool 且 pinned？）
- 后置条件（pin_count、dirty、page_table 变化）
- 失败返回什么

**PageGuard：把 pin 生命周期绑进类型系统**
- 裸指针问题：

```cpp
Page *p = bpm->FetchPage(7);
// ... 中间可能 evict page 7 ...
p->GetData();  // 危险：p 可能已悬空
```

- PageGuard 思路：
- 构造时 Fetch 并 pin。
- 析构时自动 Unpin。
- 禁止拷贝或仅允许移动，避免 double unpin。

```cpp
{
  WritePageGuard guard = bpm->FetchPageWrite(7);
  guard.AsMut<TablePage>()->InsertTuple(...);
}  // 析构自动 Unpin，若改动了则 mark dirty
```

**为什么这是正确性设施**
- 不是 C++ 炫技，而是强制“谁最后持有谁负责 unpin”。
- 异常路径、早 return 也不泄漏 pin。

**初学者易错点**
- 把 guard 存到全局容器，生命周期超过预期，page 永不被 evict。
- 从 guard 取出裸指针传到异步线程，别的线程 evict 同一 page。

---

**Replacer 与 BPM 的契约**
- bustub LRUKReplacer 典型接口语义：
- RecordAccess(frame_id)：记录访问。
- SetEvictable(frame_id, bool)：pin=0 时可 true，pin>0 必须 false。
- Victim(&frame_id)：选一个 evictable frame。

**Victim 选不出时**
- 说明所有 frame 都被 pin。
- FetchPage 应失败或等待（看课程设定）。
- 这是“忘记 unpin”的第一现场。

**最小实现路径（推荐）**

**对应 Code 目录**
- 这一段如果要动手实现，代码统一放在 `Code/p4_buffer_pool/`。
- 这一课在 `Code/` 里的主题是：`Buffer Pool、Page Table、Pin/Unpin、Replacer`。
- 建议起手顺序：先让单线程 FetchPage / NewPage / UnpinPage / FlushPage 跑通。


**阶段 1：单线程 + 固定 pool**
- frames_[pool_size]，pages_[pool_size]。
- page_table_ 哈希。
- Fetch / Unpin / Flush。
- replacer 先用 FIFO 或 Clock。

**阶段 2：NewPage + DeletePage**
- 支持 B+Tree/TableHeap 分配新页。

**阶段 3：PageGuard**
- 把 TableHeap 改成 guard 风格访问。

**阶段 4：LRU-K replacer**
- 替换 FIFO，跑 bustub 自带测试。

**阶段 5：并发 latch**
- BPM 全局 latch 或 page-level latch（按项目要求）。
- 先保证单线程全绿，再加锁；不要一步多线程。

**与 P3 TableHeap 的集成点**
- TableHeap::InsertTuple 需要：
- Fetch 某 TablePage（Write guard）
- 插入 tuple，可能改 dirty
- Unpin（guard 析构）

- Iterator 扫描：
- 逐个 page_id Fetch（Read guard）
- 读 tuples，Unpin

- 集成测试：Insert + Scan 全流程走 BPM，而不是内存假 page。

---

**与 WAL 的边界（现在知道接口即可）**
- 修改 page 前，日志应先写（WAL 原则）。
- BPM FlushPage 写数据文件，不替代 WAL。
- checkpoint 可能触发 FlushAllPages。

- 若你先在 P4 不写 WAL，也要留 dirty 标记和 Flush 接口，后面恢复课能接上。

---

**边界陷阱专题**

**陷阱 1：double pin 误解**
- 同一线程 Fetch 同一 page 两次，pin_count 应为 2，Unpin 也要两次。
- 只 Unpin 一次就 evictable，另一持有者 UAF。

**陷阱 2：evict 后 page_id 复用 frame**
- frame 5 先装 page 3，后装 page 9。
- 若旧指针还在，读写的是 page 9 内容以为是 page 3。

**陷阱 3：Flush 失败仍 clear dirty**
- 磁盘写失败却 dirty=false，丢数据。

**陷阱 4：DeletePage 后 page_table 残留**
- Fetch 以为还在内存，读到 stale frame。

**陷阱 5：replacer 与 pin 不同步**
- pin=0 但未 SetEvictable(true)，pool 假满。
- pin>0 却 evictable，灾难。

---

**调试手册：现象 -> 检查项**

| 现象 | 优先检查 |
|------|----------|
| pool is full / no evictable frame | 哪些 page pin 没归零？PageGuard 泄漏？ |
| 重启后数据回滚 | dirty evict 前是否 flush？WAL 顺序？ |
| 偶发 tuple 乱码 | unpin 后仍用 Page*？并发无 latch？ |
| 同一 page 两 frame | page_table 插入/evict 逻辑 |
| 测试 hang | 等 evict 但全 pinned |

- 建议在 Debug 构建加：

```cpp
void BufferPoolManager::AssertInvariants() {
  // 每个 occupied frame 的 page_id 在 page_table 反查一致
  // pin>0 -> replacer 不可 evict
  // pin_count 无下溢
}
```

- 每个单测结束调用 AssertInvariants。
