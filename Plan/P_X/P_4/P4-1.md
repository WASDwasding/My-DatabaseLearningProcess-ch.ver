`P3` 你已经知道数据在磁盘上按 page 组织，TableHeap 通过 BufferPoolManager 间接读写 page。但磁盘太慢、内存有限——这一课专门解决：`怎样在内存里缓存 page、怎样安全地换入换出、怎样不让并发和刷盘把正确性搞崩。` **P4-1 开始**

**今天这次的目标**
- 我们现在正式开始 `P4`，主题是：`内存管理与缓冲池`。
- 这一段先建立总框架，不急着实现 LRU。
- 你学完这一段后，应该能回答 3 个问题：
- 为什么数据库不能每次访问都直接读磁盘文件。
- page 和 frame 有什么区别。
- pin/unpin 为什么是正确性问题，而不只是性能问题。

**先把 `P3` 和 `P4` 接起来**
- `P3`：page 是磁盘 I/O 单位，TablePage 管页内 tuple。
- 但 executor 读数据时，如果每个 RID 都触发一次磁盘 read：
  - 延迟爆炸
  - 吞吐崩溃
  - 磁盘寿命和系统负载都不可接受

- 所以必须有缓存层：
- `Buffer Pool（缓冲池）= 在内存里缓存一组 disk page 的框架 + 生命周期协议`

- 在 bustub 里，这条链是：

```text
TableHeap / Index
  -> BufferPoolManager::FetchPage(page_id)
       -> 命中：返回内存中的 page
       -> 未命中：选 frame，必要时 evict，再从 DiskManager 读入
  -> 用完后 UnpinPage
```

- 如果 `P4` 学不稳，后面 B+Tree 分裂、WAL 刷盘、并发访问都会出现“偶发、难复现、一 evict 就炸”的 bug。

---

**先给你一张总图**
- 缓冲池在系统里的位置：

```text
        +------------------+
        | Executor / Index|
        +--------+---------+
                 |
        +--------v---------+
        | BufferPoolManager |
        |  page table       |
        |  pin counts       |
        |  replacer (LRU-K) |
        +--------+---------+
                 |
        +--------v---------+
        |   DiskManager     |
        |   (文件 I/O)      |
        +-------------------+
```

- 三层各管什么：
- 上层：逻辑上要某个 page_id 的内容。
- BPM：这个 page 现在在不在内存？在哪个 frame？能不能 evict？
- 磁盘：持久化副本。

---

**问题定义**
- 什么是 buffer pool？
- `buffer pool 是数据库在内存中维护的一组固定槽位（frame），用于缓存磁盘 page，并通过 pin/unpin、dirty 标记和替换策略管理页生命周期。`

- 什么是 frame？
- `frame 是 buffer pool 中的一个内存槽位，某一时刻最多承载一个 disk page 的内容。`

- 什么是 page table？
- `page table 维护 page_id 到 frame_id 的映射，回答“这个逻辑页现在是否在内存里”。`

- 注意：这里的 page 仍然是 `P3` 里的逻辑页；frame 是它在内存里的“容器”。

---

**为什么不能每次都读磁盘**
- 第一性原理：局部性。

- 时间局部性：
- 刚读过的 page，很可能马上再读（例如 B+ 树同一节点、同页内多条 tuple）。

- 空间局部性：
- 读一个 page 时，相邻 page 也可能马上被访问（范围扫描、预读）。

- 如果没有缓存：
- 每次 GetTuple 都可能是一次磁盘 I/O。
- 一条 SQL 可能触发成千上万次 I/O，而实际 distinct page 可能只有几十个。

**代价对比（数量级直觉）**
- 内存访问：纳秒级。
- 磁盘随机读：微秒到毫秒级。
- 差 3–5 个数量级很常见。

- 所以数据库的第二个工程结论（接 `P3` 之后）：
- `必须在内存中复用已读入的 page，并控制内存上限。`

---

**page vs frame：必须分清**
- 初学者最高频混淆之一。

```text
page_id = 3   （磁盘/逻辑世界的页编号）
frame_id = 7  （内存 buffer pool 里的槽位编号）
```

- 关系：
- 同一时刻，一个 frame 最多映射一个 page_id。
- 一个 page_id 最多出现在一个 frame 里（在单 buffer pool 实例下）。
- page 被 evict 后，frame 7 可能下次装 page_id=9。

- 类比：
- page 像“书的内容身份”（第 3 章）
- frame 像“书桌上的某一个位置”（第 2 个桌位）
- 桌位有限，章节会被换下来，但章节编号不变

**如果没有这层区分**
- 你会用 frame_id 当 RID 的一部分，evict 后全乱。
- 你会以为“内存指针 = 永久 page 地址”，unpin 后还在用，UAF。

---

**buffer pool 不是普通 LRU 缓存**
- 应用层缓存（如 Redis、本地 HashMap）常常：
- 键不存在就算 miss
- evict 旧条目，一般没人持有旧指针

- 数据库 buffer pool 额外有硬约束：

**1. pin 协议**
- 正在使用某 page 的线程必须 pin 住它。
- pin count > 0 的 frame 不能被 evict。

**2. dirty 协议**
- 若 page 在内存中被改过，标记 dirty。
- evict 前若是 dirty，必须先 flush 到磁盘。

**3. 与 WAL 的配合（预告）**
- 刷脏页顺序和日志顺序有协议，不能乱 flush。

- 所以：
- `buffer pool 替换策略是性能问题 + 正确性问题 + 恢复问题的交叉点。`

---

**pin / unpin：为什么不是可选优化**
- FetchPage 典型语义：
- 若 page 已在内存：pin count++，返回 page 指针。
- 若不在：分配 frame，读盘，建立映射，pin count=1。

- UnpinPage 典型语义：
- pin count--。
- 若降到 0，该 frame 重新变为“可驱逐候选”。

**如果忘记 unpin**
- 可驱逐 frame 耗尽。
- 新 page 无法载入，系统假死或报错。
- 这不是“性能差一点”，是资源泄漏型正确性故障。

**如果 pin 期间 evict**
- 上层仍持有 page 指针，内存已被复用给别的 page。
- 读写随机内存，数据损坏，极难调试。

- 所以 bustub 引入 PageGuard：
- 把“持有 page 指针”和“pin 生命周期”绑定在 RAII 对象上。

---

**核心术语入门**
- `BufferPoolManager (BPM)`：缓冲池总控，Fetch/New/Flush/Unpin。
- `FrameHeader`：每个 frame 的元数据：page_id、pin_count、is_dirty 等。
- `PageTable`：page_id -> frame_id 哈希或数组映射。
- `Replacer`：LRU、Clock、LRU-K 等，决定 evict 哪个 unpinned frame。
- `DiskManager`：负责 read/write page 到文件偏移。

---

**一次 FetchPage 的完整故事（命中）**
- 1. 查 page table：page_id=5 是否在内存？
- 2. 在，frame_id=2，pin_count 从 0 变 1。
- 3. 返回 frame 2 的 page 内存地址。
- 4. 调用者读/改 TablePage。
- 5. UnpinPage(5)，pin_count 变 0。
- 6. replacer 记录 frame 2 为最近使用或可驱逐候选。

---

**一次 FetchPage 的完整故事（未命中 + 需 evict）**
- 1. page_id=9 不在内存。
- 2. 找 free frame；若无，问 replacer 选一个 pin_count=0 的 frame。
- 3. 若被选 frame 是 dirty：先 FlushPage 到磁盘。
- 4. 从 page table 删掉旧 page_id 映射。
- 5. DiskManager 读 page 9 到该 frame。
- 6. 建立 page_id=9 -> frame 映射，pin_count=1。
- 7. 返回指针。

- 这条路径任何一步错序，都可能 corrupt 数据或丢更新。

---

**不变量：现在就要建立的 4 条**
- `B1`：pin_count > 0 的 frame 不得被 replacer 选中 evict。
- `B2`：evict dirty frame 前必须 flush 成功，或系统明确 abort。
- `B3`：page table 与 frame 内容一致：映射存在当且仅当 frame 持有该 page_id。
- `B4`：Unpin 之后，调用者不得再使用之前拿到的 page 指针（除非再次 Fetch 并 pin）。

---

**没有 buffer pool 会怎样**
- 性能：每条 tuple 一次磁盘 I/O。
- 正确性：难以与 WAL、checkpoint 配合。
- 工程：TableHeap、B+Tree 每个模块都要自己读文件，边界全乱。

---

**和 bustub 的对齐**
- 直接对应：
- `BufferPoolManager`
- `DiskManager`
- `LRUKReplacer`（或课程指定 Replacer）
- `PageGuard` / `ReadPageGuard` / `WritePageGuard`

- 读源码建议顺序：
- Frame 状态字段
- FetchPage / UnpinPage
- Replacer 接口
- NewPage / DeletePage（分配新页）

---

**初学者易错点**
- 把 BPM 当成“全局 new 一个 page 数组随便用”。
- Fetch 后不 Unpin，跑几个测试就“pool full”。
- evict 时不 flush dirty page，重启后丢修改。
- 多线程不加 latch，page table 和 pin_count 竞态。
